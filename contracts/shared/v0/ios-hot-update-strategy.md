# iOS 热更新分发策略（v0）

## 背景

本策略用于约束 Chaos.IL2CPP 热更新包在 iOS 渠道下的分发边界，目标是在不修改宿主原生二进制的前提下，仅分发可被解释执行的托管增量内容。

## App Store 边界

- Apple App Store Review Guideline 2.5.2 要求应用不得下载、安装或执行会改变应用主要功能的代码，除非这些代码完全运行在 Apple 提供的 WebKit / JavaScriptCore 等允许环境中。
- Apple Developer Program License Agreement 3.3.2 允许脚本类内容在解释执行前提下动态下发，但前提是不绕过平台安全模型，也不改变应用的审核属性。
- 因此 iOS 热更新包只能承载托管 IL bytecode、补充元数据和声明性配置，不得分发原生可执行代码。

## 允许内容

- 托管程序集 `.dll`，内容应为可被解释执行的 IL bytecode。
- HybridCLR/解释执行所需的补充元数据文件。
- 纯数据配置、资源索引、版本签名等非可执行描述文件。

## 禁止内容

- 任何原生动态库或原生可执行载荷，例如 `.dylib`、`.so`、`.framework`。
- 依赖 `dlopen`、`dlsym`、`mmap` 等原生装载或内存映射入口的热更新包逻辑。
- 以热更新包形式分发新的 Objective-C / C / C++ 机器码，或通过桥接方式绕开宿主预编译能力边界。

## 落地约束

- 宿主应用必须预置热更新运行时能力，热更新包只提供托管层增量。
- 校验器在分发前检查包大小、文件扩展名和受限 API 标记，提前阻断不符合 2.5.2 / 3.3.2 的内容。
- 真实上架前仍需结合 macOS + Xcode + 真机证据进行最终验证；本仓库当前仅提供 Windows 可执行的基础合规防线。
