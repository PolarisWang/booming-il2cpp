# 平台抽象层（verification/platforms）

## 概述

`tests/e2e/verification/platforms/` 把验证管线里的**平台差异**收敛到一处。在此
之前，hotupdate 阶段的三处平台知识全部硬编码为「MSVC + Visual Studio 生成器」，
导致任何非 MSVC 平台直接跳过该阶段 —— Linux 上 hotupdate 覆盖为 0，chunk 永远
拿不到满分。

新增一个平台（android / ios / 其他交叉编译目标）应该只是**注册表加一行**，而不是
在 stage 里再加一个 `if sys.platform`。

## 为什么要抽象：一个具体缺陷

hotupdate 的 distinct-linking 机制依赖「两个 .cpp 定义同名符号，靠链接顺序决定谁赢」：

```
patch-host-arrays.cpp    → 真实的 kPatchDataHost* 数组
runtime-patchdata.cpp    → 哨兵（声称 0 个 patch）
```

patch 必须赢，否则 hotupdate 静默地什么都没做却报告通过。原实现用三步保证：

1. 改 CMakeLists，把 patch 文件列在哨兵之前
2. 构建
3. **解析 MSBuild 构建日志**，事后推断哪个文件先编译

第 3 步是平台耦合的根源 —— 它只认 MSBuild 的日志格式，于是整个阶段在
Linux/Ninja 上被守卫直接跳过。

**关键洞察**：CMake 在 `add_executable` 中**保持源文件顺序**（Ninja 与 Unix
Makefiles 已实测），而链接器**保留第一个定义**（MSVC `LNK4006` 与 GNU ld
`--allow-multiple-definition` 语义一致，两种链接顺序均已实测）。既然「列在前面」
本身就是保证，就不需要再读日志去事后推断 —— 改为**观察运行时结果**。

## 三层抽象

| 层 | 文件 | 职责 | 不该做什么 |
|---|---|---|---|
| 产物布局 | `layout.py` | 纯路径算术：对象目录、可执行文件、对象 glob | 不做平台判断、不调 subprocess |
| 链接器能力 | `linker.py` | 能否容忍重复符号、用哪个 flag | 不关心产物在哪 |
| 打补丁策略 | `patch_link.py` | 如何让 patch 符号赢 | 不做路径计算 |

层次边界是刻意的：`BuildTreeLayout` 若要真实构建才能测试，说明它管得太多了。
现有单元测试对 layout 全部用 `tmp_path` 假目录，不需要 cmake 或编译器。

### layout.py

```python
class BuildTreeLayout(Protocol):
    def object_dir(self, build_dir, config) -> Path
    def executable(self, build_dir, config, stem) -> Path
    def object_glob(self, build_dir, config, stem) -> str
```

| 实现 | 对象目录 | 可执行文件 |
|---|---|---|
| `MsBuildLayout` | `build/chaos_entry.dir/RelWithDebInfo/` | `build/RelWithDebInfo/chaos_entry.exe` |
| `NinjaLayout` | `build/CMakeFiles/chaos_entry.dir/` | `build/chaos_entry` |

Ninja 与 Makefiles 共用 `NinjaLayout` —— 二者的差异在**如何驱动构建**，不在产物
布局，本层刻意不建模。

### linker.py

```python
@dataclass(frozen=True)
class LinkerProfile:
    name: str
    duplicate_symbol_flag: str | None    # None = 该链接器不支持
```

| 平台 | name | flag |
|---|---|---|
| Windows + MSVC | `msvc` | `/FORCE:MULTIPLE` |
| Linux | `gnu-ld` | `-Wl,--allow-multiple-definition` |
| macOS | `apple-ld` | **None**（无等价物） |
| Windows 无 MSVC | `windows-non-msvc` | **None** |

**`None` 是刻意设计**：clang-cl / MinGW 也设 `sys.platform == 'win32'`，但不接受
`/FORCE:MULTIPLE`。若给它一个 flag，最好的结果是链接报错，最坏的结果是哨兵赢了
却报告成功。`duplicate_symbol_flag is None` 让调用方**必须**注意到并改走别的策略。

### patch_link.py

```python
class PatchLinkStrategy(Protocol):
    def is_available(self, layout, linker) -> bool
    def cmake_reorder(self, cmake_text, patch_stem, sentinel_stem) -> str | None
    def link_flags(self, linker) -> list[str]
```

| 策略 | 状态 | 适用 |
|---|---|---|
| `distinct_link` | ✅ 已实现 | MSVC / GNU ld / lld |
| `weak_symbol` | ⬜ **仅接口** | 哨兵标 `__attribute__((weak))`；Android 用得上 |
| `single_tu` | ⬜ 未实现 | 条件编译合并成单 TU；iOS 无 flag 时的出路 |

`weak_symbol` 的 `is_available()` 返回 `False`，保证**不会被误选** —— 接口存在是
为了标明扩展方向，不是半成品。

### registry.py

```python
PLATFORM_REGISTRY = {
    "win32":  PlatformSpec("win32",  MsBuildLayout(), LinkerProfile("msvc", "/FORCE:MULTIPLE"),              ("distinct_link",)),
    "linux":  PlatformSpec("linux",  NinjaLayout(),   LinkerProfile("gnu-ld", "-Wl,--allow-multiple-definition"), ("distinct_link", "weak_symbol")),
    "darwin": PlatformSpec("darwin", NinjaLayout(),   LinkerProfile("apple-ld", None),                       ("weak_symbol",)),
}
```

**新增平台 = 加一行。** 查表用前缀匹配，因此 `linux2` 等历史值也能命中。

## 验证语义的变更（重要）

删除日志解析后，改为两级验证：

| 检查 | 作用 | 捕捉的失败 |
|---|---|---|
| `verify_patch_objects_linked` | patch 对象参与了链接 | 「CMakeLists 手术静默失效」—— 否则与成功无法区分 |
| `verify_patch_active` | 运行 `entry.exe --hotupdate`，确认 patch 真正生效 | 哨兵赢了链接（校验 0 patch 必然失败） |

`verify_patch_active` **严格强于**原来的顺序推断：它观察的是顺序本应产生的**结果**，
且与构建生成器无关。原实现是「推断原因」，新实现是「观察结果」。

**注意 `verify_patch_active` 处理了引擎日志污染**：引擎会把 WARN 写到 stdout，
所以它先用 `find("{")` / `rfind("}")` 定位 JSON，而不是假设整个流是 JSON。

## 新增平台指南

以 android 为例：

1. **layout**：若用 Ninja/Makefiles，复用 `NinjaLayout`，无需新类。
2. **linker**：查该平台链接器是否支持重复符号容忍，填 `LinkerProfile`。
   注意「保留第一个」这半个语义同样必要 —— 只容忍重复但保留最后一个的链接器，
   distinct-linking 的杠杆就不成立。
3. **策略**：若链接器不支持，`patch_link_strategies` 里不要列 `distinct_link`；
   此时需要先实现 `weak_symbol` 或 `single_tu`。
4. **注册**：往 `PLATFORM_REGISTRY` 加一项。

**iOS 特别注意**：Apple ld 没有 `--allow-multiple-definition`，因此 iOS 必须走
`weak_symbol` 或 `single_tu`，注册表里**不应**列 `distinct_link`。单元测试
`test_platform_without_duplicate_support_does_not_offer_distinct_link` 就是在
钉住这条约束 —— 平台不得宣称自己能跑做不到的策略。

## 测试

```bash
python -m pytest tests/e2e/verification/tests/test_platform_*.py
```

| 文件 | 覆盖 |
|---|---|
| `test_platform_layout.py` | 两种 layout 的路径计算、平台选择 |
| `test_platform_linker.py` | 链接器能力、注册表一致性、策略选择与降级 |
| `test_platform_patch_link.py` | 运行时验证：零 patch 必须失败、容忍日志前缀、不依赖构建日志 |

测试全部不依赖真实 cmake/编译器 —— 这是分层的直接收益。

## 一个踩过的坑：包名不能叫 `platform`

本包原名 `verification/platform/`，**遮蔽了 Python 标准库的 `platform`**：
`verification/` 在 `sys.path` 上时，`build.py` 与 `nightly/run.py` 的
`import platform` 会解析到本包，报
`AttributeError: module 'platform' has no attribute 'system'`。

已改名 `platforms`。**新增包时留意不要与标准库同名** —— 这类问题只在运行时
特定 import 顺序下暴露，静态检查看不出来。
