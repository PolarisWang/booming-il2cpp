## 二、各能力缺口分析

### #1: 模块间集成测试 ✅ 已实施

**问题**：所有测试目标是模块级隔离的（GC 只测 GC、Interpreter 只测 Interpreter），没有跨模块编排的集成测试。实际运行时，GC 可能在 Interpreter 执行中间触发，Threading 可能在 GC 进行时分配。

**实施**：在 `testing/project-test/runtime-self-test/` 中新增了 4 个集成测试用例：

| 测试方法 | 涉及子系统 | 验证场景 |
|----------|-----------|----------|
| `GcAndDelegateInvoke` | GC + Delegate dispatch | 创建委托 → GC.Collect() → 委托仍可正确调用 |
| `FinalizerAndNewAllocation` | GC + Finalizer | 创建可终结对象 → GC + WaitForPendingFinalizers → 新分配对象正常 |
| `GcAcrossMethodCalls` | GC + Interpreter dispatch | 多阶段数组分配 → 跨方法调用触发 GC → 累加和正确 |
| `ThreadedGcAllocation` | GC + Threading + Monitor | 后台线程持续分配 → 主线程强制 GC → 共享计数器通过 lock 同步正确 |

**文件**：
- `testing/project-test/runtime-self-test/managed/src/IntegrationProof.cs`
- `testing/project-test/runtime-self-test/managed/src/Program.cs`
- `testing/project-test/runtime-self-test/expected/fact-output.txt`
- `testing/project-test/runtime-self-test/project.json`

**验证方式**：通过 project-test fact 管线运行，验证 stdout 输出 `RTS_INT_*=` 行是否与 expected/fact-output.txt 匹配。

### #2: 测试资源自动清理

**问题**：多个测试共享全局状态（GC 全局区、TLAB、Thread 注册表、MemoryDomain），一个测试泄漏会影响后续测试。当前依赖手动 `SetUp`/`TearDown`，但缺乏自动化泄漏检测。

**预期方案**：
- 在 `gc_test_base.h` 的 `GcTestBase` 中增加 RAII 资源追踪：
  - `TearDown()` 时自动断言：分配的 Region 数 == 初始 Region 数
  - 注册的线程列表回到初始状态
  - TLAB 被正确清空
- 新增 `GcResourceTracker` 类，在 `SetUp()` 中快照全局状态，`TearDown()` 中比对
- 测试框架级：`add_chaos_test()` 宏可选注入 `--gtest_repeat` 以检测跨测试污染

**工作量估计**：2-3 天

**影响范围**：`testing/src/native/runtime-core/gc/gc_test_base.h`、`gc_test_base.cpp`

### #3: 测试分类标签

**问题**：当前只有 `benchmark`、`stress`、`gc` 三个 ctest 标签。没有 `smoke`、`unit`、`integration`、`regression` 等粒度分类。无法按测试类型筛选运行。

**预期方案**：
- 在 `add_chaos_test()` 宏中增加 LABELS 参数默认值：
  ```cmake
  add_chaos_test(test_gc_region
      gc_region_test.cpp
      LIBS ...
      LABELS "unit;gc;region"
  )
  ```
- 定义标准标签体系：
  | 标签 | 含义 | 示例 |
  |------|------|------|
  | `smoke` | 快速冒烟 | 构建验证、基本分配 |
  | `unit` | 单组件测试 | scheduler、TLAB、bit_utils |
  | `integration` | 跨模块测试 | GC+Threading、GC+Interpreter |
  | `stress` | 压力测试 | 多线程 GC 压力 |
  | `benchmark` | 性能基准 | gen1_benchmark、throughput |
  | `regression` | 回归测试 | 已修复 bug 的复测 |

**工作量估计**：1-2 天

**影响范围**：`testing/src/native/CMakeLists.txt`（`add_chaos_test` 宏），所有子 CMakeLists.txt

---

### #4: 性能回归门禁

**问题**：benchmark 测试运行后只输出 JSON，没有自动比较基线、判定退化/进步的逻辑。每次人工读 JSON 对比不可持续。

**预期方案**：
- 实现 Python 工具 `testing/scripts/benchmark_compare.py`：
  - 读取 benchmark JSON 输出
  - 对比 `results/baselines/` 中的基线（自动保存上次运行的 JSON）
  - 计算退化/进步百分比
  - 输出 PASS（退化 < 5%）、WARN（5-15%）、FAIL（> 15%）
  - 支持 `--update-baseline` 标志更新基线
- 在 CI 中作为可选步骤运行

**与 foundation-dll verification pipeline 的关系**：
- `<assembly>/<family>/benchmark/` 已有 3-way benchmark 比较逻辑（`benchmark_comparator.py`）
- 本能力应为通用版本，适用于 `testing/` 内所有 benchmark label 的测试

**工作量估计**：3-5 天

**影响范围**：`testing/scripts/benchmark_compare.py`（新文件），`results/baselines/` 目录

### #5: 参数化测试工厂

**问题**：GC 测试中有大量"相同逻辑、不同参数"的模式（如不同 size class、不同线程数），目前靠复制 `TEST_F` 或手写循环。代码膨胀且容易遗漏边界值。

**预期方案**：
- 封装 GC 专用参数化宏：
  ```cpp
  // 自动注册 size_class × thread_count 的叉积组合
  GC_PARAM_TEST(AllocationSizeAndThreads, GcTestBase,
      GcParamRange<size_t>(16, 1024, 16),      // size: 16,32,...,1024
      GcParamRange<int>(1, 8)                    // threads: 1,2,...,8
  );
  ```
- 或者用 gtest 原生 `testing::Values` + `testing::Combine`，但封装成更简洁的 DSL
- 关键收益：测试逻辑写一次，参数组合由宏自动展开

**备选**：直接使用 gtest 的 `TEST_P` + `INSTANTIATE_TEST_SUITE_P`——大部分团队已经熟悉，不需要额外 DSL 开销。

**工作量估计**：2-3 天

**影响范围**：`testing/src/native/runtime-core/gc/gc_test_macros.h`

---

### #6: 不稳定测试隔离机制

**问题**：压力测试偶尔因时序问题 flaky（如 BGC stress、delegate stress），但失败的测试被当成"真红"，掩盖了真正的回归。目前没有自动重试或隔离机制。

**预期方案**：
- ctest 层面：`ctest --test-dir build -C RelWithDebInfo --repeat until-pass:3`
  - 为所有 stress label 测试默认启用 `--repeat until-pass:2`
- 代码层面：新增 `CHAOS_FLAKY_TEST` 宏：
  ```cpp
  // 标记为 flaky：首次失败自动重试 1 次
  // 连续失败才记为 FAIL
  CHAOS_FLAKY_TEST(GcBgcStress, StressScenario) {
      // ...
  }
  ```
- 配合 `results/flaky/` 日志目录，记录 flaky 测试的失败历史

**注意事项**：不能简单对 retry-pass 的测试完全忽略——需要记录 flaky 率，超过阈值（如 > 20%）应告警。

**工作量估计**：2-3 天

**影响范围**：`testing/src/native/CMakeLists.txt`、gc_test_macros.h、CI 配置

### #9: 内存分配追踪

**问题**：没有测试断言"这个操作应该分配 0 次 GC 内存"的能力。性能测试需要知道分配计数和分配大小，但当前 benchmark 只测量耗时。

**预期方案**：
- 新增 `GcAllocationTracker` RAII 类：
  ```cpp
  class GcAllocationTracker {
      int64_t alloc_count_before_;
      int64_t alloc_bytes_before_;
  public:
      GcAllocationTracker() {
          alloc_count_before_ = g_gc_scheduler.total_alloc_count();
          alloc_bytes_before_ = g_gc_scheduler.total_alloc_bytes();
      }
      ~GcAllocationTracker() {
          int64_t delta_count = g_gc_scheduler.total_alloc_count() - alloc_count_before_;
          int64_t delta_bytes = g_gc_scheduler.total_alloc_bytes() - alloc_bytes_before_;
          // 在析构时自动记录或断言
      }
      int64_t AllocCount() { ... }
      int64_t AllocBytes() { ... }
  };
  ```
- 用法示例：
  ```cpp
  TEST_F(SomeTest, NoAllocation) {
      GcAllocationTracker tracker;
      DoOperation();  // 应零分配
      EXPECT_EQ(tracker.AllocCount(), 0);
  }
  ```
- 与 benchmark 集成：benchmark 输出 JSON 时附带 `alloc_count` 和 `alloc_bytes` 字段

**工作量估计**：3-4 天

**影响范围**：`src/native/runtime-core/gc/gc_scheduler.h`（需要暴露统计计数器）、`testing/src/native/runtime-core/gc/gc_test_base.h`

### #10: Fuzz 测试入口

**问题**：IL 翻译路径、GC 分配路径有大量边界情况（空 IL 序列、超大分配、无效 token），目前靠人工枚举用例，覆盖不全。

**预期方案**：
- IL Fuzzer：生成随机 IL 指令序列 → 送入 Interpreter → 验证不崩溃
  - 输入空间：所有 IROpCode、寄存器组合、立即数范围
  - oracle：不崩溃 + 不触发 ASSERT
- GC Fuzzer：随机分配大小（含对齐边界）、随机线程数、随机 GC 触发时机
  - 使用 libFuzzer（Windows 支持正在完善）或自定义的简单 fuzzer
- 作为独立测试目标注册：
  ```cmake
  add_chaos_test(test_fuzz_il
      fuzz_il_test.cpp
      LIBS ...
  )
  set_tests_properties(test_fuzz_il PROPERTIES TIMEOUT 600 LABELS "fuzz")
  ```

**工作量估计**：5-10 天（含 fuzzer 框架搭建 + 初始种子语料库）

**影响范围**：`testing/src/native/fuzz/` 新目录、`src/native/interpreter/` 可能需要增加 fuzz 友好的入口

### #12: 测试结果仪表盘

**问题**：目前结果散落在 `results/` 目录、`foundation-dll/reports_generated/` 和 CI 日志里，没有统一的趋势图。无法直观看到 benchmark 性能随时间的变化。

**预期方案**：
- 阶段一（轻量级）：在 `scripts/` 中增加 `generate_report.py`
  - 扫描 `results/` 下所有 benchmark JSON
  - 输出一个 `results/dashboard.html` 静态页面
  - 包含：测试通过率、benchmark 耗时趋势（用 Chart.js 或简单表格）
- 阶段二（CI 集成）：在 CI 中收集结果，推送到 GitHub Pages：
  - `gh-pages` 分支托管 `dashboard.html`
  - 每次 CI 运行更新
- 阶段三（高级）：对接 InfluxDB + Grafana
  - benchmark JSON → InfluxDB line protocol
  - Grafana 面板展示跨时间维度的性能趋势

**当前已有的基础设施**：
- `testing/results/benchmarks/` — native benchmark JSON 存储
- `testing/results/coverage/` — 覆盖率数据
- `<family>/reports_generated/` — foundation-dll pipeline 报告

**工作量估计**：阶段一 2-3 天，阶段二 2 天，阶段三 5-7 天

### #13: CRT/内存错误检测标准化

**问题**：ASan 已集成但仅限 debug 构建（`cmake --preset debug`），RELEASE 构建下 `/RTC1` 和 `_CRT_SECURE_NO_WARNINGS` 没有标准化配置。不同测试目标可能使用不同的 CRT 标志。

**预期方案**：
- 在 `config/sanitizers/` 中定义标准化配置预设（已有部分文件）：
  | 配置 | 编译标志 | 链接标志 | 用途 |
  |------|---------|---------|------|
  | ASan | `/fsanitize=address` | `/fsanitize=address` | 日常开发 |
  | RTC | `/RTC1` | — | Release 构建基本检查 |
  | UBSan | `/fsanitize=undefined` | `/fsanitize=undefined` | MSVC 有限支持 |
- 在 CI 中增加 ASan 门禁：
  - 所有 PR 必须通过 ASan 构建 + 运行 smoke 和 unit 测试
  - stress 测试在 ASan 下运行（超时放宽到 2 倍）
- 在 `add_chaos_test()` 中增加 SANITIZE 参数控制每个测试目标的 sanitizer 配置

**已有基础**：
- `testing/config/sanitizers/` 目录已存在
- `testing/src/native/CMakeLists.txt` 已有 ASan DLL 自动复制逻辑
- `asan-suppressions.txt` 已在项目根目录

**工作量估计**：3-5 天

**影响范围**：`testing/src/native/CMakeLists.txt`、`testing/config/sanitizers/`、CI yaml
