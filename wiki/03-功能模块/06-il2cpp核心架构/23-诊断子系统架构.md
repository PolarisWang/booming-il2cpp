# 诊断子系统架构

> Chaos IL2CPP 诊断子系统设计架构概述。涵盖 DAP 调试器、EventPipe 事件管道、SOS 调试扩展和 CommonLibrary 诊断三件套（log/trace/profile）。

## 架构总览

```
诊断子系统 (src/native/diagnostics/)
├── debugger/          # DAP 协议调试器 (v2, 替代 v1 debug_agent)
│   ├── dbg_server.cpp/h     — 请求分发、响应构建、传输写入
│   ├── dbg_protocol.h       — JsonWriter、DapMessageBuilder、协议类型
│   ├── dbg_runtime.cpp/h    — 解释器集成（暂停/恢复/步进）
│   ├── dbg_breakpoint.cpp/h — 断点管理（CRUD、source→IL解析）
│   ├── dbg_stepping.cpp/h   — 步进状态机（StepInto/StepOver/StepOut）
│   ├── dbg_stack.cpp/h      — 调用栈快照
│   └── dbg_variables.cpp/h  — 变量展开与表达式求值
├── eventpipe/         # EventPipe 事件管道
│   ├── ep_protocol.h        — 协议常量、校验和、事件类型
│   ├── ep_event.cpp         — 事件数据构造与发送
│   ├── ep_gc_bridge.cpp     — GC→EventPipe 回调桥接
│   ├── ep_transport.cpp     — 命名管道 I/O (Windows OVERLAPPED)
│   └── receiver/            — chaos_diag.exe CLI 接收器
├── sos/               # WinDbg SOS 调试扩展
│   └── gc_sos.cpp           — DbgEng 扩展 DLL，GC 状态检查命令
└── CMakeLists.txt     — 构建聚合 (CHAOS_IL2CPP_DEBUGGER 开关)
```

CommonLibrary 诊断三件套独立于 diagnostics/ 目录，位于 `src/native/common/chaos/`：
- `log.h` — 分级日志（DEBUG/INFO/WARN/ERROR），线程安全
- `trace.h` — 追踪 ring buffer（JSON 格式，256 条目环形缓冲）
- `profile.h` — RDTSC 性能分析 scope（在 PROFILE 构建中启用）

## 数据流

### DAP 调试器
```
IDE (VS Code) ←→ stdin/stdout JSON-RPC ←→ dbg_server ←→ dbg_runtime → Interpreter 线程
                                      ↕
                              dbg_breakpoint / dbg_stack / dbg_variables
```

### EventPipe
```
GC Runtime → ep_gc_bridge → ep_event (序列化) → ep_transport (命名管道) → chaos_diag.exe (接收/JSON输出)
```

### SOS 扩展
```
WinDbg → gc_sos.dll → IDebugDataSpaces::ReadVirtual → 目标进程 GC 内存
```

## 关键设计决策

| 决策 | 方案 | 理由 |
|------|------|------|
| 调试器协议 | v2 DAP（废弃 v1 debug_agent） | DAP 是 VS Code 标准协议，VS Code 是主要开发环境 |
| EventPipe 平台 | Windows-only | 当前阶段不做 POSIX 抽象；管道 I/O 依赖 OVERLAPPED |
| 线程安全 | shared_mutex + thread_local buffer + atomic flags | 调试器操作频率低，读多写少，shared_mutex 足够 |
| 零开销诊断 | 编译时开关 (`CHAOS_IL2CPP_DEBUGGER`/`CHAOS_IL2CPP_PROFILE_ENABLED`) | 发布构建完全不包含诊断代码 |
| 测试策略 | 单元测试 + 集成测试 + 结构体布局验证 | 覆盖协议解析、业务逻辑、ABI 兼容性三层 |
