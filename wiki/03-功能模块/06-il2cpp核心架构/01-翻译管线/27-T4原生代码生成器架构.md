# JIT 原生代码生成器架构

> T4（JIT）是 Chaos IL2CPP 自适应分层执行系统的第四层，将寄存器分配 IR（`RegisterMethod`）编译为原生 x64 机器码，完全绕过解释器调度循环以获得最大性能。

---

## JIT 定位与分层

Chaos IL2CPP 使用四层自适应执行系统：

| 层级 | 名称 | 执行方式 | 触发条件 |
|------|------|----------|----------|
| T1 | FastExecute | 栈机 IR 直接解释 | 首次执行（cold） |
| T2 | RegisterExecute | 寄存器 IR 解释 | call_count 达到阈值 |
| T3 | RegisterExecute 优化 | 寄存器 IR + inline 缓存 | 热点方法 |
| JIT | 原生代码生成 | x64 机器码直接执行 | 最热方法（T3 再升温后） |

T4 代码生成由 `entry_direct.cpp`（`src/native/interpreter/interp_entry/entry_direct.cpp`）中的 `InterpreterEntryDirect` 触发。当方法达到 JIT 升温阈值时，调用 `GenerateNativeCode` 编译为原生代码，之后所有调用直接执行生成的机器码。

T4 代码通过 `CodeGenConfig` 结构体配置，由调用方（entry_direct）在调用时传入：

```cpp
CodeGenConfig config;
config.enable_safepoint_polls = true;
config.enable_register_caching = true;
config.enable_deopt = true;
config.safepoint_interval = 64;
config.safepoint_fn = reinterpret_cast<void*>(SafepointPoll);
config.pic_dispatch_data = pm->pic_dispatch_data;

NativeMethod* nm = GenerateNativeCode(rm, config);
```

生成的函数遵循标准 x64 调用约定：
```cpp
void native_entry(void* args_buf, void* ret_buf);
// RCX = args_buf, RDX = ret_buf (Win64)
```

## 整体架构

T4 代码生成子系统（JIT 工业化后）由以下文件组成：

| 文件 | 作用 |
|------|------|
| `jit_engine.h/cpp` | 主代码生成器：`NativeCodeGenerator` 类，IR→x64 翻译 |
| `IEncoder.h` | 编码器抽象接口（86 个纯虚 Emit* 方法）|
| `X64Encoder.h` | x64 编码器实现（IEncoder 接口，通过 x64_encoder.h 编码基元）|
| `Arm64Encoder.h` / `arm64_encoder.h` | ARM64 编码器实现（IEncoder 接口），暂未用于 JIT 生产 |
| `ISehHandler.h` | SEH handler 抽象接口（RegisterCode、FindCodeByAddress、DemoteByToken 等）|
| `WinSehHandler.h/cpp` | Windows VEH-based SEH handler（支持 catch/finally/fault）|
| `LinuxSehHandler.h/cpp` | Linux POSIX signal-based SEH handler |
| `jit_seh.h/cpp` | 平台无关的 SEH 转发层（通过 GetSehHandler() 分派）|
| `jit_method.h` | `JitMethod` 结构体（生成代码的元数据，含 GC slot map、OSR entry、deopt 表）|
| `jit_helpers.h/cpp` | 运行时辅助函数（CodegenLdFld、CodegenStFld、CodegenBox、CodegenNewObj、CodegenCallVirt 等）|
| `jit_unwind.h/cpp` | Win64 .pdata/.xdata 和 Linux .eh_frame 展开信息生成 |

文件位置：`src/native/jit/`

## NativeCodeGenerator 类设计

`NativeCodeGenerator` 是 JIT 代码生成的核心类（定义在 `jit_engine.cpp` 中）。

### Generate() 主循环

```
1. SelectCacheableRegs()           — 频次分析选择 R12-R15 候选
2. 发射 Prologue                    — 保存被调用者保存寄存器 + 分配栈帧
3. 遍历所有指令：
   a. 记录 instr_offsets_[i]       — 当前指令在输出缓冲区的偏移
   b. EmitInstruction(instr)       — 翻译单条 IR 指令为 x64
   c. 递增 instr_since_safepoint_   — Safepoint 间隔计数器
   d. 检查间隔回退 poll
4. ResolveBranches()               — 修复前向分支跳转偏移
5. 发射 SEH clause table           — SEH 子句表（有异常处理方法时）
6. buf_.Seal()                     — 完成代码缓冲区
7. 填充 JitMethod 元数据         — call_sites、gc_points、deopt_entries、gc_slot_map
```

### EmitInstruction 分派

根据 `IROpCode` 分派到对应的代码发射逻辑：
- 算术/位运算/比较 → 内联 x64 指令
- 字段访问/数组/Box/NewObj → 辅助函数调用
- 分支/条件分支 → x64 jcc + rel32
- 虚方法调用 → PIC 链 + deopt 回退
- SEH 指令 → CodegenThrow/CodegenRethrow 调用

### Prologue/Epilogue

Prologue（方法入口）：
```asm
push rbp         ; 保存帧指针
push rbx         ; 保存 args_buf
push rsi         ; 保存 ret_buf
push r12-r15     ; 仅当寄存器缓存启用时
sub rsp, 864     ; 分配栈帧（32 shadow + 512 GPR + 256 FPR + 64 CallVirtArgs）
mov rbx, rcx     ; rbx = args_buf
mov rsi, rdx     ; rsi = ret_buf
```

Epilogue（方法出口）：
```asm
SpillCachedRegs  ; 冲刷缓存寄存器到栈帧
add rsp, 864     ; 恢复栈帧
pop r12-r15      ; 仅当寄存器缓存启用时
pop rsi          ; 恢复 ret_buf
pop rbx          ; 恢复 args_buf
pop rbp          ; 恢复帧指针
ret
```

## 帧布局

每个 JIT 方法分配 864 字节栈帧：

| 偏移 | 大小 | 内容 |
|------|------|------|
| RSP+0 | 32 字节 | Win64 影子空间（调用子函数时使用） |
| RSP+32 | 512 字节(64×8) | GPR 寄存器文件（virtual register 0-63） |
| RSP+544 | 256 字节(32×8) | FPR 寄存器文件（virtual register 64-95） |
| RSP+800 | 64 字节 | `CodegenCallVirtArgs` 结构体（仅 CallVirt 使用） |

布局常量：
```cpp
constexpr uint32_t kGprFileOff     = 32;    // RSP+32
constexpr uint32_t kFprFileOff     = 544;   // RSP+544
constexpr uint32_t kCallVirtArgsOff = 800;  // RSP+800
constexpr uint32_t kFrameSize      = 864;   // 总帧大小
```

GPR 的 RSP 偏移计算：`kGprFileOff + vreg * 8`
FPR 的 RSP 偏移计算：`kFprFileOff + (vreg - 64) * 8`

## 指令发射模式

T4 的寄存器文件在栈上（非 x64 寄存器），每条 IR 指令的典型发射模式：

### 算术运算（Load→Compute→Store）
```asm
mov rax, [rsp + GprOff(src1)]   ; LoadGpr scratch, src1
add rax, [rsp + GprOff(src2)]   ; 运算
mov [rsp + GprOff(dst)], rax    ; StoreGpr scratch, dst
```

### 浮点运算
```asm
movsd xmm0, [rsp + FprOff(src1)]  ; LoadFpr xmm0, src1
addsd xmm0, [rsp + FprOff(src2)]  ; 运算
movsd [rsp + FprOff(dst)], xmm0   ; StoreFpr xmm0, dst
```

### 辅助函数调用
```asm
mov rcx, [rsp + GprOff(src)]      ; 参数1
mov rdx, imm32                     ; 参数2
mov rax, <CodegenHelperPtr>        ; 函数指针
call rax
mov [rsp + GprOff(dst)], rax       ; 返回值
```

## Five Stages of JIT V3

T4 V3 实现了五个核心能力阶段：

### Stage 1: Safepoint 回边检测

在以下场景插入 GC Safepoint Poll：
- **条件分支回边**：`Beq/BneUn/Blt/Bgt/Ble/Bge/BltUn/BgtUn/BleUn/BgeUn` 的 `branch_target < current_instr_index_`
- **条件 true/false 分支**：`BrTrue/BrFalse` 的 `branch_target < current_instr_index_`
- **无条件分支**：`Br` 的 `branch_target < current_instr_index_`
- **Switch 回边**：任一 switch target < current 时发射
- **间隔回退**：每 64 条指令（`safepoint_interval`）无回边 poll 时强制发射

EmitSafepointPoll 序列：
```asm
sub rsp, 32                ; 预留影子空间
mov rax, safepoint_fn_ptr  ; 加载 SafepointPoll 函数指针
call rax                   ; 调用
add rsp, 32                ; 恢复影子空间
```

### Stage 2: Deopt OSR（去优化 + 栈上替换）

当 JIT 代码遇到无法处理的情况（overflow、CallVirt PIC miss）时，通过 `kDeoptMagic` 机制回退到解释器：

1. **触发**：T4 代码中的检测点（jo overflow、CodegenCallVirt PIC miss）将 `kDeoptMagic(0xDE0D7FA57A11ULL)` 写入 `ret_buf[0]`
2. **检测**：`entry_direct.cpp` 在 `native_entry` 返回后检查 `ret_buf[0]`
3. **重建**：`DeoptRuntime::DeoptTrap` 从栈帧 spill slot 重建 GPR/FPR 寄存器文件
4. **回退**：将重建的寄存器状态写入 `t_deopt_state`（TLS），跳转到 RegisterExecute 路径

去优化数据流：
```
T4 call → 检测到 overflow
  → DeoptTrapEntry(ctx, codegen_rsp)
    → DeoptRuntime::FindEntry(nm, return_address)
    → DeoptRuntime::ReconstructRegisterFile(gpr, fpr, ctx, entry, values, rsp)
    → t_deopt_state 填充
  → ret_buf[0] = kDeoptMagic
  → entry_direct 检测 kDeoptMagic
  → t_deopt_state → RegisterFrame 重建
  → RegisterExecute(rf, method, frame)
```

### Stage 3: SEH（结构化异常处理）

T4 SEH 使用 Windows VEH（Vectored Exception Handler）实现异常分发：

1. **注册**：`runtime_init.cpp` 调用 `RegisterT4SehHandler()` 注册 VEH handler
2. **抛出**：`CodegenThrow(exception_obj)` 将异常对象存入 TLS，调用 `RaiseException(0xE0000001)`
3. **捕获**：VEH handler 被触发，通过 `FindT4CodeByAddress` 定位 `NativeMethod`
4. **分派**：`FindSehHandlerForOffset` 遍历 SEH clause table，找到匹配的 handler
5. **重定向**：异常对象写入 RCX，RIP 被重定向到 handler 代码

SEH clause table 布局（追加在代码缓冲区末尾）：
```
uint32_t count
for each clause:
  uint32_t flags           (SEHFlags: 0=catch, 1=filter, 2=finally, 4=fault)
  uint32_t try_start_offset
  uint32_t try_end_offset
  uint32_t handler_start_offset
  uint32_t class_token     (catch 的异常类型 token)
```

### Stage 4: 寄存器分配（Light）

T4 实现了轻量级寄存器缓存，将热 vreg 缓存到 x64 callee-saved 寄存器 R12-R15：

**SelectCacheableRegs**：扫描所有指令，统计每个 vreg 的 src/dst 访问频率，选择 top 4 作为缓存候选。

**Write-through 策略**：
- `LoadGpr`：检查 vreg 是否缓存 → 命中则 `mov reg, cached_reg`（从缓存读），未命中则从栈加载
- `StoreGpr`：总是写入栈帧 + 可选更新缓存寄存器（write-through）

**Prologue 推挽**：缓存的 R12-R15 在 prologue 中 push，epilogue 中 pop。

`kCacheableX64Regs = {12, 13, 14, 15}`（R12-R15，Win64 callee-saved）。

### Stage 5: GC 分配（NewObj/Box）

NewObj 和 Box 通过 `GcAllocate`（而非 `CHAOS_IL2CPP_MALLOC`）分配堆内存：

- **CodegenNewObj**：`GcAllocate(sizeof(InterpreterObject))`，通过 placement new 构造，resize fields 向量
- **CodegenBox**：`GcAllocate(sizeof(BoxedValue))`，通过 placement new 构造

代码生成器为分配调用记录 GC point（`RecordGcPoint`），使 GC 在分配时能保守扫描栈帧。

## 限制与未来工作

1. **无限寄存器分配**：当前使用栈式寄存器文件（load→compute→store），图着色分配器已实现（ir_optimizer）但未集成到 T4
2. **TLAB 内联分配**：NewObj/Box 通过 C 辅助函数调用，未内联 TLAB bump 快速路径
3. **精确 GC slot maps**：GC point 使用保守栈扫描，无精确 slot 信息
4. **调试信息**：T4 代码不发射调试信息（行号映射、变量位置）
5. **多模块 hotpatch**：跨模块方法修补依赖共享 HotpatchNameRegistry

## 附录：AOT/JIT/Hybrid 三模式编译体系

> 2026-05 新增。在既有 JIT codegen 基础上，新增 JIT 和 Hybrid 两种编译模式，实现 CoreCLR 风格的三模式编译体系。

### 三种 CodegenMode

| 模式 | CLI 选项 | 行为 | 适用场景 |
|------|----------|------|----------|
| **Aot** | `--mode aot`（默认） | 所有方法编译为 C++ AOT 代码，零运行时开销 | 生产发布 |
| **Jit** | `--mode jit` | 所有方法启动时注册 JitPrecode，首次调用触发 Tier 0 Quick JIT 编译（~7µs），热点方法自动升级到 StackInterpreted 优化编译（带图着色寄存器分配） | 开发迭代、启动敏感场景 |
| **Hybrid** | `--mode hybrid` | AOT C++ 函数体 + JIT IR 双输出。冷时执行 AOT 原生代码，热点计数触发后台 StackInterpreted JIT 编译，编译完成后 atomic swap direct_ptr | 对热更友好且兼顾启动性能 |

### 架构对比

| 维度 | 旧 T4（解释器触发） | 新 JIT（Precode Stub） |
|------|---------------------|------------------------|
| 触发方式 | `InterpreterEntryDirect` 内升温阈值触发 | `JitPrecode` trampoline 首调用触发 |
| 编译入口 | `GenerateNativeCode()` → `NativeCodeGenerator` | `jit::Compile()` → Tier 0 (Quick) / StackInterpreted (Opt) |
| 配置结构 | `CodeGenConfig` | `CompileConfig`（含 compile_tier、enable_pgo 等） |
| 输出结构 | `NativeMethod`（codegen 子系统） | `JitMethod`（jit 子系统） |
| 代码位置 | `src/native/codegen/` | `src/native/jit/` |
| 命名空间 | `chaos::il2cpp::codegen` | `chaos::il2cpp::jit` |
| 寄存器分配 | 栈式寄存器文件（load→compute→store） | Tier 0: 栈式；Tier 1: 图着色（ir_optimizer） |

### Precode Stub 分派机制

三模式共享统一分派入口 `HotpatchEntryV0::direct_ptr`：

- **AOT**: `direct_ptr` 直接指向 AOT 函数，调用零开销
- **JIT**: `direct_ptr` 指向 `JitPrecode` trampoline（15 bytes），首调用通过 `JitStubDispatchImpl` 触发编译，编译成功后 atomic store 替换为编译后代码地址
- **Hybrid**: `direct_ptr` 指向 `HybridPrecode` trampoline，带递减计数器。冷时返回 AOT entry；计数器归零时触发 JIT 编译，编译后替换 direct_ptr

### 分层执行模型（更新版）

| 层级 | 名称 | 执行方式 | 触发条件 |
|------|------|----------|----------|
| T1 | FastExecute | 栈机 IR 直接解释 | 首次执行（cold） |
| T2 | RegisterExecute | 寄存器 IR 解释 | call_count 达到阈值 |
| T3 | RegisterExecute 优化 | 寄存器 IR + inline 缓存 | 热点方法 |
| JIT | 原生代码生成 (AOT/JIT) | x64 机器码直接执行 | AOT：编译时直接生成；JIT：首调用触发生成 |

### JitPrecode 结构体

定义在 `src/native/jit/jit_precode.h`：

```cpp
struct JitPrecode {
    std::atomic<uint32_t> state{kPrecodeUncompiled};  // 0/1/2 state machine
    interpreter::RegisterMethod  ir;                   // owned copy of the IR
    CompileConfig                config;               // compilation config
    JitMethod*                   compiled   = nullptr; // result of Compile()
    HotpatchEntryV0*             entry      = nullptr; // back-pointer to patch entry
    void*                        trampoline = nullptr; // executable trampoline code

    // ── PGO fields ──
    std::atomic<uint32_t> pgo_call_count{0};
    bool                  tier1_enqueued{false};
};
```

### JitStubDispatchImpl 状态机

`JitStubDispatchImpl`（`src/native/jit/jit_precode.cpp`）管理 JIT 模式的三态 CAS 状态机：

```
入口
  │
  ├─ state == kPrecodeCompiled?
  │   ├─ YES → stale flag?
  │   │   ├─ YES → CAS: Compiled→Uncompiled, 重新编译
  │   │   └─ NO  → PGO: fetch_add pgo_call_count
  │   │              超阈值? → EnqueueJitRecompilation
  │   │            → return compiled->code        ← 快路径
  │   └─ NO  → 继续
  │
  ├─ CAS: kPrecodeUncompiled → kPrecodeCompiling
  │   ├─ 成功 (Winner) → CompileWithCatch(ir, config)
  │   │   ├─ 编译成功 → direct_ptr = jit->code    ← HotpatchEntryV0 原子更新
  │   │   │              state = kPrecodeCompiled
  │   │   │              return jit->code
  │   │   └─ 编译失败 → state = kPrecodeUncompiled (可重试)
  │   │                  return nullptr
  │   └─ 失败 (Loser) → 自旋等待 (pause + yield)
  │                       直到 state == kPrecodeCompiled
  │                       → return compiled->code
```

关键设计点：
- **不阻塞调用方**：Loser 线程自旋等待编译完成，适合 JIT 模式（首调用即编译）
- **Stale 检测**：当被内联的方法被 hotpatch 后，通过 `InlineReverseMap` 标记 stale，触发重新编译
- **PGO 不 patch direct_ptr**：`enable_pgo=true` 时保留 dispatch 路径用于计数，直到 Tier 1 编译完成后才 patch

### PrecodeArena RWX 页管理

`PrecodeArena` 管理预分配的 RWX 内存页，提供 trampoline 分配：

| 参数 | 值 |
|------|-----|
| 页大小 | 64 KB |
| 每 trampoline | 15 bytes（mov r10, imm64 + jmp rel32）|
| 共享入口 | 每页前 64B（Jit + Hybrid 各一个）|
| 分配策略 | 页内线性分配，空间不足时分配新页 |

每个 trampoline 的 15 字节布局：

```asm
mov r10, <precode_ptr>  ; 10 bytes: 加载 JitPrecode* 地址
jmp  <shared_entry>     ; 5 bytes:  跳转到共享分派入口
```

共享入口（Per-page, ~37 bytes）：
```asm
push rcx                ; 保存参数寄存器
push rdx
push r8
push r9
sub  rsp, 0x20
mov  rcx, r10           ; precode* → 第一个参数
mov  rax, <dispatch_fn> ; JitStubDispatchImpl 地址
call rax
add  rsp, 0x20
pop  r9                 ; 恢复参数寄存器
pop  r8
pop  rdx
pop  rcx
jmp  rax                ; tail-call 到编译后的入口点
```

### RegisterJitEntryMethods 启动注册流程

`RegisterJitEntryMethods`（`src/native/jit/jit_precode.cpp`）在启动时为每个 JIT 模式方法执行注册：

1. **反序列化** AotCoreIr JSON → `IRMethod`
2. **寄存器分配** `AllocateRegisters` → `RegisterMethod`
3. **堆分配** `JitPrecode`（含 RegisterMethod + CompileConfig）
4. **查找** `HotpatchEntryV0`（通过 GetHotpatchNameRegistry）
5. **分配 trampoline** 从 PrecodeArena RWX 页
6. **设置** `direct_ptr = trampoline` — 首次调用触发编译

### PGO（Profile-Guided Optimization）

Tier 0 Quick JIT 编译后，通过 `CompileConfig::enable_pgo` 控制是否启用 PGO：

1. `enable_pgo=false`（默认）：Tier 0 编译后直接 patch `direct_ptr`，不会触发 Tier 1
2. `enable_pgo=true`：Tier 0 编译后不 patch `direct_ptr`，每次调用递增 `pgo_call_count`，超过阈值（100 次）后通过 `TierManager` 后台线程触发 StackInterpreted 重编译，编译完成后 atomic swap `direct_ptr`

后台线程处理优先级：JIT 重编译 > RegisterMapped→OptimizedRegister 解释器优化

### 弃用说明

旧 `RegisterJitMethods()`（解释器-only JIT 路径）已被 `RegisterT4JitMethods()`（T4 JIT Precode Stub 路径）取代。旧函数保留以兼容已有生成的测试文件，新 codegen 运行统一使用新路径。

### ISehHandler 接口与平台 SEH

`ISehHandler`（`src/native/jit/ISehHandler.h`）定义了 7 个纯虚方法：

- `RegisterCode` / `UnregisterCode` — JIT 代码段注册/注销
- `FindCodeByAddress` — 地址→JitMethod 查找（含页级 TLS 缓存）
- `DemoteByToken` / `DemoteByCallSiteToken` — hotpatch 降级
- `ReclaimDemoted` — GC 安全点回收降级代码
- `Initialize` — 注册平台异常处理器

**WinSehHandler**（Windows VEH）：
- 通过 `AddVectoredExceptionHandler` 注册 VEH，捕获硬件异常和托管抛出
- 支持 catch/finally/fault 三种 SEH 子句两阶段分派
- 使用页面粒度的 TLS 缓存加速 `FindCodeByAddress`

**LinuxSehHandler**（POSIX signal）：
- 通过 `sigaction` 注册 `SIGSEGV`/`SIGFPE`/`SIGILL` 处理器
- 使用 `sigsetjmp`/`siglongjmp` 实现 SEH 语义移植
- 捕获 ucontext 中的寄存器状态用于异常分派

**转发层**（`jit_seh.h/cpp`）：平台无关的 API 层，所有公开函数（`RegisterT4Code`, `FindT4CodeByAddress`, `DemoteT4ByToken` 等）通过 `GetSehHandler()` 自动分派到平台实现。

### PGO 多槽位 Polymorphic Inline Cache

CallVirt 的 PIC 从单槽位升级到三槽位，支持 monomorphic（1 slot）、bimorphic（2 slot）和 trimorphic（3 slot）内联分派：

```cpp
struct PerInstrPicData {
    uint32_t expected_type_tokens[3] = {};  // 接收者类型 token（按热路径排序）
    void*    direct_fns[3] = {};            // 预解析的 AOT 函数指针
    uint32_t slot_count = 0;                // 0=无数据, 1-3=活跃槽位
};
```

CodegenCallVirt 生成的类型检查链：
```asm
; rcx = method_token (type)  加载一次，复用所有槽位检查
slot 0: mov rax, expected_type_0
        cmp rax, rcx
        jne slot_1
        ; direct call via direct_fns[0]
        jmp .done

slot 1: mov rax, expected_type_1
        cmp rax, rcx
        jne slot_2
        ; direct call via direct_fns[1]
        jmp .done

slot 2: mov rax, expected_type_2
        cmp rax, rcx
        jne .full_resolve
        ; direct call via direct_fns[2]
        jmp .done

.full_resolve:
        call CodegenCallVirt  ; 完整 vtable 解析
.done:
```

PIC 数据由 `entry_direct.cpp` 在触发编译前从 PatchMethod 的 PIC 链构建，最多填充 3 个热槽位。
