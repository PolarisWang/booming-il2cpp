# 故障诊断指南（按模式分类）

> AOT / JIT / Hybrid 各模式的常见故障分类、诊断方法和解决方案。

---

## 通用排查框架

遇到运行时 crash 或异常行为时，按以下顺序排查：

```
1. 确认当前模式（AOT/JIT/Hybrid）
   └─ 检查构建命令的 --mode 参数
   └─ 检查运行时是否调用了 RegisterJitEntryMethods / RegisterHybridMethods

2. 确认故障类型
   └─ 段错误 / 访问违例 → 参照下表分类
   └─ 断言失败 / CHAOS_IL2CPP_FAIL → 查看 LOG_ERROR 消息
   └─ 结果不正确 → 跨模式语义差异 / 优化错误

3. 使用 trace 系统定位
   └─ run trace → 查看最新会话的 span 树
   └─ trace-analyze → 分析阶段耗时分布
   └─ 详见 wiki/04-工具与集成/统一追踪体系.md
```

## AOT 模式故障

### 未解析符号 / 段错误

**症状**：启动时 crash 在 AOT 函数入口、vtable 或 method table 访问。

**常见原因**：

| 原因 | 诊断方法 | 解决方案 |
|------|----------|----------|
| entry point 未找到 | trace 显示 `Stage_Preflight` 失败 | 确认 `--entry-point` 指定的类型名/方法名正确 |
| VTable 未注册 | crash 在 `ResolveVirtualMethodPointer` | 确认所有类型在 `runtime-entry.cpp` 的 `RegisterModules` 中注册 |
| Method table 索引越界 | crash 在跨程序集调用 | 确认 `MethodTableAllocator` 分配的索引在 0-65535 范围内 |
| 跨程序集类型 extern 声明不匹配 | link error / 运行时类型转换失败 | 确认 `extern const TypeInfo` 声明和实际程序集的 TypeInfo 对齐 |

### 跨程序集调用决议失败

**症状**：`TryGetMethodTableIndex` 返回 false 导致调用走 Interpreter 回退。

**诊断**：在 codegen 输出中搜索 `TryGetMethodTableIndex` 调用。

**解决方案**：
- 检查 callee SubjectId 格式是否正确（`"AssemblyName/Type::Method"`）
- 检查 callee 程序集是否在 `--assembly` 参数列表中
- 检查跨程序集调用涉及的方法是否有 method table 条目

### Dispatch slot 冲突

**症状**：hotpatch 后方法替换未生效，或替换了错误的方法。

**诊断**：检查 `BuildHotpatchTable` 输出的 name-index.h 中 slot 映射。

**原因**：无 ECMA token 的合成方法（Array 方法、委托方法）缺少 dispatch slot。

**解决方案**：
- AOT Phase 4（p4-hotpatch）已覆盖所有 IL 方法生成 dispatch slot
- 确认 codegen 版本包含 Phase 4 补丁
- 手动检查 `BuildDispatchSlotMap` 是否遍历了全 `_assembly.Methods`

## JIT 模式故障

### JitPrecode state 卡死

**症状**：调用 JIT 方法时线程挂起（自旋等待超过预期）。

**诊断**：
- 使用调试器检查 `JitPrecode::state` 值
- `kPrecodeCompiling(1)` 表示还有线程在编译
- 长时间处于 `kPrecodeCompiling` 说明编译线程可能 crash

**常见原因**：

| 原因 | 诊断 | 解决方案 |
|------|------|----------|
| Compile() 内 crash | 检查编译线程是否有 SEH catch（`CompileWithCatch`） | 修复 Compile() 中的未处理异常 |
| CAS 竞争导致永远自旋 | state 卡在 `kPrecodeCompiling` 但无编译线程 | 增加自旋超时回退（当前 1000 pause + yield） |
| Compile 返回 nullptr 未回退 state | `CompileWithCatch` 捕获到异常但未重置 state | 确认 `CompileWithCatch` 失败后重置 `state = kPrecodeUncompiled` |

### 编译失败

**症状**：`JitStubDispatchImpl` 返回 nullptr，方法无法执行。

**诊断**：查看 LOG_ERROR 消息 `"JitStubDispatchImpl: Compile() failed for method"`。

**常见原因**：

| 原因 | 诊断 | 解决方案 |
|------|------|----------|
| CompileConfig 设置错误 | `enable_safepoint_polls`/`enable_register_caching` 等标志冲突 | 检查 `RegisterJitEntryMethods` 中 `CompileConfig{}` 默认值 |
| 不支持的 opcode | `EmitInstruction` 遇到未实现的 opcode 分派 | 检查 T4 V3 opcode 支持表，确认已覆盖全部 103 个 opcode |
| RegisterMethod IR 无效 | `DeserializeAotCoreIrMethod` 反序列化失败 | 检查 `.jit-entries` 段的 AotCoreIr JSON 格式 |
| 栈帧溢出 | 单方法栈帧超过 864 字节限制 | 增大 `kFrameSize` 或优化栈分配 |

### GC Liveness 栈扫描遗漏

**症状**：GC 回收了仍在栈上的对象引用，导致随机 crash 或数据错乱。

**诊断**：在 GC stress 模式下运行（`CHAOS_IL2CPP_GC_STRESS=1`），观察是否出现悬挂引用。

**原因**：
- Liveness 分析裁剪了活跃的栈值
- GC slot map 中漏报了 GPR 栈槽

**解决方案**：
- 确认 `jit_engine.cpp` 中 GC slot map 发射阶段包含所有调用者保存寄存器
- 确认 `JitMethod::gc_slot_map` 非空（GcSlotMapV0 含 GPR 条目）
- 临时关闭 Liveness（`enable_liveness = false`）验证是否由 Liveness 引起

### OSR / Deopt 回退失败

**症状**：`kDeoptMagic(0xDE0D7FA57A11ULL)` 未正确检测，T4 代码回退到解释器失败。

**诊断**：检查 `ret_buf[0]` 在 native_entry 返回后的值。

**常见原因**：

| 原因 | 诊断 | 解决方案 |
|------|------|----------|
| DeoptTlsState 空指针 | crash 在 `DeoptRuntime::ReconstructRegisterFile` | 确认 `t_deopt_state` TLS 已初始化 |
| 栈帧未对齐 | crash 在 OSR entry 的 `push rbp` | 确认 `OsrResolveLoopHeader` 中栈帧 16 字节对齐 |
| OSR entry 基本块跳转偏移错误 | crash 在 `jit_engine.cpp` 的指令偏移计算 | 检查 `instr_offsets_` 是否正确跟踪 OSR entry 点 |
| 值描述不匹配 | 重建的寄存器值与实际栈布局不一致 | 检查 `DeoptEntry::values` 和 `DeoptValue` 描述与 `RegisterMethod` 一致 |

### SEH 捕获失败

**症状**：异常未被 JIT SEH handler 捕获，传播到系统层面（崩溃）。

**诊断**：
- 检查 `RegisterT4SehHandler()` 是否在 `runtime_init.cpp` 中调用
- 检查 `WinSehHandler::FindCodeByAddress` 是否能定位到 `NativeMethod`
- 检查 SEH clause table 的 `try_start_offset`/`try_end_offset`/`handler_start_offset` 范围

**常见原因**：

| 原因 | 诊断 | 解决方案 |
|------|------|----------|
| VEH 未注册 | 启动时 `AddVectoredExceptionHandler` 未被调用 | 确认 `RegisterT4SehHandler()` 在 `runtime_init` 中调用 |
| Clause table 偏移不匹配 | 代码缓冲区布局变化后 clause table 偏移未同步 | 确认 `SehHandlerForOffset` 使用正确的 SEH table 基址 |
| FindCodeByAddress 页缓存 miss | 使用 `FindT4CodeByAddress` 但未找到对应方法 | 确认 `WinSehHandler::RegisterCode` 在 Compile() 后调用 |
| 跨模式异常传播 | AOT 代码抛出异常，JIT 代码期望捕获 | 确认 `DetermineSehHandlerType` 能否正确处理 AOT→JIT 异常传播 |

## Hybrid 模式故障

### HybridPrecode counter 不减

**症状**：方法始终不触发 JIT 编译（超过 30 次调用仍走 AOT）。

**诊断**：检查 `HybridPrecode::call_counter` 值是否递减。

**原因及解决方案**：

| 原因 | 诊断 | 解决方案 |
|------|------|----------|
| Trampoline 路由错误 | `direct_ptr` 未被替换为 Hybrid trampoline | 检查 `RegisterHybridMethods` 中 `direct_ptr = trampoline` 是否执行 |
| call_counter 初始化错误 | counter 初始值为 0（直接触发编译）或未初始化 | 确认 `call_counter.store(kJitUpgradeThreshold)` 在 `RegisterHybridMethods` 中调用 |
| direct_ptr 被其他路径覆盖 | Hotpatch 或 slot map 更新覆盖了 trampoline 地址 | 确认 slot update callback 不覆盖 Hybrid trampoline |

### 编译后 direct_ptr 未更新

**症状**：`Compile()` 成功返回，但后续调用仍走 AOT（未切到 JIT 代码）。

**诊断**：
- 检查 `HybridPrecode::state` 是否为 `kPrecodeCompiled`
- 检查 `HotpatchEntryV0::direct_ptr` 是否指向 `compiled->code`

**原因**：
- CAS 竞争：另一个线程的 `compare_exchange_strong` 丢失，未更新 direct_ptr
- PGO 模式下 enable_pgo=true 会跳 direct_ptr 更新（预期行为）
- `HybridStubDispatchImpl` 在 CompileWithCatch 失败后重置 state，但未重置 counter

**解决方案**：
- 确认 `precode->entry->direct_ptr = jit->code` 在 CAS 成功后执行
- 确认 `enable_pgo` 标志符合预期

### AOT entry 丢失

**症状**：`HybridStubDispatchImpl` 返回 nullptr，方法无法执行。

**诊断**：检查 `HybridPrecode::aot_entry` 是否为 null。

**原因**：
- `RegisterHybridMethods` 中 `precode->entry` 为 null，无法获取 `direct_ptr` 作为 aot_entry
- Hotpatch 替换覆盖了原有 AOT entry，未保留备份

**解决方案**：
- 确认 `GetHotpatchNameRegistry().GetDispatchEntry()` 能返回有效的 `HotpatchEntryV0`
- 在 Hybrid 模式下，`aot_entry` 应在 `RegisterHybridMethods` 时从 `entry->direct_ptr` 读取并独立保存

### AOT→JIT 结果不一致

**症状**：同一方法在 AOT 执行和 JIT 编译后执行的结果不同。

**诊断**：Foundation-DLL Hybrid stage 14 验证失败。

**常见原因**：

| 原因 | 诊断 | 解决方案 |
|------|------|----------|
| JIT 编译使用了错误的 IR | JIT 编译的 IR 与 AOT 版本的模板不匹配 | 确认 `RegisterHybridMethods` 从 `.jit-entries` 段反序列化 IR |
| 寄存器分配差异 | 图着色分配器和 AOT 的寄存器策略不一致 | 确认两个路径的 `CompileConfig` 一致 |
| 优化导致语义变化 | JIT 的窥孔优化改变了程序语义 | 逐个阶段关闭优化定位问题 |
| PGO 重编译错误 | Tier 0 和 Tier 1 的编译结果不一致 | 确认背景 `JitRecompileToTier1` 使用正确配置 |

## 定位工具

### Trace 系统

```bash
# 查看最新会话的 span 树
run trace

# 分析阶段耗时分布
trace-analyze

# 按模式过滤
# AOT：关注 codegen / emission 阶段
# JIT：关注 jit-engine / compile 阶段
# Hybrid：关注 hybrid-dispatch / counter 阶段
```

### Profile Scope 分析

在 `cmake --preset debug` 或 `cmake --preset profile` 构建下，以下热点已预埋 `PROFILE_SCOPE`：

- `JitStubDispatchImpl` / `HybridStubDispatchImpl` — dispatch 耗时
- `Compile()` / `CompileWithCatch()` — 编译耗时
- `InterpreterEntryDirect` — 所有 6 步回退链耗时
- GC 相关点（`GcAllocate`、`ResolveVirtualMethodPointer` 等）

### RDTSC 时钟级分析

`profile.h` 使用 RDTSC 实现零 I/O 热点统计。启动时自动校准 RDTSC→ns。查看 stdout 中的平均耗时表：

```
Profile scope         Calls    Total(ns)      Avg(ns)
JitStubDispatchImpl    157      2,384,000      15,184
Compile                157      2,084,000      13,273
HybridStubDispatchImpl  29         58,000       2,000
```

### Hotpatch / Patchdata 状态检查

```bash
# 检查 patchdata 二进制格式
patch-data inspect my.patchdata

# 检查 dispatch slot 映射
# 在 codegen 输出中搜索 name-index.h
```
