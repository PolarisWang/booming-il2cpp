# 异常处理架构

## 5 种 EH Shape

| Shape | 描述 | C++ 模式 |
|-------|------|---------|
| CatchOnly | 只有 catch 子句 | `try { ... } catch (T&) { ... }` |
| FilterOnly | 只有 filter 子句 | `try { ... } catch (...) { if (filter) { ... } }` |
| FinallyOnly | 只有 finally 子句 | `try { ... } finally { ... }`（CPP_THROW） / `setjmp + finally + re-raise`（SETJMP） |
| CatchAndFinally | catch + finally 混合 | `try { ... } catch (T&) { ... } finally { ... }` |
| FilterAndFinally | filter + finally 混合 | `try { ... } catch (...) { filter; cleanup; }` |

## 双路径异常处理架构（Dual-Path EH）

从 v1.2 起，异常处理采用编译时双路径方案，根据目标平台自动选择：

| 模式 | 宏 | 默认平台 | 机制 | 性能 |
|------|-----|---------|------|------|
| **CPP_THROW** | `CHAOS_IL2CPP_EH_CPP_THROW` | Windows, macOS, Linux, 服务器 | C++ `throw` + RAII 栈展开 | ~1.7-5µs/throw, 需 EH 表 |
| **SETJMP** | `CHAOS_IL2CPP_EH_SETJMP` | iOS, Android, 移动端/游戏主机 | `setjmp`/`longjmp` + 手动 finally 分发 | ~0.3µs/throw, 零 EH 表 |

### 平台声明与功能映射

从 v1.2 起，平台信息与功能映射分离控制，分两层：

**第 1 层 — CMakeLists.txt 声明平台**：顶层 `CMakeLists.txt` 根据 `ROADMAP0_PRESET_TARGET` 分支，通过 `add_compile_definitions` 注入 `CHAOS_IL2CPP_TARGET_PLATFORM_*` 宏：

```cmake
if(ROADMAP0_PRESET_TARGET STREQUAL "windows-x64-reference")
    add_compile_definitions(CHAOS_IL2CPP_TARGET_PLATFORM_WINDOWS=1)
    ...
elseif(ROADMAP0_PRESET_TARGET STREQUAL "android-arm64-smoke")
    add_compile_definitions(CHAOS_IL2CPP_TARGET_PLATFORM_ANDROID=1)
    ...
elseif(ROADMAP0_PRESET_TARGET STREQUAL "ios-arm64-packaging")
    add_compile_definitions(CHAOS_IL2CPP_TARGET_PLATFORM_IOS=1)
    ...
elseif(ROADMAP0_PRESET_TARGET STREQUAL "macos-reference")
    add_compile_definitions(CHAOS_IL2CPP_TARGET_PLATFORM_MACOS=1)
    ...
elseif(ROADMAP0_PRESET_TARGET STREQUAL "linux-x64-packaging")
    add_compile_definitions(CHAOS_IL2CPP_TARGET_PLATFORM_LINUX=1)
    ...
endif()
```

**第 2 层 — config.h 平台→功能映射**：`<chaos/config.h>` 读取平台宏，定义 EH 模式。同时保留编译器内置宏 fallback，兼容非 preset 直接构建：

```cpp
// 平台检测：优先 CMake 传递的宏，fallback 到编译器内置宏
#if !defined(CHAOS_IL2CPP_TARGET_PLATFORM_WINDOWS) \
    && !defined(CHAOS_IL2CPP_TARGET_PLATFORM_ANDROID) \
    && !defined(CHAOS_IL2CPP_TARGET_PLATFORM_IOS) \
    && !defined(CHAOS_IL2CPP_TARGET_PLATFORM_MACOS) \
    && !defined(CHAOS_IL2CPP_TARGET_PLATFORM_LINUX)
    // 编译器内置宏 fallback ...
#endif

// 平台 → EH 模式：移动端 SETJMP，桌面端 CPP_THROW
#if defined(CHAOS_IL2CPP_TARGET_PLATFORM_IOS) \
    || defined(CHAOS_IL2CPP_TARGET_PLATFORM_ANDROID)
    #define CHAOS_IL2CPP_EH_SETJMP
#else
    #define CHAOS_IL2CPP_EH_CPP_THROW
#endif
```

### 统一 API

所有 runtime 代码和 codegen 输出统一调用 `chaos_raise_exception(obj)`，该函数在两种模式下都有定义：

```cpp
// SETJMP 模式（exception_jmp.h）
[[noreturn]] inline void chaos_raise_exception(CHAOS_IL2CPP_INTPTR obj) noexcept {
    g_chaos_exception_obj = reinterpret_cast<void*>(obj);
    if (g_chaos_exception_jmp_depth > 0) {
        longjmp(g_chaos_exception_jmp_stack[g_chaos_exception_jmp_depth - 1], 1);
    }
    std::abort();
}

// CPP_THROW 模式（exception_jmp.h）
[[noreturn]] inline void chaos_raise_exception(CHAOS_IL2CPP_INTPTR obj) {
    throw chaos_managed_exception{obj};
}
```

## SETJMP 模式设计

### TLS 数据结构（`exception_jmp.h`）

```cpp
static constexpr int kMaxNestedTry = 16;
extern thread_local jmp_buf g_chaos_exception_jmp_stack[kMaxNestedTry];
extern thread_local int g_chaos_exception_jmp_depth;
extern thread_local void* volatile g_chaos_exception_obj;

inline jmp_buf* push_exception_jmp_buf() noexcept {
    if (g_chaos_exception_jmp_depth >= kMaxNestedTry) std::abort();
    return &g_chaos_exception_jmp_stack[g_chaos_exception_jmp_depth++];
}
inline void pop_exception_jmp_buf() noexcept {
    if (g_chaos_exception_jmp_depth > 0) g_chaos_exception_jmp_depth--;
}
```

### Codegen 生成的 SETJMP 模式

#### TryCatch
```cpp
{
    auto* _chaos_jmp = chaos::il2cpp::runtime_core::push_exception_jmp_buf();
    if (setjmp(*_chaos_jmp) == 0) {
        // try 体
    } else {
        // catch handler — 读取 g_chaos_exception_obj
        // 类型兼容性检查
        // 不匹配 → pop_exception_jmp_buf + re-raise
    }
    chaos::il2cpp::runtime_core::pop_exception_jmp_buf();
}
```

#### TryFinally
```cpp
{
    auto* _chaos_jmp = push_exception_jmp_buf();
    bool _chaos_caught = false;
    if (setjmp(*_chaos_jmp) == 0) {
        // try 体
    } else {
        _chaos_caught = true;
        // finally 体
    }
    pop_exception_jmp_buf();
    if (_chaos_caught) {
        chaos_raise_exception(g_chaos_exception_obj);
    }
}
```

#### TryFilter
```cpp
{
    auto* _chaos_jmp = push_exception_jmp_buf();
    if (setjmp(*_chaos_jmp) == 0) {
        // try 体
    } else {
        // 读取异常对象 → 执行 filter
        // filter 不通过 → pop + re-raise
        // filter 通过 → handler 体
    }
    pop_exception_jmp_buf();
}
```

### CPU 架构要求

#### ARM64 (iOS/Android)
- ARM64 的 `setjmp`/`longjmp` 保存/恢复所有 callee-saved 寄存器 (x19-x30) 和 SP
- 符合 ARM 向量表 ABI (AAPCS64)
- 无需 `.ARM.extab` / `.ARM.exidx` 节（省 15-25% 二进制大小）
- 内存在 setjmp 时为 8×64 位寄存器 + 1 个 64 位帧指针 ≈ 80 字节/jmp_buf

#### x64 (当意外退回到 SETJMP 时)
- x64 的 setjmp/longjmp 保存/恢复 callee-saved 整数寄存器 (RBX, RBP, R12-R15) + RSP + RIP
- 无需 LSDA 表

### RAII finally 守卫

CPP_THROW 模式通过 `chaos::il2cpp::common::make_finally_guard` 实现 finally 语义：

```cpp
// <chaos/finally.h>
template <typename TAction>
class FinallyGuard {
    TAction action_;
    bool active_ = true;
public:
    explicit FinallyGuard(TAction action) : action_(std::move(action)) {}
    ~FinallyGuard() { if (active_) action_(); }
    void dismiss() { active_ = false; }
};

template <typename TAction>
FinallyGuard<TAction> make_finally_guard(TAction action);
```

## 异常处理的关键约束

- Filter 子句通过 `catch (...) { if (filter_expr) { ... } else { throw; } }` 模拟（CPP_THROW）/ `setjmp else { filter; if (!match) chaos_raise_exception(...); }`（SETJMP）
- Finally 在 CPP_THROW 模式下通过 RAII 守卫实现，SETJMP 模式下通过 setjmp/longjmp + manual re-raise 实现
- 不允许在 filter 中执行托管内存分配
- 异常对象通过 `chaos_raise_exception` 统一 API 抛出

## Runtime Support

异常处理需要的 runtime helper：
- `chaos_raise_exception` — 抛托管异常（统一 API，两种模式）
- `ChaosReflectionSetExceptionMetadata` — 设置异常元数据（message, param_name）
- `ChaosReflectionGetExceptionMessage` / `chaos_reflection_get_exception_param_name` — 异常元数据查询
- `chaos_is_type_compatible` — 类型兼容性检查（codegen 内联函数）
- `push_exception_jmp_buf` / `pop_exception_jmp_buf` — SETJMP 模式的 jmp_buf 栈管理

## FastDispatch 异常保护

解释器的 FastDispatch 路径通过 `CanFastExecute()` 检查 `ir.seh_clauses.empty()` 来拦截包含异常处理的方法：

```cpp
// fast_dispatch.h
static bool CanFastExecute(const AotCoreIrMethodArtifact& ir) {
    return ir.seh_clauses.empty();  // 有 SEH 的方法走完整解释路径
}
```

所有 EH 相关 opcode（Handle_Throw, Handle_Rethrow, Handle_EndFinally, Handle_EndFilter）在 FastDispatch 中被映射到 `Handle_Unsupported`，触发 fallback 到完整解释器。

## 解释器 SEH 实现

解释器中的 SEH 实现在 `InterpreterVM::Execute()` 内部，使用纯状态机模型（不依赖 C++ EH）。

### SEH Clause 结构

```cpp
struct SEHClause {
    SEHFlags              flags;            // Exception/Filter/Finally/Fault
    CHAOS_IL2CPP_SIZE     try_start_idx;    // try 块起始指令索引
    CHAOS_IL2CPP_SIZE     try_end_idx;      // try 块结束指令索引（独占）
    CHAOS_IL2CPP_SIZE     handler_start_idx; // handler 起始指令索引
    CHAOS_IL2CPP_SIZE     handler_end_idx;  // handler 结束指令索引（独占）
    CHAOS_IL2CPP_UINT32   class_token;      // typed catch 的类型 token
};
```

### 两阶段异常处理模型

#### Phase 1 — 搜索（Throw / Rethrow）

```
① 从栈顶弹出异常对象
② 反向扫描 SEH clause 列表（从后往前 = innermost first）
③ 找到第一个匹配的 catch handler
   ✓ 找到 → 进入 Phase 2（展开）
   ✗ 未找到 → result.threw_exception = true，返回给调用者
```

#### Phase 2 — 展开（Unwind）

```
① 收集所有位于 throw 点和 catch handler 之间的 finally/fault clause
   筛选条件：try 范围覆盖 throw 点，且嵌套在 catch clause 的 try 范围内
② 按 innermost-first 顺序依次执行 finally/fault handler
③ 每个 handler 执行完后，EndFinally 推进到下一个 finally/fault
④ 所有 finally/fault 执行完毕 → 跳转到 catch handler handler_start_idx
⑤ 将异常对象压回栈顶供 catch 子句使用
```

#### 执行状态变量

```
exception_in_flight     — 展开阶段是否在进行中
exception_obj            — 当前传播的异常对象
unwind_catch_clause      — 目标 catch clause 索引
unwind_finally_list[]    — 展开途中的 finally/fault clause 索引数组
unwind_finally_count     — finally 列表长度
unwind_finally_current   — 当前执行到的 finally 索引
pending_leave            — Leave 指令是否挂起
pending_leave_target     — Leave 的跳转目标
```

### Leave / EndFinally 交互

```
Leave(try_block):
  ① 检查是否有 enclosing finally handler
  ② 有 → 保存 pending_leave_target，跳转到 finally handler
  ③ 无 → 直接跳转到 branch_target

EndFinally:
  ① exception_in_flight → 推进展开队列
  ② pending_leave → 跳转到 pending_leave_target
  ③ 正常 → 继续下一条指令
```
