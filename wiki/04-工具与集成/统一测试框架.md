# 统一测试框架

一句话摘要：仓库内测试域统一收口到 `run test ...`，并共享固定的 suite/manifest、日志目录、事件流、摘要文件、红绿灯覆盖和性能基线规则。

## 关键结论

- 测试域公开入口统一为 `run test <family> <suite> [options]`，并支持 `run test <family> all` 与 `run test all`。
- 测试相关旧入口不再长期保留；测试型 `run build ...` / `run verify ...` 已降为隐藏兼容层，对外只保留 `run test ...`。
- 公开测试家族固定为 `unit / integration / contract / smoke / gate / workflow / perf`。
- 测试日志根目录固定为 `artifacts/logs/tests/`，测试构建缓存固定为 `artifacts/tests/build/`。
- 运行结果固定输出 `session.json`、`summary.json`、`console.log`、`events.jsonl`、`telemetry.json` 与各 suite 的 `report.json`、`stdout.log`、`stderr.log`。
- 事件流固定为 `session-start`、`stage-start`、`stage-finish`、`progress`、`case-result`、`warning`、`artifact`、`final-summary`。
- 红绿灯覆盖默认强制于 `unit / integration / contract / smoke / gate`；`workflow / perf` 默认非强制。
- `perf` 默认采集数据，只有配置阈值或基线时才参与失败判定；基线存放在 `tests/perf/<suite>/baselines/<host>.json`。
- macOS 上如果 suite 运行链实际需要 `dotnet` 且本机缺失，交互式会提示通过 Homebrew 安装；非交互式直接失败并返回手动安装指引。

## 分类导航

- 命令模型：`run test ...` 是测试域唯一公开入口，`--stage` 统一控制 `build|run|report|all`。
- 目录模型：测试目录统一为 `tests/unit`、`tests/integration`、`tests/contract`、`tests/smoke`、`tests/gate`、`tests/workflow`、`tests/perf`。
- 结果模型：固定状态、固定计数、固定事件、固定文件布局，便于 TUI、harness、CI 共享消费。
- 覆盖与性能：红绿灯覆盖使用结构化 selector；性能规则支持静态阈值与仓库内基线文件。

## 公开命令

```text
run test <family> <suite> [options]
run test <family> all [options]
run test all [options]
run test list [family] [--host <host>] [--json]
run test list --invalid [--host <host>] [--json]
```

常用选项：

- `--stage all|build|run|report`
- `--host <host>`
- `--strict`
- `--include-tag <tag>`
- `--exclude-tag <tag>`
- `--json`
- `--update-baseline`

补充规则：

- `run test all` 默认只包含 `unit / integration / contract / smoke / gate`。
- `workflow / perf` 必须显式指定 family 或 suite。
- 显式点名 host 不兼容 suite 时直接报错；批量 `all` 时自动过滤不兼容 suite。

## 目录与 Suite 组织

每个 suite 采用本地 manifest：

```text
tests/<family>/<suite-id>/suite.manifest.json
```

目录迁移规则：

- `tests/contracts -> tests/contract`
- `tests/platform -> tests/gate`
- `tests/reference-desktop -> tests/workflow`
- `tests/tooling/run/* -> tests/integration/run/*`

当前过渡规则：

- `tests/integration/run/` 已作为统一入口 tooling 测试的 catalog 归属目录，并带有独立 `suite.manifest.json`。
- `tests/contract/` 与 `tests/gate/` 已作为新的命令路径与 CMake 路径根。
- 旧 `tests/tooling/run/`、`tests/contracts/`、`tests/platform/` 仍保留为过渡兼容副本，最终清理由计划最后阶段统一完成。

case 不写入 manifest，由 adapter 运行时发现。没有天然 case 的 suite 由 adapter 生成稳定 synthetic case，例如 `main`。

当前 adapter / case discovery 规则：

- `build/toolchains/run/testing/adapters/` 固定包含 `python-pytest`、`dotnet-app`、`native-cmake`、`shell-script`、`workflow` 五类 adapter。
- discovery 统一返回 `DiscoveredCase(caseId, sourceId, sourceName)`。
- `caseId` 会先归一化为 ASCII kebab-case，再在冲突时追加稳定的 4 位短后缀。
- `dotnet-app`、`native-cmake`、`workflow` 在没有天然 case 时默认生成 synthetic `main`。

当前 coverage policy 规则：

- suite manifest 可选 `coveragePolicy`，第一版只支持 `caseIds`、`sourceIds`、`tags`、`include`、`exclude` 五类 selector。
- 每个 discovered case 必须恰好落入 `green / red / yellow` 之一；selector 重叠会被视为明确配置错误。
- 未显式命中的 case 当前默认进入 `green`，从而保持每个 case 都有稳定 traffic-light bucket。
- `workflow / perf` family 默认 `coverageEnforced=false`；其他 family 默认启用覆盖约束，suite 可通过 manifest override。

当前 session / stage 规则：

- `run test ...` 现在先进入 `testing/session.py`，再桥接到旧 smoke / trace / verify 执行链。
- `--stage run` 对需要构建前置的 suite 会在 `stageResults.build` 中标记 `implicit=true`。
- 显式点名 host 不兼容 suite 时，命令失败并返回契约退出码 `2`。
- `test all --strict` 在 catalog 扫描发现 invalid suites 时会升级为契约失败并返回退出码 `2`。
- `commands/test.py` 只负责 public suite 解析、batch 聚合和 session 调度；隐藏旧命令仍作为底层兼容执行器存在。
- `build/toolchains/run/testing/events.py` 提供稳定事件封套，至少固定 `schemaVersion`、`eventType`、`timestampUtc` 和 `payload`。
- public `run test ...` 在成功写盘时会把 `runId`、`summaryPath`、`sessionPath`、`eventsPath` 等元数据回填到命令 payload，便于 TUI、CI 和外部工具跳转产物。
- `build/toolchains/run/run.py` 在 `--json` 模式下如果检测到 `eventsPath`，会优先输出 `events.jsonl` 原文；只有没有事件流可用时才回退到单个 `CommandResult` JSON。

## 运行与结果契约

每次运行写入：

```text
artifacts/logs/tests/<run-id>/
  session.json
  summary.json
  console.log
  events.jsonl
  telemetry.json
  suites/<suite-id>/report.json
  suites/<suite-id>/stdout.log
  suites/<suite-id>/stderr.log
```

当前落地规则：

- `summary.json` 继续保留 `suiteResults[]` 作为机器优先索引。
- `events.jsonl` 目前至少写出 `session-start` 和结尾的 `final-summary`。
- `final-summary.payload` 不内联 `suiteResults`，避免事件流尾包膨胀。
- `suites/<suite-id>/report.json` 会记录 suite 级结果和对应 `reportPath`。
- TUI 运行态可以消费 `progress` / `warning` / `artifact` / `final-summary` 事件，并从事件流渲染当前进度屏，而不是依赖旧的扁平测试输出。
- `report.json` 和 `summary.json` 现在都会携带 `trafficLightCounts`；suite report 还会保留 case 级 `trafficLight` 映射。
- session 级 `final-summary` 事件会同步带出聚合后的 `caseCounts` 与 `trafficLightCounts`。

结果语义固定为：

- `finalStatus = ok | fail | aborted`
- `suite status = ok | fail | skip | aborted`
- `case status = ok | fail | skip | aborted`
- `stage status = ok | fail | skipped | not-requested | aborted`

退出码固定为：

- `0`：成功
- `1`：已进入执行，但 suite / case / stage 失败
- `2`：请求、契约、manifest、catalog 或 strict 校验失败
- `3`：框架内部或基础设施异常

计数固定为：

- `suiteCounts = total / ok / fail / skip / aborted`
- `caseCounts = total / ok / fail / skip / aborted`
- `trafficLightCounts.<green|red|yellow> = total / ok / fail / skip / aborted`

时间字段固定为：

- `readyAtUtc`
- `startedAtUtc`
- `finishedAtUtc`
- `startupMs`
- `executionMs`
- `totalMs`

## 覆盖与性能

红绿灯覆盖规则：

- 使用 `caseIds`、`sourceIds`、`tags`、`include`、`exclude` 这些结构化 selector
- 每个 case 必须恰好映射到 `green / red / yellow` 之一
- 红绿灯只表示覆盖类型，不改变 `ok / fail / skip / aborted` 的执行语义

性能规则：

- `perf` 默认先采集数据
- 配置静态阈值或基线规则后，性能回退才失败
- 基线按 host 拆分
- 基线文件只能通过显式命令更新，不允许普通执行自动改写
- perf 基线文件固定放在 `tests/perf/<suite>/baselines/<host>.json`
- 普通执行会读取仓库内 baseline，但不会自动回写；只有显式 `--update-baseline` 才允许更新

构建缓存与指纹规则：

- 测试 build cache 固定写到 `artifacts/tests/build/<host>/<family>/<suite>/fingerprints/<fingerprint>/`
- 最近一次成功构建通过 `current.json` 记录当前 fingerprint 指针
- 第一版 fingerprint 采用受控输入的稳定 JSON 哈希，不使用 mtime

## 与统一入口的关系

统一测试框架是现有 `run.*` 入口在测试域上的正式契约，不另起入口。TUI、harness 和 CI 都应基于 `run test ...`、`run prepare ...`、`run clean ...` 运行。

补充规则：

- `run test ...` 相关构建链在 macOS 上会复用统一入口的 `dotnet` 按需引导逻辑。
- 交互式可以确认后执行 `brew install --cask dotnet-sdk`；非交互式不会自动安装。
- `run prepare ... --json` 在 CI / harness 中不会代替依赖安装，缺失 `dotnet` 时会直接报错。
- `run prepare smoke` 会通过 `run test smoke all --stage build` 预热统一 smoke suite，而不是逐个调用旧 `build smoke ...` 兼容命令。
- TUI 中公开测试能力是动态输入项：选择 `test <family> <suite>` 或 `test <family> all` 时，会补充提示目标 family / suite 后再生成实际命令。
- harness / CI 如果调用 `run test ... --json`，应直接消费 line-delimited `events.jsonl` 事件流，而不是假设返回单个 JSON 对象。
- 运行结束后如果需要回看汇总或跳转产物，应优先读取返回 payload 里的 `summaryPath` / `eventsPath`。
