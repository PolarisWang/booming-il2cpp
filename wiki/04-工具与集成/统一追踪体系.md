# 统一追踪体系

> 本文档说明项目的跨语言统一追踪（Trace）系统架构、使用方法和集成点。
> 该系统覆盖 Python/C#/C++ 三层，实现测试全链路的可追溯性。
> **trace 是日常开发中定位错误的首选手段** — 参见"错误排查工作流"章节。

---

## 架构概览

```
┌──────────────────────────────────────────────────────────┐
│                   Python 编排层                           │
│  trace_init() → 创建 trace.jsonl + 导出环境变量           │
│  trace() / @trace_call() → 写入 JSONL 记录               │
│  spanId/parentSpanId → 自动生成 span 层级                 │
│  set_run_id() → 与 events 系统双向关联                    │
├──────────────────────────────────────────────────────────┤
│                        环境变量桥                          │
│  CHAOS_TRACE_PATH → trace.jsonl 文件路径                  │
│  CHAOS_TRACE_ID   → 跨语言统一追踪 ID (UUID hex[:16])     │
├──────────────────────┬───────────────────────────────────┤
│    C# 层              │     C++ 层                         │
│  ChaosTrace.cs       │  trace.h (ring buffer, atexit)     │
│  Point() / TraceCall │  CHAOS_IL2CPP_LOG_TRACE() 宏        │
│  RuntimeTrace.cs     │  仅 Debug 构建启用                  │
├──────────────────────┴───────────────────────────────────┤
│                    CLI 工具                                 │
│  run trace        → span 树形展示                          │
│  trace-analyze    → 性能分析（阶段耗时、最慢操作）          │
└──────────────────────────────────────────────────────────┘
```

### 核心设计原则

- **通过环境变量传播** — `CHAOS_TRACE_PATH` 和 `CHAOS_TRACE_ID` 由 Python 编排层设置，子进程自动继承
- **统一 JSONL schema** — Python/C#/C++ 三层使用相同的记录格式，共享 `traceId`
- **Span 层级** — 每个操作自动分配 `spanId`，记录 `parentSpanId` 形成父子关系树
- **零性能开销** — 测试时生效，不影响生成代码的运行时性能；C++ 层仅在 Debug 构建开启
- **永不崩溃** — 所有 trace 写操作静默忽略 IO 错误
- **幂等初始化** — `trace_init()` 可多次调用，仅首次生效

## JSONL Schema

每条记录是一个 JSON 对象，写入 `artifacts/logs/trace/<session>/trace.jsonl`：

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `t` | string | 是 | ISO 8601 UTC 时间戳 |
| `l` | string | 是 | 语言标签：`python` / `cs` / `cpp` |
| `o` | string | 是 | 操作名称 |
| `traceId` | string | 是 | 跨语言统一追踪 ID |
| `s` | string | 否 | 阶段名称 |
| `f` | string | 否 | 源文件:行号 |
| `spanId` | string | 否 | Span ID（自动生成） |
| `parentSpanId` | string | 否 | 父 Span ID |
| `phase` | string | 否 | 阶段：`enter` / `exit` / `exception` |
| `dur_ms` | number | 否 | 持续时间（毫秒） |
| `runId` | string | 否 | 事件系统运行 ID（与 events.jsonl 关联） |

### 示例

```jsonl
{"t":"2026-05-05T10:30:00Z","l":"python","o":"session_start","traceId":"a1b2c3d4e5f6a7b8","session":"20260505-103000-12345","stage":"batch-native-aot"}
{"t":"2026-05-05T10:30:01Z","l":"python","o":"batch_start","traceId":"a1b2c3d4e5f6a7b8","spanId":"s1","phase":"enter","s":"batch-native-aot","f":"batch_runner.py:439"}
{"t":"2026-05-05T10:30:02Z","l":"python","o":"family_convert","traceId":"a1b2c3d4e5f6a7b8","spanId":"s2","parentSpanId":"s1","s":"convert","f":"batch_runner.py:165"}
{"t":"2026-05-05T10:30:05Z","l":"cs","o":"driver.convert.pipeline","traceId":"a1b2c3d4e5f6a7b8","s":"convert","f":"DriverEntry.cs:254"}
```

## Python 层使用

### 初始化（自动）

- `run.py` 主入口：所有 `run xxx` 命令自动调用 `trace_init()`
- 各 batch runner：`trace_init()` 幂等化，重复调用无副作用
- `CHAOS_TRACE_PATH` 和 `CHAOS_TRACE_ID` 自动导出到环境变量，子进程继承

```python
from testing.trace import trace_init, trace, trace_call, set_run_id, get_trace_id

trace_init(repo_root, stage="batch-native-aot")   # 幂等，仅首次生效
set_run_id("run-20260505-...")                      # 与 events 系统关联
```

### 单点追踪

```python
trace("family_convert", family="convert-char", method_count=18)
```

### 装饰器追踪（自动 span 层级）

```python
@trace_call("run_family")
def run_family(family_slug: str):
    ...
```

装饰器自动生成 `spanId` 和 `parentSpanId`，记录 `enter` → `exit`（含 `dur_ms`）→ `exception` 三阶段。

### 公共访问器

```python
trace_id = get_trace_id()       # 当前 traceId（其他模块集成用）
session_id = get_session_id()   # 当前 session ID
```

### 调用位置

| 调用方 | 追踪的操作 |
|--------|-----------|
| `run.py` — `main()` | `session_start` — 所有 `run xxx` 命令 |
| `run.py` — `execute_parsed_command()` | 注入 `runId` → events 与 trace 双向关联 |
| `batch_native_aot_runner.py` | `batch_start`、`family_*_failed`、`family_passed` |
| `batch_hotupdate_runner.py` | `batch_start`、各阶段 `*_failed`、`family_passed` |
| `batch_semantic_patch_runner.py` | `batch_start`、各阶段 `*_failed`、`family_passed` |
| `native_compile_runner.py` | `compile_start`、`compile_ok`、`compile_failed` |
| `native_benchmark_runner.py` | `benchmark_start`、`benchmark_done` |
| `subject_validations.py` | `subject_validations_start`、`subject_validations_done` |
| `verification_kernel.py` | `kernel.build_snapshot`、`kernel.evaluate_*` |

## C++ 层使用

### 规范实现

位置：`src/native/common/chaos/trace.h`

```cpp
// 初始化（读取 CHAOS_TRACE_PATH 和 CHAOS_TRACE_ID 环境变量）
CHAOS_IL2CPP_LOG_TRACE_INIT();

// 追踪点
CHAOS_IL2CPP_LOG_TRACE("runtime", "ResolveOrInstantiateType", "\"arg_count\"=%u", arg_count);

// 手动刷出 ring buffer（默认 atexit 自动刷出）
CHAOS_IL2CPP_LOG_TRACE_FLUSH(path);
```

### 关键特性

- **Ring buffer** — 256 条目，每行最多 256 字符，线程安全
- **atexit 自动刷出** — 进程退出时自动 flush 到文件
- **Debug 构建启用** — 通过 `CHAOS_TRACE_ENABLED` 编译定义控制
- **零开销** — SHIP/PROFILE 构建中所有宏展开为 `((void)0)`

### 当前 C++ trace 点

| 文件 | 追踪点 |
|------|--------|
| `runtime_core.cpp` | `RuntimeInit` — 含 `CHAOS_IL2CPP_LOG_TRACE_INIT` |
| `runtime_instantiation.cpp` | `ResolveOrInstantiateType`、`ResolveOrInstantiateMethod`、`InterpreterDispatch`、`bridge_init` |
| `runtime_vtable.cpp` | `BuildRuntimeVTable` |
| `layout_engine.cpp` | `GetOrComputeLayout` |
| `generic_context.cpp` | `RegisterGenericInstantiation`、`TryResolveClosedType` |

## C++ 统一日志系统（Chaos Log）

位置：`src/native/common/chaos/log.h`

在 trace 系统（结构化 JSONL 追踪）之上，新增了**统一日志系统**用于人类可读的运行时信息输出。

### 架构

- **Per-thread TLS ring buffer** — 64 条目 × 256 B = 16 KB/线程，热路径无锁
- **Buffer wrap 触发 flush** — 全局 mutex 保护，批量写出
- **编译期等级消除** — 低于阈值的日志展开为 `((void)0)`，运行时零开销
- **输出目标可配置** — stdout / trace ring buffer，运行时位掩码切换

### 等级控制

| 宏 | 等级值 | 编译条件 |
|----|--------|---------|
| `LOG_ERROR` | 0 | **始终编译** |
| `LOG_WARN` | 1 | `CHAOS_IL2CPP_LOG_LEVEL >= 1` |
| `LOG_INFO` | 2 | `CHAOS_IL2CPP_LOG_LEVEL >= 2`（默认 SHIP） |
| `LOG_DEBUG` | 3 | `CHAOS_IL2CPP_LOG_LEVEL >= 3`（Debug 构建默认） |

`CHAOS_IL2CPP_LOG_LEVEL` 默认值：Debug 构建为 3，Ship 构建为 2。

### API 参考

```cpp
// 简单消息（无格式化开销）
CHAOS_IL2CPP_LOG_ERROR("Memory", "allocation failed");
CHAOS_IL2CPP_LOG_WARN("GC", "heap near limit");
CHAOS_IL2CPP_LOG_INFO("Init", "runtime ready");
CHAOS_IL2CPP_LOG_DEBUG("Codegen", "emit method table");

// 格式化消息（fmtlib 语法 {0} {1}）
CHAOS_IL2CPP_LOG_ERROR_M("Memory", "alloc {0} failed at {1}", size, loc);
CHAOS_IL2CPP_LOG_INFO_M("Init", "loaded {0} types in {1}ms", count, ms);

// 原始协议输出（机器消费，无日志前缀，flush mutex 保护）
CHAOS_IL2CPP_LOG_WRITE_RAW("{\"elapsed\":1.23}\n");
CHAOS_IL2CPP_LOG_WRITE_RAW_M("{{\"key\":{0}}}\n", value);

// 控制
CHAOS_IL2CPP_LOG_FLUSH();                                    // 显式刷出当前线程 buffer
CHAOS_IL2CPP_LOG_FLUSH_STDOUT();                             // 刷新 stdout（flush mutex 保护）
CHAOS_IL2CPP_LOG_SET_OUTPUT(CHAOS_IL2CPP_LOG_OUTPUT_STDOUT); // 输出到 stdout（默认）
CHAOS_IL2CPP_LOG_SET_OUTPUT(CHAOS_IL2CPP_LOG_OUTPUT_TRACE);  // 输出到 trace ring buffer
CHAOS_IL2CPP_LOG_SET_OUTPUT(1u | 2u);                        // 同时输出到两者
```

### 与 trace 系统的关系

| 维度 | Trace（`CHAOS_IL2CPP_LOG_TRACE`） | Log（`CHAOS_IL2CPP_LOG_*`） |
|------|------|------|
| 用途 | 结构化 JSONL 追踪，供工具消费 | 人类可读的运行时日志 |
| 输出格式 | JSONL (ring buffer → file) | `[timestamp][LEVEL][cat] msg` |
| 编译控制 | `CHAOS_TRACE_ENABLED` | `CHAOS_IL2CPP_LOG_LEVEL` |
| 多线程 | 全局无锁 ring buffer | Per-thread TLS buffer + mutex flush |
| 可选路由到对方 | — | `LOG_SET_OUTPUT(TRACE)` |
| 错误联动 | — | ERROR/WARN 自动同时写 trace |

### 项目约定

1. **禁止直接使用 std::printf / std::fprintf** — 所有输出必须通过 `CHAOS_IL2CPP_LOG_*` 系列宏
2. **禁止直接使用 std::fflush** — 必须使用 `CHAOS_IL2CPP_LOG_FLUSH_STDOUT()`
3. **机器协议输出**（benchmark JSON 等）使用 `CHAOS_IL2CPP_LOG_WRITE_RAW` / `_M`
4. **字符串格式化**使用 `fmt::format` / `fmt::format_to_n`，禁止 `std::snprintf`

### 迁移状态

| 项目 | 状态 |

| `std::fflush` 消除 | 全部完成 — 仅 log.h 实现内部保留 |
| `std::snprintf` → `fmt::format` | 全部完成 — 仅 trace.h 保留（已转换为 fmt::format） |
| `#include <cstdio>` 清理 | 全部完成 — 仅 log.h/trace.h 保留 |

## 事件系统关联

trace 系统与 `events.py` / `operation_reporting.py` 事件系统双向关联：

| 方向 | 机制 | 用途 |
|------|------|------|
| trace → events | 每个 trace record 带 `runId` | 从 trace 跳到对应 events session |
| events → trace | 每个 event 带 `traceId` | 从 event 跳到对应 trace session |
| 初始化 | `run.py` 在 `start_operation_report()` 后调用 `set_run_id()` | 自动关联 |

这使得 `trace.jsonl` 和 `events.jsonl` 可以通过 `runId` / `traceId` 交叉查询。

## 错误排查工作流

> trace 是日常开发中定位错误的**首选手段**。在提问题、加日志、断点调试之前，先看 trace。

### 标准流程

```
[1] 运行测试/管线
        │
        ▼
[2] 发现失败（编译错、测试红、断言挂）
        │
        ▼
[3] 查看 trace 最新会话
        run trace                           ← 第一步
        run trace --stage codegen           ← 按阶段缩小范围
        run trace --exception               ← 只看异常
        │
        ▼
[4] 定位错误阶段
        "batch-native-aot:family_convert FAILED"
        "compile_failed"
        "family_emit_failed"
        │
        ▼
[5] 查看源文件和行号
        run trace --source                  ← 显示每个 trace 点的源文件:行号
        │
        ▼
[6] 分析性能退化（如适用）
        trace-analyze                       ← 看阶段耗时分布
        trace-analyze --op compile          ← 某操作的平均耗时
```

### 场景化示例

#### 场景 A：batch 管线失败

```bash
# 1. 运行 batch
python batch_native_aot_runner.py --families convert-char

# 2. 查看 trace
python -m build.toolchains.run.commands.trace_viewer

# 3. 预期看到：
#    batch_start → build_entrypoint → convert → trim → emit-native-aot
# 如果某一步 FAILED，trace 记录会显示 phase="exception" 和 error 信息
```

#### 场景 B：foundation-dll 测试失败

```bash
# 1. 运行测试
python -m pytest tests/unit/compatibility/test_xxx.py -v

# 2. 查看 trace 最新会话
python -m build.toolchains.run.commands.trace_analyze_entry --session 0

# 3. 如果有疑问，查具体操作的 span 链
python -m build.toolchains.run.commands.trace_viewer --op "kernel.evaluate_native_proof"
```

#### 场景 C：性能变慢

```bash
# 对比两次运行的阶段耗时
trace-analyze --session 0      # 运行 A 的 trace
trace-analyze --session 1      # 运行 B 的 trace

# 关注 stage_breakdown 中的 total_ms 变化
# 如果某个 stage 耗时翻倍，说明该阶段出了问题
```

### 规则

- **先看 trace，再问问题** — 任何管线/测试失败，第一步是 `run trace` 或 `trace-analyze`
- **trace 查不到再补日志** — trace 遵循统一 schema 且有 span 层级，如果信息不够才考虑加临时 print
- **新功能必须带 trace 点** — 新增测试管线步骤时，必须在入口和退出加 `trace()` 调用
- **失败必须可追溯** — 任何 `except` / `catch` 路径必须包含 `phase="exception"` 的 trace 记录，附带 `exception` 类型和 `message`
- **不跳过错排查** — 开发/调试过程中禁止用 `--no-trace` 跳过 trace 初始化

## 数据流

```
Python run.py / batch_*_runner.py
  │
  ├─ trace_init() → 创建 artifacts/logs/trace/<session>/trace.jsonl
  ├─ 导出 CHAOS_TRACE_PATH + CHAOS_TRACE_ID 环境变量
  │
  ├─ spawn C# Driver (dotnet run ...)
  │    └─ ChaosTrace.InitFromEnv() → 读取 CHAOS_TRACE_PATH/ID
  │    └─ 在各阶段调用 Point() → 写入同一 trace.jsonl
  │
  ├─ spawn C# TestFramework.Runtime (dotnet run ...)
  │    └─ RuntimeTrace 静态初始化 → 读取 CHAOS_TRACE_PATH/ID
  │    └─ 每个 test/benchmark 调用 TraceCall() → 写入同一 trace.jsonl
  │
  └─ spawn C++ 进程（仅在 Debug 构建）
       └─ CHAOS_IL2CPP_LOG_TRACE_INIT() → 读取 CHAOS_TRACE_PATH/ID
       └─ CHAOS_IL2CPP_LOG_TRACE() → ring buffer → atexit flush 到同一文件
```
