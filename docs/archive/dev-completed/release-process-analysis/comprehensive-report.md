## 3. 关键断层（产品级阻断）

以下断层使得项目**无法达到产品级发布品质**。每个都是必须解决的门槛问题。

### 🔴 F1：无 GitHub Release 创建流程

**现状**：`release_bump.sh --tag` 创建 git tag，但没有任何 GitHub Release 创建、产物上传、或 release notes 发布。

**影响**：
- 没有可下载的发布包（没有 `.zip`/`.tar.gz` SDK 包）
- 没有可追溯的发布版本映射
- 用户无法通过 GitHub Releases 页面获取二进制

**产品级要求**：每个 `v*` tag 自动触发 GitHub Release 创建，包含：
- 预编译的 SDK 包（Windows + Linux + ARM64）
- 与 tag 配套的 release notes
- 校验和（SHA256）
- 发布包签名

### 🔴 F2：无发布分支策略

**现状**：所有开发都在 `main` 分支上进行，没有 `release/*` 或 `stable/*` 分支。

**影响**：
- 无法在发布冻结后继续开发而不互相干扰
- 没有 hotfix 分支流程
- 紧急修复无法与主开发线隔离
- 无法做"发布后补丁"的稳定基线

**产品级要求**：
```
main ──┬── feature/* ────┐
       │                 ▼
       ├── release/0.1.x ─── tag v0.1.0 ── hotfix/0.1.1
       ├── release/0.2.x ─── tag v0.2.0
       └── ...
```

### 🔴 F3：无 Release Notes 自动化

**现状**：`CHANGELOG.md` 是纯手工维护的高层级摘要，无自动生成机制。

**影响**：
- 每次发布时人工编写 release notes 是瓶颈
- 容易遗漏重要变更
- 无法按分类（breaking/feature/fix/perf）自动生成
- 无法追溯每个 commit 对应的发布版本

**产品级要求**：`git log --oneline v0.1.0..HEAD` + 分类模板 → 自动生成 release notes draft

### 🔴 F4：无产物校验和与签名

**现状**：publish 产出 `entry.exe` 和 `publish.manifest.json`，但无任何完整性校验。

**影响**：
- 无法验证产物的完整性
- 无法对抗供应链篡改（supply chain attack）
- 没有可验证的出处（provenance）

**产品级要求**：
- 所有发布产物附带 SHA256 校验和
- 关键产物（SDK libs、runtime DLL）需要数字签名
- 生成 SBOM（Software Bill of Materials）

### 🔴 F5：无 SBOM / 安全扫描

**现状**：`SECURITY.md` 存在但无自动化安全扫描。无 Dependabot 配置。无 CodeQL 分析。

**影响**：
- 第三方依赖的漏洞无法自动发现
- 无法满足企业级安全合规要求
- 没有 SBOM 无法做供应链安全审计

**产品级要求**：
- 启用 Dependabot 或类似工具扫描依赖漏洞
- 启用 CodeQL 或类似工具做静态分析
- 每次发布时生成 SBOM（CycloneDX 或 SPDX 格式）

### 🔴 F6：无发布节奏 / 日历

**现状**：没有定义的发布频率（周/月/季度）、没有发布窗口、没有冻结期。

**影响**：
- 发布是"准备好了就发"的临场行为
- 没有可预测的版本交付承诺
- 下游用户无法规划升级

**产品级要求**：定义发布节奏（如：每月 minor、按需 patch），并遵守发布冻结期。

### 🔴 F7：Mobile 发布无 CI 支持

**现状**：Android NDK/emulator 和 iOS Xcode 的测试都是"人工手动"的，release-checklist 仅要求"附带证据"。

**影响**：
- 移动端发布无法自动化
- 发布前没有 CI 级的移动端验证
- 人工证据容易遗漏或过时

**产品级要求**：Android 至少需要 CI 中编译 + 模拟器运行；iOS 至少需要 macOS runner 编译。

## 4. 中等风险缺口

### 🟡 M1：Pre-push 审查为 advisory 而非 blocking

**现状**：`pre-push` hook 运行 LLM 审查，但即使是 L1 严重问题也**不阻止 push**（`exit 0`）。

**风险**：严重问题（如内存安全、数据竞争）可能被记录但被忽略，尤其在大团队或多分支协作时。

**建议**：对 L1 问题改为 blocking（`exit 1`），或至少对 `main` 分支做 blocking。

### 🟡 M2：Release Checklist 无自动化强制

**现状**：7 个必查项只有文档，没有任何 CI 检查或自动化验证。

**风险**：发布者可能"忘记"或"觉得不重要"跳过某些检查项。

**建议**：至少将其中可自动化的项（perf regression、soak test 结果）对接 CI 数据。

### 🟡 M3：PublishController 未完全就绪

**现状**：`PublishController` 存在但不完整：
- `IsJit` 模式未接线（emit warning 后继续使用 AOT）
- entry `Main(string[])` 传入 null 指针，会崩溃
- `CopyRealSdkLibsOverStubs` 依赖 repo 根目录探测

**风险**：`publish --mode app` 在非 repo 环境中不可靠。

**建议**：完成这些 TODO 条目，并添加 publish 端到端测试。

### 🟡 M4：无 NuGet 或包管理发布

**现状**：`src/managed/` 下的项目能够生成 NuGet 包，但无发布管线。

**风险**：项目作为 IL2CPP 工具链，缺少 nuget.org 或私有 feed 的发布能力。

**建议**：如果面向 .NET 工具链消费者，需要 NuGet 发布管线。

### 🟡 M5：无版本升级/热修复流程

**现状**：`release_bump.sh` 只处理正常的版本递增，无 hotfix 分支合并流程。

**风险**：线上紧急修复时可能破坏版本一致性。

**建议**：定义 hotfix 流程：`hotfix/0.1.1` → `release/0.1.x` → 合并回 `main`。

### 🟡 M6：无发布演练/干跑能力

**现状**：每次发布是"第一次"发布，没有 rehearsal 流程。

**风险**：发布当天才发现 CI 失败、产物缺失、权限不足等问题。

**建议**：支持 `--dry-run` 模式的发布演练，在隔离环境验证完整流程。

### 🟡 M7：兼容性矩阵未自动化

**现状**：`version-compatibility-matrix.md` 定义了规则，但无 CI 自动校验。

**风险**：hotupdate patch 可能导致兼容性断裂，发布时未发现。
                      
**建议**：将 `PackageValidator` 的兼容性校验集成到 CI 中。

### 🟡 M8：产物清理/保留策略

**现状**：CI 产物（upload-artifact）无限保留，无过期策略。

**风险**：GitHub Actions 存储空间浪费，长期维护成本增加。

**建议**：定义产物保留天数（如：30 天 PR 产物，365 天发布产物）。

### 5.2 需要新增的 CI 工作流

```yaml
# .github/workflows/release.yml（新增）
name: Release
on:
  push:
    tags: ['v*']
jobs:
  create-release:
    steps:
      - generate-release-notes    # 从 git log 自动生成
      - build-all-platforms       # 构建 Windows + Linux + ARM64 SDK
      - generate-checksums        # SHA256 + 签名
```

| **产物分发** | 15/100 | 严重缺失 — 无 Release、无签名、无 SBOM |
| **发布治理** | 40/100 | 清单存在但无自动化，无节奏，无演练 |
| **安全合规** | 25/100 | SECURITY.md 存在但无自动化扫描 |
| **文档化** | 60/100 | 有 release-checklist 但发布流程无完整文档 |

### 7.2 主要差距

2. **安全合规**严重不足（25/100）：没有自动化漏洞扫描，没有 SBOM
3. **发布治理**半成品（40/100）：有文档但无自动化，容易被跳过

### 7.3 达到产品级发布需要完成的工作

```
P0 完成 → 可做"受限产品发布"（alpha/beta）
P0 + P1 完成 → 可做"正式产品发布"（GA）
P0 + P1 + P2 完成 → 可做"工业化产品发布"（enterprise-grade）
```

## 8. 结论

### 总体评价

Chaos IL2CPP 的发布流程当前处于**"开发成熟但发布原始"**的状态：

- **开发阶段的质量门禁是行业领先的**：pre-commit 的 8 道检查、分层已知失败基线、性能回归检测、仓库卫生监控 — 这些是很多商业产品都不具备的。
- **发布阶段的自动化是工业级的缺失**：从 git tag 到用户可下载的发布包这一段，完全是空白。没有发布分支、没有 GitHub Release、没有校验和、没有 SBOM、没有自动 release notes。

### 关键建议

1. **立即补齐 P0 四项**（2.5 天工作量）—— 这是从"我们能跑"到"我们能发"的最小门槛
2. **在首次正式发布前完成 P1 六项**（4.25 天工作量）—— 确保发布质量可信
3. **定义发布节奏**并坚持执行 —— 即使只是每月一次，也比"准备好了就发"更专业
4. **将 pre-push 审查从 advisory 改为 blocking**（至少对 main 分支）—— 这是最便宜的高价值改进

### 风险提示

如果以当前状态进行首次产品级发布，以下风险极高：

1. **产物完整性无法验证** → 用户下载的二进制可能被篡改而不被发现
2. **无发布分支隔离** → 发布后继续开发可能引入破坏，且无法做紧急修复
3. **无发布节奏** → 下游用户无法规划升级，影响项目信誉
4. **移动端无 CI 验证** → 声称支持 iOS/Android 但无法验证
