# 综合报告：AI-Agent 生成的目录文件，这套方案能否防漂移？

> 2026-08-27 · 域：仓库结构/技术债
> 背景：仓库绝大部分文件由 AI agent 生成/驱动。用户问：我已部署的守卫体系（root-clean /
> --disk / generated-drift / churn-registry）**能否真正有效防止漂移**。
> 本文做批判性、诚实的评估——不只讲能做到的，也讲**结构性做不到的**。

---

## 〇、一句话结论

> **这套体系对"有确定生成器、可对账"的漂移有效；对"AI 手写、无 oracle"的漂移
> 结构性失效。** 而仓库的绝大多数 AI 文件恰恰属于后者。所以——它防住了最容易被
> 机器判定的漂移，但**没有、也不可能**防住 AI 迭代本身带来的语义漂移。

---

## 一、"漂移"的分层（AI 环境下必须先分清）

| 层 | 定义 | 例子 | 能机器判定吗？ |
|----|------|------|---------------|
| **L1 机械漂移** | 生成物与确定的 schema/生成器不一致 | `ir_opcode_names.h` 37 → schema 112 | ✅ 能（有 oracle） |
| **L2 结构污染** | 生成物/产物逃离规定目录，混入源码 | `.inc` 平铺；新建 `debug_output/` | ✅ 能（路径白名单） |
| **L3 语义漂移** | 同一来源文件，AI 重写后含义变了（未知变） | AI 改了一个 stub 的行为 | ❌ 不能（无 oracle） |
| **L4 需求-代码漂移** | 需求/架构变了，代码没跟上（或反之） | 新 opcode 加入但解释器没实现 | ❌ 不能（需人/测试） |

**我的体系解决了 L1 + L2，对 L3/L4 无能为力。**

---

## 二、各守卫生效地（诚实评估）

| 守卫 | 防什么漂移 | 有效上限 | 结构性盲区 |
|------|-----------|---------|-----------|
| `check_repo_clean.py`（根） | L2 根级结构污染 | 只对**未忽略的**新顶层文件/目录 | **ignored 产物**（进不去 git status）看不见——--disk 补了一层，但只到"阈值告警" |
| `--disk` | L2 ignored 产物堆积 | 只报 >200MB 的 ignored 根 | 不知道哪些是"该删"vs"该留"；不可精确（bounded walk） |
| `generated-registry` + churn 意识 | L1 可再生文件改动 | 只对**登记过的** glob | 名单外的新生成文件漏 |
| `check_generated_up_to_date` | **L1 唯一真正抓到漂移的** | 只对**注册的生成器**（现只有 ir_opcodes） | **C# pipeline 的 362 个 .generated.cpp 一个都没注册**；手写 stub 无 oracle |

**关键缺口实证**：
- 362 个 `.generated.cpp` 是 C# codegen 产物，**没有任何 drift 守卫**（我没注册其生成器）。
- 1062 个手写 `.cpp` 中大都是 AI 写的，**无 oracle**——AI 改逻辑、加 stub、改 enum_stubs，我的守卫无从对账。
- 我抓到的 37→112 漂移，是因为**碰巧 ir_opcodes 有确定的 YAML schema 作 oracle**。

---

## 三、为什么 AI 环境下"防漂移"本质上更难

1. **生成器本身是 AI 写的、还在变**。昨天能稳定重生成 `ir_opcodes.h` 的脚本，今天可能被 AI 改了输出格式——drift 守卫会在生成器自身迭代时**误报**（把"生成器变了"误判为"文件脏了"）。
   → 我的 whitespace 归一化就是在处理这种"生成器微小输出变化"。
2. **没有 golden 可对账的 AI 产出占大多数**（stub、手写逻辑、测试 fixture）。这类文件只能靠**编译/测试/人工 review**，机器守卫无 oracle。
3. **AI 的 L3/L4 漂移往往伴随"行为不变但表述变"**——守卫看字节，行为等价它无从得知。

---

## 四、能做什么（把体系补强成对 L3/L4 也有发言权）

不是"无法"，而是"需要换武器"——从**呆板 diff** 升级到**行为验证**：

| 补强 | 治的漂移 | 成本 | 风险 |
|------|---------|------|------|
| **① 给 C# codegen 产物也接 drift 守卫**（注册其生成器 + `--out-dir`） | L1（362 个 .generated.cpp） | 中 | 低 |
| **② "生成器迭代=脏"边界**：drift 守卫区分"生成器变了" vs "生成器没变但输出变了"（记录生成器自身 hash） | L1 误报 | 低 | 低 |
| **③ 编译门**：pre-commit 对**生成的 C++**跑 compile-check（不 build 全仓，只 syntax） | L3（生成物不可编译=漂移铁证） | 中 | 中（慢） |
| **④ 行为单测锚**：为关键生成物（ir_opcodes/解释器 opcode 处理）加"数值+数量"不变式单测（static_assert 已有一半） | L3 | 中 | 低 |
| **⑤ AI 变更追溯**：README/commit 约定 AI 改的生成物必须"重生成提交"而非手改（治理 + git blame 威慑） | L3/L4 人工防线 | 最低 | 低 |

**但必须诚实**：④⑤ 治标，真正防 AI 的 L3/L4 语义漂移，**没有机械 oracle 可替代"测试 + 人"**。守卫能把"最易机器判定"的 L1/L2 管住（这是实打实的），把 L3/L4 的压力降到"让测试和 review 去抓"，这已是 AI 仓能做到的最好。

---

## 五、这份报告证明的、反证的事

**证明**：守卫确实能抓真漂移（37→112 是活证据）、架构可扩展（新增生成器一行注册）。

**反证（警惕）**：
- 我把"当前全部干净不 churn"当成"防住了"，其实是被动等 generator 出问题才触发。
- 362 个 .generated.cpp 没守卫 + 1062 个 AI 手写 cpp 无 oracle —— **这是真实的覆盖空洞**。
- 我此前多次说"已防住/干净"，对 L3/L4 而言**过于乐观**。

---

## 六、建议动作（务实排）

| 优先级 | 动作 | 治漂移层 |
|--------|------|---------|
| **P0** | 给 C# codegen 产物注册 drift 守卫（①）——补最大覆盖洞 | L1 |
| **P0** | 修已知 L1 漂移 `ir_opcode_names.h`（37→112，独立代码任务） | L1 |
| **P1** | 编译门：生成的 C++ pre-commit syntax-compile（③） | L3 |
| **P1** | AI 变更追溯治理（⑤）| L3/L4 |
| **P2** | 生成器自身 hash 去误报（②）+ 行为不变式单测（④）| L1/L3 |

> 一句话给决策：**这套守卫把"可对账的漂移"管严了，但 AI 仓的真风险在"无 oracle 的
> 语义漂移"——那只能靠测试 + 编译门 + 人，不能靠 diff 守卫。别把结构守卫当成防漂移
> 的全部。**
