# 这些守卫方案，在 Agent Coding 里到底有没有实际意义？

> 2026-08-27 · 纯分析/判断，无新增代码。
> 用户问：我提出的语义漂移守卫（①符号契约 ②行为锚 ③生成器hash ④治理）在真实
> agent-coding 工作流里，最终是否有实际价值？诚实回答。

---

## 一、得先认清 agent-coding 的真实反馈闭环

Agent 写代码不是"写完提交就完了"，而是 `改 → 跑测试 → 修 → 提交` 的**本地闭环**。
这意味着 agent 对自己刚动的文件有**局部上下文**——它知道为什么变。

对一个正在跑的闭环：
- **测试套件** = 真语义 oracle（行为对不对）
- **编译/链接** = 真"能不能建" oracle（健不健壮）
- agent 本来就跑这两样。

**所以守卫的价值坐标不是"绝对能力"，而是"边际价值"**——在测试 + 编译都过了的前提下，
它还能不能抓到一个没被抓住的问题？这才是它存在的理由。

---

## 二、按"是否逃出 测试+编译 闭环"给漂移分类

| 漂移类型 | 测试会抓? | 编译会抓? | 需要一个独立守卫? |
|---------|:---:|:---:|-------|
| 编译错 / 链接错 | — | ✅ | **否**（编译已是 oracle） |
| 行为错（AI 改坏逻辑） | ✅ | — | **否**（测试已是 oracle，守卫=赘余测试） |
| **静默过期**：`.generated` 值旧但没任何地方报错 | ❌ | ❌ | **✅ 是！唯一真缺口** |
| **诱饵 stub**：extern 有、实现是 return-0/假货 | ❌ | ✅(通常) | **✅ 是**（编译过但语义是假） |
| **常量-vs-bound**：kMax=4096 数组 1024 | ❌ | ❌(常) | **✅ 是** |

> **结论：守卫的边际价值只存在于"静默"类——测试和编译都放过了，但状态是错的。**

---

## 三、逐方案掂量（在 agent 闭环里的真实意义）

### 方案①（符号契约 / 编译 + nm 审计）
- 编译已让链接器抓符号缺失。**边际只抓"链接成功但实现是假 stub"**——这确实是有价值的
  （memory 里 111 个 stub gap、return-0 假实现就是这类）。
- **但**：agent 本来就会 `nm`/看链接错。独立守卫的边际 = 抓"链接过但语义假"这一层。
- **评价：有一点意义，但窄**。性价比低于直接做"stub 完成度测试"。

### 方案②（行为锚测试）——**这个要泼冷水**
- 行为锚 = "输入→期望输出"测试 = **就是测试**。
- **若测试已够好，行为锚是冗余**，守卫层是赘余。
- **若测试不够好**（本仓 memory 反复显示：corelib 5/75 覆盖、111 stub gap、5% 覆盖），
  那缺口在"**测试质量**"，不在"守卫"。加行为锚门 = 把一个测试质量问题伪装成守卫问题。
- **评价：方案本身没意义，但暴露的真问题（测试覆盖差）极有意义。** 别造守卫，去补测试。

### 方案③（生成器 hash 去误报）——**唯一明确有价值的**
- agent 常跑生成器、常提交。守卫若因"生成器迭代/whitespace"误报，agent 会学乖忽略它
  → 守卫信号**衰减死亡**。
- 给生成器 hash，让守卫只对"生成器没变但输出变了"报警，**保住守卫信用**。这是让整套
  守卫活下来的地基。
- **评价：值得做，成本低，防守卫自毁。**

### 方案④（治理/规约）——人格化博弈
- "禁止手改 .generated"靠 git blame 威慑。对 AI 有效吗？AI 不会主动看规约，除非 hook。
- 它不拦，只事后归责。**用于事后追责可以，防漂移作用弱。**

## 四、agent-coding 里最被低估的真问题（守卫外的）

> 以上全在讨论"守卫能防什么"。但 agent-coding 的实践里，语义漂移的头号来源不是
> "文件过期"，而是 **AI 用一个 return-0/假 stub 去"填坑"，编译过、测试没覆盖——静默贷债**。
> 这**不是守卫能解的**，是**测试覆盖 + 完成度断言**能解的。

真正高杠杆的两件事：
1. **完成度断言**：关键符号/API 必须有"行为已完成"标记，AI 填 return-0 会被钉死
   （比守卫强，因为直接卡行为）。
2. **测试覆盖门**：核心域（interpreter/GC/stub）丢掉的覆盖面补上——比任何守卫都实际。

---

## 五、一句话诚实结论

> **这些守卫方案里，只有 ③ 和"完成度断言/测试覆盖"真有实际意义。①②④ 大多是
> 把"已经存在的 oracle（测试/编译）"或"本应补的测试"伪装成守卫装置——造出来多半
> 沦为 agent 必须点心跳的噪音，最终被跳过。**

**真正要做的（按性价比）**：
| 优先级 | 做 | 为什么 |
|--------|----|--------|
| **P0** | ③ 生成器 hash（守卫信用） | 防守卫自毁，成本低 |
| **P0** | 完成度断言（stub 必须"真实现"标记） | 直接卡 AI return-0 贷债，比守卫高级 |
| **P1** | 补测试覆盖（interpreter/GC/stub） | 真语义 oracle，治本 |
| ~~②~~ | ~~行为锚门~~ | ~~= 测试，冗余，不做~~ |
| ~~①④~~ | ~~符号门/治理~~ | ~~编译已管 / 事后才有用，边际低~~ |
