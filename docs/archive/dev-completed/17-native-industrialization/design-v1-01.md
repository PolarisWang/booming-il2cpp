## 2. 对标 production il2cpp 工程门禁

production il2cpp（Unity/微软版）的工业化特征：

- **clang-tidy 全量主机构建**：每次 CI 构建同时运行 static analyzer
- **测试矩阵**：多个 SDK 版本 × 多个平台 × 多个配置
- **覆盖率门禁**：新代码必须覆盖，历史代码逐步收敛
- **性能基线**：benchmark 自动比较，Δ% 超阈值自动 red
- **API 文档**：核心合约头文件有 Doxygen 注释，自动生成
- **模块化**：runtime-core 拆为独立可测试的子系统
- **静态分析 0 warning 策略**：clang-tidy 所有检查必须通过

本项目当前状态：**骨架已具备（CI 管线、测试框架、契约系统），但缺少 production 级别的质量门禁和工程化工具链**。

## 3. 方案设计

### 方案 A：先工具链，后重构（推荐）

**策略**：先建立完整的质量门禁体系（工具链全覆盖），再在护网保护下进行模块化重构。

**阶段**：
1. T-A: 工具链全覆盖（clang-tidy/clang-format/覆盖率/UBSan/模糊测试 CI）
2. T-B: 架构设计与编码规范收紧
3. P1: 编码规范审计（分配/错误处理/命名）
4. P2: 模块化重构（大文件拆分/循环依赖消除）
5. P3: API 文档体系
6. P4: 单测覆盖补齐

**优势**：护网先行，重构安全；每阶段可独立交付
**风险**：T-A 阶段可能暴露大量存量 clang-tidy 警告，需要分类处理

### 方案 B：先重构，后工具链

**策略**：先完成模块化重构和编码规范收紧，再建立工具链。

**优势**：重构时不受存量警告干扰
**风险**：无护网保护下重构，可能引入回归且无法被 CI 捕获

### 方案 C：整体并行推进

**策略**：所有方向并行推进，worktree 隔离。

**优势**：总耗时最短
**风险**：团队并行能力要求高；冲突管理复杂

### 推荐方案 A

**理由**：
1. 工具链先行是 GC-工业化已验证的成功模式（T-A → T-B → P1-P5 顺序）
2. 护网先行确保重构安全性（P1 性能优先级需要在工具链保护下安全执行）
3. 存量 clang-tidy 警告可通过分类（suppress/ignore/fix）逐步处理，不影响 CI 门禁启动

### 优先级权衡

| 方案 | P1 性能 | P2 架构 | P3 热更新 | 推荐 |
|------|---------|---------|----------|------|
| A | ✅ 工具链不降性能 | ✅ 逐步改善 | ✅ 不影响 | ⭐ |
| B | ⚠️ 重构可能临时降性能 | ✅ 先做 | ✅ 不影响 | |
| C | ⚠️ 并行冲突可能 | ✅ 最快 | ✅ 不影响 | |

## 5. 风险评估

| 风险 | 概率 | 影响 | 缓解 |
|-----|------|------|------|
| clang-tidy 存量警告过多 | 高 | T-A 阶段阻塞 | 分类策略：P0 错误(必须修)/P1 警告(逐步修)/suppress(允许) |
| 覆盖率阈值设置不合理 | 中 | 门禁形同虚设或频繁误报 | 先 baseline 摸底，再设渐进阈值（50%→70%→80%） |
| 模块化重构引入回归 | 中 | 功能异常 | T-A 护网先行，逐步重构，小步提交 |
| 大文件拆分破坏 git blame | 低 | 历史追溯困难 | 只拆不改逻辑，单次提交只做拆分+重命名 |
| 性能回归 | 低 | 重构后性能下降 | 性能基线 + Δ% 阈值 + 对比 CI 步骤 |
| 工具链迁移成本 | 中 | Windows/Linux 差异 | 工具链配置同时兼容 MSVC 和 GCC/Clang |

## 6. 验收标准

### 各阶段完成定义

| 阶段 | 完成定义 |
|------|---------|
| T-A | clang-tidy CI 强制（0 P0 error）、clang-format CI 强制、覆盖率阈值 ≥50%（摸底值）、UBSan CI 集成、模糊测试 ≥5 个 + CI |
| T-B | 架构设计文档完成（含大文件拆分、模块依赖消除、错误类型统一方案）、用户审批通过 |
| P1 | 176 处裸 new 走宏体系、reinterpret_cast 分类审查完成、命名规范一致 |
| P2 | 22 个超大文件拆至 ≤5 个、runtime-core→jit 反向依赖消除、模块化子目录明确 |
| P3 | Doxygen 配置部署、核心合约头文件 API 注释覆盖、CI 自动生成 + GitHub Pages 发布 |
| P4 | runtime-core 核心路径覆盖率 ≥70%、known-fail 从 82 收敛至 ≤30 |

### 最终验收

- clang-tidy 全量检查通过（suppress 列表仅含合理项）
- 覆盖率 ≥80%（核心模块）
- 性能回归 Δ% < 5%（与 baseline 对比）
- 已知失败基线 ≤30 条
- API 文档自动生成并发布
- 模块化架构：无循环依赖、无 >1000 行文件、runtime-core 拆为 3-5 个子系统

## 7. 非目标

- 不重写现有 GC 核心（已在 GC-工业化覆盖）
- 不做全量 C++ 代码重构（仅聚焦工业化品质缺口）
- 不改 codegen 输出格式（需在 codegen-expert 域单独处理）
- 不引入新的第三方依赖（除非工具链必需，如 clang-tidy）
- 不改变现有 C++ 标准（保持 C++17/20）
