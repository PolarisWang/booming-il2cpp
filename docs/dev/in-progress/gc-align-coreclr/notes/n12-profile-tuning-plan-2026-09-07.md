# GC-N12 Profile 驱动调参 — 完整方案（供判断）

> 日期：2026-09-07 | 状态：**方案已实现为 AllocationDrivenYoungGc + 参数扫描，推荐 Gen1MinPromotionAge=4（推荐值是否固化默认待拍板）** — 本文件为方案设计原始文档，最终状态以 STATUS.md 为准（见 §八隔离承诺：推荐值未进生产默认） | 类别：跨域专项（GC + codegen + test-governance + profile pipeline）

## 一、问题（为什么需要这个专项）

N12 的目标是"用真实负载采集 GC profile 数据 → 驱动 GC 参数（nursery size / promotion threshold / trigger）调优 → 产生 pause/吞吐改善的量化结论"。

**阻碍**：现有 `entry.exe --profile` 逐方法测量时**只测 1 次 managed 调用**，且所有 subject 输入都是 `default(T)` / `Empty<T>()` 空值 → 单次调用分配量 0~几百字节 → **GC 从不触发** → 所有方法 `gcPauseNs = 0`。

历史证据：profile-range 扫 `System.Collections.NonGeneric` 得 **109 方法仅 7 个分配、共 271B**（注：此数据为全集累计 —— 109 个被测方法中仅 7 个方法产生了非零分配，总计 271 字节；非每方法平均值。该数据来自基础 profile 扫描，不是本会话的调参负载测量，与本 N12 方案结论的关联性为间接参考）。

**本会话已实测的第二个阻碍**（native 层 `test_gc_throughput_benchmark`）：每个参数点（nursery 1-64MB、trigger 1-4x、promotion age 1-12）跑出的 young-GC P50 都在 **61-88us 内窄幅波动**，spread 小于 run-to-run 噪声。原因：该 benchmark **显式调 `GcYoungCollection()` 强制 GC**，pause 由强制收集本身主导，参数差异被掩盖。

⇒ 结论：真正区分 GC 参数需要一个**不显式 collect、靠分配压力自然触发 GC** 的高分配 subject，且单次调用量要 > nursery region（让它自己越过 TLAB/region 上限触发 young GC）。

## 三、两条可行路径（含取舍，需你选一条）

### 路径 A：native 层高分配 target（最快，1-2 天，推荐先做）

**不改 C# subject、不走全量 codegen**。在已能跑的 native_profile 层加一个"分配压力驱动"的 benchmark 函数，它**只分配不显式 collect**，分配总量逐步越过 nursery 上限 → 自然触发 young GC。

```
新增 native_profile/<family>/gc_alloc_pressure.cpp 里一个 alloc-driven loop:
  for bulk: 分配多个 1MB byte[] / 大 array → 不留根或留部分根
  每 64KB 累积检查 alloc_since_last_gc > threshold → 让 trigger 自然拉起来
  (不调 GcYoungCollection() —— 关键是与现有 force-GC benchmark 区分)
```

- **优点**：改动小、纯 native、立刻能跑，可复用 `CHAOS_GC_*` env 旋钮（已确认 env override 生效，gc_config.cpp:65），直接复用 Release 构建。
- **缺点**：不是逐 C# 方法的 AOT profile 语义，是"分配负载级"的 GC 调参（对 N12 的"每次方法级 profile"目标只是部分的）。

### 路径 B：C# subject + DLL 扫描 + AOT（完整语义，4-7 天）

走标准 foundation-dll 主链：在某 family（建议 System.Private.CoreLib 的现有 chunk，或一个专用 family）加一个 git-tracked 的高分配方法，重新扫描 DLL → 获得 `methodSubjectId` + chunk index → 走 TPG/AOT codegen 生成 subject slot → `entry.exe --profile` 采集。

- **优点**：真正方法级 AOT profile 语义；与生产 pipeline 路径一致；产出的数据能进 perf baseline。
- **缺点**：重；要穿越 DLL-scan → codegen → C++ 生成全链，历史上有 lowering-hostile 方法（`chaos_arg_` 错、`std::memset`/大 array 未下降）需逐一绕过；**subject .cs 大多不在 git 跟踪**（`.autogen` 是 ATG 产物、scenario 目录只有 .csproj）→ 需确认 git 跟踪源到底放哪、改动是否只对测试生效。

## 四、如果走路径 A —— 具体步骤

**Phase A1**：在 `tests/contracts/native/runtime-core/`（这里是 git-tracked、纯 native、已建成 gate）加 `gc_alloc_pressure_test.cpp`：
- 一个 `TEST_F(GcAllocPressure, AllocationDrivenYoungGc)`：分配链使单线程累积分配超过当前 nursery（env 可调），**不显式 collect**，断言 `chaos_gc_get_collection_count` 增长（证明压力自然触发了 GC，非 force）。
- 用 `CHAOS_GC_YoungTriggerMultiplier` / `CHAOS_GC_NurserySize` 扫几个点，找出"自然触发所需分配量随参数变化的曲线"。

**Phase A2**：产出"压力驱动 young-GC 延迟/次数 vs 参数"表格，作为调参判据（非 force-GC 语义）。

**Phase A3**：推荐默认参数（选 P50 pause 最低 / 触发分布合理的点），写入**测试专用 config**（不写运行时默认），跑回归确认无退化。

## 五、如果走路径 B —— 具体步骤（概要）

**Phase B1**：确认一个 git-tracked family + chunk，找 subject 源真实存放处（git ls-files 现状：`.autogen/Frozen*.AutoGenerated.cs` 是 ATG 产物，scenario `.cs` 未跟踪）。若都非理想注入点，需先定"厂商 hand-written 高分配 subject 应放哪被扫描"。

**Phase B4**：单参数 + 组合扫描（复用我已验证的 env 旋钮机制），产出推荐默认 + pause 量化。
