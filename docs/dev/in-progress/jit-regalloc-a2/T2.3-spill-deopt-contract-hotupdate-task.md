## 0. ⚠️ 不处理的后果（按实害排序，已实证触发路径）

> 以下基于 2026-08-10 源码实证，区分"已实测可触发的火"vs"当前潜伏、未来才爆的雷"。**别把每个缺陷喊成同等级**。

### 🔴 C-b：热更 demotion 释放仍被执行/可被回收的旧代码（USE-AFTER-FREE，实测可触发的火）
- **触发链**：`DemoteJittedMethod`(jit_seh_handler_internal:228) → `EnqueueDemotedCode`(WinSehHandler:112) 把旧代码进入 `pending_free_` → **GC safepoint 回调 `OnGcSafepoint` → `ReclaimDemoted()`(WinSehHandler:345) 当场 `VirtualFree` 旧代码，无静默检查**（不判断是否仍有线程的栈返回地址落在旧代码上）。
- **后果**：(a) 若某线程仍在执行旧代码（栈帧返回地址在旧 region），当前线程 **executing freed memory = 崩溃（use-after-free）/未定义**；(b) GC 扫该旧帧时若地址被**回收复用**，`FindNativeCodeByAddress`/`GcLookupSlotMap` 可能命中**别的已注册方法/旧 map** → 用错布局扫帧 = **堆破坏/漏根**。
- **权值**：**热更（游戏/线上 patch 场景）必现向**；不做则每次热更都有踩空风险。
- **对照**：CoreCLR/ReJitManager 在旧版本无引用（旧帧耗尽）前**不回收旧代码**。

### 🔴 C-a：demotion 从不注销旧 GC map（泄漏 + 地址回收误配，实测）
- **触发链**：demotion 只 `entry.nm=nullptr`，从不 `GcUnregisterSlotMap(old_code)`（整个 demotion 路径无该调用；唯一在 `~JitMethod` jit_engine:5496）。
- **后果**：`s_slot_map` 残留旧地址→旧 `GcSlotMapV0`/`GcPointMapV0` 指针；地址回收复用后，新方法的相同地址会先命中**残留旧 map**（布局错误）→ 错扫/漏根。同时 `entry.nm=nullptr` 后无主释放 → **JitMethod+map 内存泄漏**（每次热更泄漏一份）。
- **权值**：与 C-b 同源同触发；保守/精确扫描都受影响。

### 🟡 C-d：热更新旧共存无回归测试 + `GcPointMapV0` 未纳入生命周期（T2.2 联动缺）
- 即使 A/C 修好，若无"重编译后旧帧用旧 map、新帧用新 map"回归测试 + `gc_point_map_data` 在 demotion/free 路径的注销，T2.2 的精确 map 会在热更后遗留，行为取决于释放顺序 → 未定义。

### 🟡 A：deopt spill offset 基址不一致（**潜伏雷，非必然现爆**）
- **实测澄清**：所有现有 `EmitDeoptSequence` 触发点（AddOvf/SubOvf/MulOvf/ConvOvf*=@指令边界；jit_engine:1850/2303/2333/2346/3164/3617/4853）都在**指令稳态**（RSP==frame base），非 helper 调用 shadow 窗口内 → **常见的纯算术溢出 deopt 当前不踩错位**。
- **会爆的场景**：方法**同时**用 `LocAlloc`（动态扩帧 → trap 时 RSP≠frame base）**且**体内有会 deopt 的 Ovf op → `ReadSpillSlot(trap_RSP, frame_base_relative_GprOff)` 错位 → **register file 重建错值 → interpreter 恢复错误状态 = 逻辑错/崩溃**。localloc + 溢出转换是合法组合，故可达。
- **权值**：当前测试覆盖少；属"修 A 成本低、爆了难查"的**低成本高价值预防**。

### 🟡 B：`int16_t spill_offset` 截断（只在高 vreg/tree 优化帧 >32K 时）
- `frame_size_extra_` 扩帧后高位 GprOff/FprOff 可能超 16-bit signed → 截断 → 同 A 的 register file 重建错值。触发需**大帧**（many tree vregs），频率低于 A 但后果同类。

### 结论（优先级）
**C（热更生命周期）> A（单一基址）> D（测试）> B（宽度）**。
- C 是**热更必现的正确性火**（use-after-free + 旧 map 泄漏）。
- A/B 是**潜伏雷**（需 localloc+Ovf / 大帧才触发），但修的成本低、预防价值高。
- 全部不做的兜底：只要**不启用 localloc deopt 场景 + 不做热更**，A/B/C 都不触发——但这两个能力（定位功能 + 热更）都是产品刚需，故实质是"迟早要修"。

## 1. 现状（已实证，源码定位）

### 1a. deopt spill offset（3 处不一致的基址）
| 位置 | 表达式 | 基址假设 |
|---|---|---|
| `DeoptValue.spill_offset` | `GprOff(vr)` = `kGprFileOff(32) + vr*8`（jit_engine:1171）；`FprOff(vr)` = `kFprFileOff(544) + ...`(:1179) | **frame-base 相对**（prologue 时 RSP） |
| `ReadSpillSlot(codegen_rsp, spill_offset)` | `codegen_rsp + spill_offset`（jit_deopt.cpp:20-22） | **deopt 时 RSP** |
| `DeoptTrap` 批量读 | `codegen_rsp + 32 + vr*8`(GPR,:108-112)；`codegen_rsp + 544 + vr*8`(FPR,:116-118) | **假设 codegen_rsp == frame base** |

- `codegen_rsp` = deopt trap 时 `RCX = RSP`（jit_engine:1194 `EmitMovRR(kScratchB, kStackReg)`），即**trap 时当前 SP**。
- **冲突**：trap 点 RSP ≠ frame base 时（localloc 动态扩帧 / 参数设置 shadow space / 中途 helper 调用），`ReadSpillSlot(base_relative_spill_offset, current_rsp)` 会错位。三个基址假设不统一。

### 1b. offset 宽度
- `DeoptValue.spill_offset` 是 `int16_t`（`jit_method.h:84`，signed 16-bit ±32767）。
- 配合 `frame_size_extra_`（tree vregs 扩帧，jit_engine:4681/4704）时，高位 vreg 的 GprOff/FprOff 可逼近/超出 16-bit 范围 → **截断/溢出风险**。且 T2.2 把 GC slot offset 扩到 31-bit，两者不对称。

### 1c. 热更重编译 GC map 生命周期
- **热更升级/promotion 重编译**（entry_direct.cpp:436-448）：`old_nm` 的 `GcUnregisterSlotMap(old_nm->code)` 被调用（:442-444）→ 新 map 注册（:445-448）。✅ 处理了。
- **热更 demotion**（jit_seh_handler_internal.cpp `DemoteJittedMethod` :228-250 / `DemoteT4ByCallSiteToken` :254-280）：只 `entry.nm=nullptr` + `EnqueueDemotedCode`，**未 `GcUnregisterSlotMap(old_code)`**。❌ 旧 map 残留。
- **新旧共存**：demotion 重编译后，旧代码栈帧可能仍存活（线程正在旧代码上），GC 需用旧 map 扫旧帧；新代码用新 map。registry 按 `code_address` 为键（gc_root_scanner.cpp:27），只要旧地址有效就天然按地址分发——但 demotion 没保证旧代码在旧帧耗尽前不被回收/地址不被复用。

### 1d. T2.2 引入的新 map
- `GcPointMapV0`（per-safepoint 精确，T2.2 新增）同样经 `nm->gc_point_map_data` 注册/释放；entry_direct 的 demotion 也未处理它 → 需一并纳入热更生命周期。

## 2. CoreCLR 对齐语义（source-grounded，见 T2.2 调研 §2f/§2g）

- **GCInfo 栈槽基址是显式的多 base**：`GC_SP_REL` / `GC_FRAMEREG_REL` / `GC_CALLER_SP_REL`，每个 slot 显式声明相对谁，运行时 `GetRegisterSlot`/`GET_CALLER_SP` 解出真实地址。**不存在"隐式假设 SP==base"**——这正是 Chaos 当前缺的"单一权威 anchor"。
- **slot 去重 + 单一权威**：`StackSlotIdKey`（offset+base+kind）去重，一个 (base,offset) 只编码一次；deopt 与 GC 扫描用同一套 slot 描述 → **单一权威 offset 语义**。
- **热更/重编译**：CoreCLR `ReJitManager` 的 code version → GC mapping 天然按 `return_address` 版本分派；旧版本代码在旧帧耗尽前保留其 GCInfo；新版本注册新 GCInfo。旧版本在无引用后回收并在 GCInfo 表中移除。

## 3. 对齐差距 → 任务清单（按依赖/风险）

### T2.3-A（🔴 核心，最低风险）：deopt spill offset 基址单一权威化
- **问题**：base-relative `spill_offset` + deopt-time `RSP` 双重假设，localloc/参数设置时错位。
- **工作**：
  - A1 定义**单一权威基址**：所有 spill/deopt offset 统一为 **frame base（prologue RSP，即 `frame_ptr`）** 相对。deopt trap 用 `frame_ptr`（或等价的 `RSP_frame_base`）而非 trap 时 RSP。
  - A2 `DeoptTrap` 批量读改为用 `frame_ptr + GprOff`/`FprOff`（与 `DeoptValue.spill_offset` 同基），删掉硬编码 `32/544`。
  - A3 若 trap 点 RSP 与 frame base 差 `delta`（localloc/arg），emit 时在 trap 前用 `lea` 恢复 `frame_base`（`frame_ptr`）传给 `codegen_rsp`；或 deopt trap 从 `rbp`(frame reg) 得 frame base（对 frame-pointer-omitted 需 prologue 记 rbp/rsp delta）。
- **验收**：一个带 localloc 或变参 shadow space 的方法 deopt 后 register file 重建正确（新增单测）。

### T2.3-B（🟡 中风险）：offset 宽度对齐（去掉 int16 截断）
- **问题**：`int16_t spill_offset` 受限；frame_size_extra_ 高位 vreg 溢出。
- **工作**：B1 `spill_offset` 升 `int32_t`（schema 改 `jit_method.h`）；B2 与 T2.2 的 31-bit GC slot offset 对称。依赖 A 定基（基址 + 32-bit offset 才无歧义）。
- **验收**：构造高 vreg（frame 超 32KB）deopt，offset 不截断。

### T2.3-C（🟡 中风险）：热更 demotion GC map 生命周期 + 新旧共存一致
- **问题**：demotion 未 `GcUnregisterSlotMap` 旧 map + 未处理 `GcPointMapV0`；新旧共存无回归测试。
- **工作**：
  - C1 `DemoteJittedMethod`/`DemoteT4ByCallSiteToken` 在 enqueue 旧代码时对旧地址 `GcUnregisterSlotMap` + 移除 `GcPointMapV0`（引入 `GcUnregisterGcPointMap`/统一 `GcUnregisterRootMaps(code)` 打包两个 map）。
  - C2 **新旧共存**：demotion 时旧地址在旧帧耗尽前**不得被回收/地址复用**——enqueue code 的回收机制(EnqueueDemotedCode)需等到"无线程返回旧地址"（或用版本化/延迟回收）；新增回归测试：重编译后旧帧仍用旧 map 扫、新帧用新 map 扫。
  - C3 与 T2.2 联动：`~JitMethod`/release 路径统一 unregister GcSlotMapV0 + GcPointMapV0（jit_engine:5459 已 unregister slot_map，需加 point_map）。
- **验收**：热更重编译（`DemoteJittedMethod`→重跑 T4）后，注册表只有当前活的新 map；旧地址在旧帧存活期间仍可扫到正确旧 map。

### T2.3-D（可选）：权威契约文档 + 契约断言
- D1 在 wiki/IN 或契约头固化"frame-base 相对 offset + 单一基址"约定。
- D2 `static_assert` 或校验：spill_offset 与 GC slot offset 同为 frame_base 相对。

## 5. 一句话结论
- **要做什么**：把 deopt spill offset 从"三处不同的 RSP/基址假设"统一为**单一权威 = frame base（frame_ptr）相对**（对齐 CoreCLR 的显式 `SP_REL/FRAMEREG_REL` 多 base + `StackSlotIdKey` 单一去重）；修复热更 demotion 不注销旧 GC map 的泄漏 + 归一化注册/释放（含 T2.2 的 `GcPointMapV0`），确保重编译后旧帧用旧 map、新帧用新 map 的新旧共存一致。
- **对齐什么**：CoreCLR GCInfo 的**显式 slot 基址** + **ReJitManager 按代码版本分派 GC-info**（registry 已按 code_address 键=天然版本化，只差 demotion 生命周期闭环）。

## 6. 方案设计（T2.3-C 热更生命周期修复，多方案对比）

> **机制前提（已实证）**：
> - `ReclaimDemoted()` 在**每次 GC safepoint**（WinSehHandler:361 `OnGcSafepoint`）无静默检查地 `VirtualFree` 旧代码 → 若线程停在旧代码内的 cooperative safepoint（栈返回地址/存活寄存器指向旧 region）→ **UAF**。
> - demotion 把 `entry.nm/entry.code_start` 置 nullptr（移除出 `g_t4_code_entries`）→ `FindNativeCodeByAddress(old_ret)` 返回 nullptr → GC **跳过旧帧**：旧帧**栈槽**被 Phase1 保守全栈扫兜底，但**存活在寄存器的 ref**（线程停在旧代码内）**不会被保守栈扫抓到 → 真漏根 → GC 搬移时堆破坏**。
> - 完整机制：STW GC（generation odd）= 所有线程停在其 safepoint（栈可读），**不保证"无线程停在旧代码内"**。
> - `s_slot_map`（GcSlotMapV0/GcPointMapV0 registry）按 code_address 键；demotion 从不 `GcUnregisterSlotMap` → 泄漏 + 地址回收复用误配。

### 方案 1 — 延迟回收 + 保守永不复用（推荐起点，正确性优先）
**做法**：
1. demotion 时**保留** old `g_t4_code_entries` 条目与 old `s_slot_map`（旧帧仍可被 `FindNativeCodeByAddress` + `GcLookupSlotMap` 精确定位 → 旧帧根不漏、栈槽+寄存器都按旧 map 扫）。
2. **不立即 free** 旧代码；`ReclaimDemoted` 改为**只在真正无旧帧引用时回收**：在每个 STW GC 扫描后检查"本次全线程栈扫描是否还有返回地址落在待回收旧 region"——若没有才 `VirtualFree` + `GcUnregisterRootMaps(old_code)`；有则继续保留到下个 GC。
3. 新增 `GcUnregisterRootMaps(code)` = 同时 `GcUnregisterSlotMap` + 移除 `GcPointMapV0`（一次性归一化）。
4. 旧代码地址**永不主动复用**（新代码另外分配），消除"地址回收→误配旧 map"。
- **优点**：正确性闭环直接（旧帧全程 rootable，等零引用才回收）；改动集中（demotion + reclaim + 一个 unregister 函数）；无并发 epoch 同步。**兼容当前 registry 按地址分派**，最贴近 CoreCLR"旧版本无引用才回收"。
- **缺点**：旧代码/旧 map 在新旧切换期间滞留（跨多版本热更时按版本累积内存，需「版本数上限或按需强制回收」兜底）。
- **估时**：0.5-1d。

### 方案 2 — 每线程 JIT epoch（CoreCLR ReJitManager 化，更激进）
**做法**：
1. 每个 ManagedThread 加 `jit_epoch`（单调递增）；进入/离开 jitted code 时更新（或 safepoint 时记录当前 hot-update generation）。
2. demotion → 全局 `hot_update_seq++`；旧代码**延迟**到「所有线程的 `jit_epoch >= 该次 demotion seq`」才回收——此时没有任何线程还在执行该旧版本代码。
3. 用 epoch 判定替代"扫栈找 old ret"：更精准、O(1) 判定，且天然支持多版本累积回收。
- **优点**：O(1) 判定可回收；精确到"无线程在旧代码"而非"扫栈碰巧没扫到"。
- **缺点**：需为 `jit_epoch` 在入口/出口/热更切换处埋点（侵入 emit/entry/hotpatch 多个点，正确性风险高）；epoch 判定要证明线程"已离开旧代码"的充分性（safepoint 时记录的 epoch 是否保证不再执行旧代码，需仔细论证）。
- **估时**：1.5-2.5d。

### 方案 3 — 永不主动回收 demoted 旧代码（最简，内存换安全）
**做法**：demotion 后旧代码**进一个 session 级 arena/leak 列表，本进程生命期不 free**；旧 map 保持注册；地址不复用。只有进程退出才回收。
- **优点**：实现几乎为零（demotion 已有 pending_free_ 记录，只是不 VirtualFree）；彻底消除 UAF + 漏根 + 复用误配（因为**从不 free、从不复用**）。
- **缺点**：**每次热更泄漏整份旧代码 + map，进程内单调增长**——热更频繁（游戏/线上）时内存失控到可观测；不适合长期服务。**作为方案 1 的兜底回退**（当方案 1 的"零引用检测"暂不做时）。
- **估时**：0.25d。

### 方案 4（补丁，正交必需）— 旧帧被跳过时不漏寄存器根
无论选 1/2/3，都要**先修"跳过即漏"**：当 `FindNativeCodeByAddress(old_ret)` 返回 nullptr 但 `GcLookupSlotMap(old_ret)` 有旧 map 时，**旧帧仍应按旧 map 精确扫**（不 skip）+ 把旧代码视作"可能仍被引用"而不回收。方案 1 天然含此（保留 registry 条目）；方案 2/3 也需显式。
- **必做**，否则任何不保留 `g_t4_code_entries` 的方案都会漏寄存器根。

### 结论建议
**推荐方案 1 + 方案 4 作为第一步**：保留旧 registry 条目 + 延迟到零引用才回收 + `GcUnregisterRootMaps` 归一化 + 新增"旧帧不跳过、旧 map 仍可查"。正确性优先、改动集中、兼容当前架构；**方案 3 作为中间临时回退**（若零引用检测分析太久）；**方案 2（epoch）作为后续性能优化**（多版本高频热更时）。

> **✅ 已落地（2026-08-10, commit `09898baae`）：方案 3（永不回收 demoted JIT 代码）**，作为当前热更生命周期的安全基础。
> - `ReclaimDemoted`/`ReclaimDemotedCode` no-op（不 free）；`UnregisterCode`/`DemoteJittedMethod`/`DemoteT4ByCallSiteToken` 保留 entry + code，只置 `code_managed_externally`。
> - 效果：修 UAF（旧代码不 freed）+ 修漏根（旧帧经保留 entry 仍可精扫）。dispatch 用 `direct_ptr`，registry 只服务 GC/SEH。
> - 验证：jit_seh_handler_test 38/38、test_jit_native 69/69、jit ctest 15/15。
> - **成本（方案3 固有）**：旧代码 + 旧 map 随热更次数单调累积。后续回收升级方案1/2。T2.3-A（deopt 单一基址）、B（int32 宽度）、D（契约文档）未做。
