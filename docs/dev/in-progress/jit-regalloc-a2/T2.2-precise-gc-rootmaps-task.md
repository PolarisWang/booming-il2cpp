# T2.2 精确 GC slot maps — 对齐任务展开（调研版）

> **状态**：调研完成（2026-08-10）｜ **上游**：T2.1 A1 已完结（caller write-through 消除）｜ **目标**：对齐 CoreCLR 精确 GC 根扫描
> **核心结论**：当前 Chaos 的 GC 扫描用的是 **per-method 保守 union 栈图（GcSlotMapV0，仅栈、无寄存器、12-bit）**；per-safepoint 精确数据（`gc_points_` + liveness `live_in_`）**已计算但未被 GC 扫描端消费**（死代码），寄存器根**完全未接入**（`GcSlotKind::Gpr` 枚举存在但从不 populate）。T2.2 就是把这个精确路径打通 + 补寄存器窗。

## 1. 现状（已实证，源码定位）

### 1a. 数据结构
| 符号 | 位置 | 含义 |
|---|---|---|
| `GcSlotMapV0` | `contracts/native/v0/codegen_bridge.h:191` | 每方法 1 个：`[frame_size][num_gc_slots][slots[]]`，slot=`12bit offset \| 1bit kind(OBJECT/INTERIOR)` |
| `CHAOS_GC_SLOT_OFFSET_MASK=0xFFF` | 同上 :181 | **offset 限 4095（12-bit）**；`static_assert(kFrameSize<=4096)` jit_engine:97 |
| `GcPoint` / `GcSlot` / `GcSlotKind{Gpr,Stack}` | `src/native/jit/jit_method.h:51-68` | 每 safepoint 的精确槽描述；**`Gpr` 枚举已定义但从不写入** |
| `live_in_` | jit_engine:252 / :4710 | 反向数据流 liveness，`uint64_t` 掩码，**仅 vreg<64（GPR）** |
| `slot_map_entries_` | jit_engine:246 | GcSlotMapV0 的 `slots[]` 来源 = **union**（所有 safepoint 合并） |

### 1b. 生成路径
- `RecordGcPoint`(jit_engine:595)：每 call/safepoint → 用 `live_in_[current_instr_index_]` 过滤 live ObjectRef vreg → `gc_points_[i]`（per-safepoint 精确栈槽 GPR 文件）+ 同时 append 到 `slot_map_entries_`（union 序列化目标）。**只 `GcSlotKind::Stack`，从不 `Gpr`。**
- 序列化(jit_engine:5342)：`slot_map_entries_` → `GcSlotMapV0`，存 `nm->slot_map_data`。

### 1c. 运行时扫描
- `GcLookupSlotMap(return_address)`(gc_root_scanner.cpp:53) → 整方法 1 个 map。
- `GcScanPreciseFrame`(gc_root_scanner.cpp:110)：`for slot map 全部槽 → frame_base+offset`，**只扫栈 offset，无寄存器窗重建**。
- `GcScanFrameHybrid`(gc_root_scanner.cpp:157)：有注册 map → precise；否则 conservative 全帧扫描。
- 注册源：`bootstrap.cpp:320`(section) + `entry_direct.cpp:446/507` + `jit_precode.cpp:449`。

### 1d. 关键死代码
- `nm->gc_points_` / `gc_point_count` **无任何 GC 扫描端读取**（grep 实证：只 jit_engine 写，runtime-core/hot-update 无人读）。即 liveness 精确结果目前对实际 GC **无效**——扫描用的是保守 union map。

### 1e. 测试现状（验收缺口）
- `jit_gc_slot_map_test` 只测 **API 机制**（register/lookup/unregister/hybrid 扫描），都是手造 stub map；**不测**：多 safepoint 同方法不同 liveness、寄存器根、真实 `JitMethod` 生成路径。

## 2. CoreCLR 对照（source-grounded，已由研究 agent 核实于 dotnet/runtime main）

### 2a. 每次扫描粒度
- **每方法 1 个 GC info 流（`GcInfoToken`）+ 流内 per-safepoint 精度**（非每方法 union）。单 blob = delta 压缩状态机，描述寄存器/栈槽 liveness 随 code offset 变化。
- 查表：`GcInfoDecoder(token, flags, breakOffset)` → `FindSafePoint`（定宽 numSafePoints 表二分/线性）→ 精确到该 return address 的 safepoint 状态。而非整方法 union。

### 2b. 栈槽
- `GcStackSlot{INT32 SpOffset; GcStackSlotBase Base}`；`StackSlotIdKey` = `(offset+base+interior)` 去重哈希 → 同槽只录一次。
- 三种 base：`GC_SP_REL`(当前SP) / `GC_FRAMEREG_REL`(帧寄存器) / `GC_CALLER_SP_REL`(entry SP)——因同一方法可能要 SP 锚(scratch/outgoing) + 帧寄存器锚(locals)。
- `SetSlotState(slotId, lifetimeStart/End)` 精确 live range；dead→dead 区间不发射；槽被非GC覆盖则 `SetSlotState` 终止其 lifetime → 后续 safepoint 移除。

### 2c. 寄存器（per-safepoint）
- **仅 volatile(caller-saved) 寄存器进 per-safepoint 掩码**。每 interruptible 点带 live-register bitmask（gcref + 并行 byref 掩码 `gcRegGCrefSetCur`/`gcRegByrefSetCur`）。
- 掩码 = 该 offset 的位级 live 状态；`ReportRegisterToGC` + `IsScratchRegister` 判活/死。
- **callee-saved 寄存器刻意不进 per-safepoint map**——它们在 prolog 保存于帧(frame image)，运行时经 unwind 的**寄存器窗重建**读回，视为根。

### 2d. 精确 vs 保守
- `GC_SLOT_TRACKED` = liveness 精确已知（`lclvar` live range → `SetSlotState` 精确区间）。
- `GC_SLOT_UNTRACKED`(0x4) = 全方法保守（address-exposed 变量、一些 this/params、PSPSym/GS-cookie 等），不经数据流。
- 回退到 untracked：address-exposed(`lvaSetVarAddrExposed`) 或部分可中断(return-only)方法。

### 2e. 内部/byref
- `GC_SLOT_INTERIOR`(0x1) 标记 byref（指进对象内部），`GC_SLOT_PINNED`(0x2) 抑制搬移。编码与 gcref 同（同 slot id/base/offset），仅 flag 位 + 并行 interior 掩码。

### 2f. 寄存器窗基线
- PC→SP/帧指针：GC stop 取 return address → per-module `RUNTIME_FUNCTION` → `UNWIND_INFO` 回溯到合法 SP/帧指针（prolog 仅：push/set-frame/alloc）。
- callee-saved 窗：encoder 记录 prolog 保存哪些 reg；decoder 用 `GetRegisterSlot`(FRAMEREG_SP_REL) 或 `GetCapturedRegister` 从帧读回 → 恢复不在 per-safepoint 掩码里的 callee-saved 根值。

### 2g. 最小精确 GC map 必须含（CoreCLR 对齐清单）
1. per-method blob + slim/fat header（size/codeLength/interruptibleRangeCount/numSafePoints/prologSize/stackBaseReg）。
2. slot 描述表（`GcSlotDesc`：register number 或 stack slot，带 INTERIOR/PINNED/UNTRACKED flag，`StackSlotIdKey` 去重）。
3. tracked/untracked 拆分。
4. **per-safepoint 精度数据（crux）**：volatile-reg liveness mask（每 reg gcref+byref）+ 该 offset 的 live 栈槽状态（signed delta 前一个 safepoint）+ interior flag。
5. **callee-saved 窗**：不在 map 内——靠 prolog 保存布局 + 帧基关系，unwind 运行时重建。
6. 归一化 offset + delta 编码 + `FindSafePoint` 二分，支持按返回地址点查。
7. 运行时 decode：`GcInfoDecoder(token,flags,breakOffset)` → per-safepoint 输出 (slot reg | stack base+offset, interior/pinned/tracked) → `ReportStackSlotToGC`/`ReportRegisterToGC`。

## 3. 对齐差距 → 任务清单（按依赖顺序）

### 差距 A（最前置、最大收益）：精确路径打通 — per-safepoint 精确而非 union
- **现状**：扫描用 union `GcSlotMapV0`；per-safepoint `gc_points_`（已带 live 过滤）未被消费。
- **工作**：
  - A1 运行时扫描端改读 per-safepoint 精确槽（新增按 `return_address→所属 safepoint→live 槽集` 的查找），淘汰对 union 的依赖。需 `GcLookupSlotMap` 升级为按 (code, offset) 定位到精确点。
  - A2 现有 `gc_points_` 已具 per-safepoint 栈槽（栈路径已较完备），**把它接进 scan**（现在死代码）。verify：B1 精确扫描"只扫该点存活引用"。
- **风险**：GcPoint 目前栈槽是 frame-relative offset；需确认 scan 端 frame_ptr 对齐（已实证 thread_state.cpp:675 一致）。
- **验收**：`jit_gc_slot_map_test` 增加"同一方法两个 safepoint，不同 live 集，精确只扫各自存活"用例。

### 差距 B（核心新增）：寄存器根扫描 + 寄存器窗
- **现状**：`GcSlotKind::Gpr` 枚举在，但 `RecordGcPoint` 从不 populate Gpr；无 volatile-reg 掩码；无 callee-saved 帧窗重建。
- **工作**：
  - B1 `RecordGcPoint` 增加 **volatile(caller-saved) live GPR 掩码**：该点哪些物理寄存器（R8-R11/RDI on Win）持 gcref。T2.1 的 `caller_colored_mask_` + `vreg_types_` + liveness 可给出。GcPoint 加 `reg_mask` 字段。
  - B2 `ManagedFrameInfo` 提供 CPU 寄存器上下文（GC 入口需捕获 caller 的 volatile regs——通常在 thread_state/GC 入口有 CONTEXT；若是 sigreturn/软栈，需 `GcCaptureRegisters`）。
  - B3 callee-saved 窗重建：GC 用 prolog 保存布局（`callee_gpr_regs_` + prologue push 顺序/offset）从帧读回 callee-saved 根值。需在 GcSlotMap 或 unwind 旁存"callee-saved 保存位置表"。
  - B4 GcPoint 增加 interior/byref 并行掩码（若需支持 byref 根）。
- **验收**：`jit_gc_slot_map_test` 覆盖"精确扫描只扫存活引用（含寄存器根）"；一个跨调用保持 gcref 在 callee-saved reg 的用例。

### 差距 C：编码/寻址对齐（消 12-bit 上限 + 多 base）
- **现状**：12-bit offset(4096) + 单 base(frame_ptr-rel)。
- **工作**：
  - C1 槽 offset 扩到 INT32（或至少去 4096 上限）；低风险：`CHAOS_GC_SLOT_OFFSET_MASK` 从 12-bit 扩到 32-bit（改枚举 + 序列化 + decode）。
  - C2（可选）引入 SP_REL/FRAMEREG_REL/CALLER_SP_REL 多 base + `StackSlotIdKey` 去重——在 A1 打通后可延后，非阻塞。
- **风险**：`static_assert(kFrameSize<=4096)` 需评估放开后 frame 布局是否仍与 `GprOff`/deopt offset 一致（§2.3 契约耦合）。
- **验收**：>4KB 帧或更高 slot 编码不丢。

### 差距 D：精确 vs 保守（untracked 等价）— 可选优化
- **现状**：无 tracked/untracked 概念，union=最保守。
- **工作**：add-exposed/locals 用 whole-method 保守槽（untracked 等价），其余 per-safepoint 精确。在 A1 精确扫描稳定后可做，收益=减少无谓 over-retention。
- **验收**：GC 不"过度保留"——仅存活性覆盖的引用被扫。

### 差距 E：偏移/去重对齐（延后，非阻塞）— 归入 C2 或 §2.3 deopt 契约一起做

## 5. 一句话结论
- **要做什么**：把已经算出来的 per-safepoint 精确栈槽（`gc_points_`+liveness）真正接入 GC 扫描，补上寄存器根（volatile 掩码 + callee-saved 窗重建 + CPU 上下文），并扩 offset 编码/去重对齐 CoreCLR 的 `GcInfo`。
- **对齐什么**：CoreCLR 的 `GcInfoEncoder`/`GcInfoDecoder` 的 per-safepoint 精度数据模型（volatile-reg mask + live 栈槽 + interior/tracked flag + SP/FRAMEREG 双 base + `StackSlotIdKey` 去重 + unwind 窗重建）——但**不必照搬 delta 编码**，可用等价的显式 per-safepoint 槽表（当前 `gc_points_` 已是显式结构），只要语义对齐：**按返回地址精确到点、补寄存器根、支持 interior**。
