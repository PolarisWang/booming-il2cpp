## 二、测试完善度审查

### 现状（基本良好）
| 维度 | 数据 |

| 每模块验证 | 全绿：test_jit_native 69 + gc_slot_map 16 + simd 8 + osr... + jit ctest 15/15 |

**强项**：拆分主要通过 **黑盒集成测试**（Compile→Execute 真生成代码）验证，**每个模块的生成代码都被实际执行到**，这是纯移动重构最强的回归护栏——15/15+69/69 说明 8 模块语义保持。

### 覆盖缺口（建议补）
| 缺口 | 风险 | 建议 |
|---|---|---|
| **无模块级单元测试**（直接调 RecordGcPoint/EmitSafepointPoll/EmitInstruction 等） | 拆分只靠黑盒；若某模块逻辑后续单改，需跑整套才回归 | 可选：为 emit/gc 最复杂方法补聚焦单测（但纯移动下收益低，可缓） |
| **ARM64 构建路径未测** | 本次 review 就抓到 ARM64 编译漏符号——说明 ARM64 是盲区 | 优先：CI 加 ARM64 交叉编译或至少一个 ARM64 构建目标试跑 |
| **无覆盖率工具（gcov/llvm-cov）** | 无法量化哪些行/分支未被测试 | 引入 gcov 统计 jit 各模块覆盖率，作为回归基准 |
| **无拆分回归哨兵**（验证 8 模块文件各自独立编译+无 ODR）| 未来再拆/改模块时可能重蹈 ARM64 漏符号 | 可选：加一个"每模块可单独 TU 编译"的脚本/检查 |

### 结论
- **测试主体充分**：黑盒集成覆盖 8 模块的生成代码正确性，纯移动语义保持有强护栏。
- **真正缺口 = ARM64 + 覆盖率量化**——都不是拆分引入的，但拆分把 ARM64 跨 TU 漏符号暴露了（已修+commit）。ARM64 是当前测试盲区，建议 CI 补 ARM64 构建；覆盖率工具可引入以量化。
