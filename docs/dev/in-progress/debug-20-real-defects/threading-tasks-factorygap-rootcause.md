# threading-tasks factoryGap 根因 — Create<T> 是 stub_definition 而非真工厂

> **日期**: 2026-09-18
> **上游**: `THREAD-NEXT-2026-09-18.md` P1「T4 ContinueWith 40 红」
> **结论**: T4 的工作量与 roadmap 预估**不符** —— ContinueWith 本身不是缺口

## 一、推翻的前提

`THREAD-NEXT-2026-09-18.md` 判断：

> **P1 — T4 ContinueWith（40 红，最大单块）**
> - **无需新 native 入口**（roadmap 原话：「已有混沌设备」）
> - 是**纯接线批次** —— 性价比最高

**该判断不成立。** ContinueWith 的 shape **已经完整注册**，见下。

## 二、实测：ContinueWith shape 早已存在

`RuntimeHelperShapeRegistry.CoreStubs.Part1.S16.cs:467-540` 有完整的
`RegisterGeneric(GenericShapeDescriptor(TypeDisplayNamePrefix: "System.Threading.Tasks.Task",
MethodName: "ContinueWith", Resolver: ...))`，且：

- 已处理 backtick 与尖括号**两种泛型拼写**（`IsAnyContinuationDelegate`，
  Part1.cs:139-160 的 remarks 明确记录了这个坑）
- 有 `paramTypes.Count != 1` 的 arity 守卫，拒绝 CT / options / scheduler / object-state 重载
- 路由到 `chaos_task_continue_with`

**但 capa manifest 里 `Continue entries = 0`**（threading-tasks 与 threading 两个 chunk 都是）。
这不矛盾 —— 因为记录**根本没执行到 ContinueWith**。

## 三、真根因：factoryGap 发生在 ContinueWith **调用之前**

40 个 ContinueWith 记录**全部**是 `factoryGap`。生成的测试体
（`.autogen/System_Threading_Tasks_Task/Task.AutoGenerated.cs:452`）：

```csharp
SubjectInstanceFactory.Create<System.Threading.Tasks.Task>()
    .ContinueWith(default(System.Action<System.Threading.Tasks.Task>)!)
    .GetAwaiter().GetResult();
```

`factoryGap` 的定义（`fact_chunk.py:211-217`）：

> the test's `SubjectInstanceFactory.Create<T>()` returned **null** in AOT
> (its generic instantiation has no native stub), so the emitted null-guard
> raised NRE.  **The method under test never ran.**

即：**`Create<Task>()` 返回 null → NRE → ContinueWith 一行都没执行。**

### 决定性证据

`native-aot.generated.cpp:64-78` 里 `Create<T>` 的每个实例化**只有声明没有定义**：

```cpp
extern "C" CHAOS_IL2CPP_INTPTR
  Chaos_TestFramework_Sdk_..._SubjectInstanceFactory_Create_System_Threading_Tasks_Task__generic(void);
extern "C" CHAOS_IL2CPP_INTPTR
  chaos_stub_definition_..._SubjectInstanceFactory__Create_1___0___type____method__System_Threading_Tasks_Task(
      CHAOS_IL2CPP_INTPTR chaos_generic_context);
```

全仓 grep `chaos_stub_definition_...SubjectInstanceFactory` **在 src/ 下 0 命中** ——
没有任何 native 实现提供这个符号。它就是"没有 native stub"的具象。

### 决定性对照（排除替代解释）

同一 chunk、同一 `Task` 类型下，**唯一变量是测试体是否经由 `Create<T>()`**：

| 生成体形态 | 例 | resultKind |
|---|---|---|
| **静态调用**，无工厂 | `Task.WaitAll(default(Task[]), default(TimeSpan))` | ✅ **real** |
| | `Task.Yield()` | ✅ **real** |
| **实例调用**，经工厂 | `SubjectInstanceFactory.Create<Task>().ContinueWith(...)` | ❌ **factoryGap**（40/40） |

证据：`Task.AutoGenerated.cs:1138`（WaitAll，静态）vs `:452`（ContinueWith，工厂）。

**这排除了**「Task 类型整体无 AOT 支持」「ContinueWith shape 缺失」等替代解释 ——
TaskTests 里有 16 个 `real`，全是静态调用形态。

## 四、这属于哪条线

**属于 `generic-instantiation-materialization` 的 L2 缺口**（跨程序集目标程序集未加载），
**不属于 T4**。

`SubjectInstanceFactory` 定义在 `Chaos.TestFramework.Sdk`（跨程序集），
`Create<Task>` 是**泛型方法实例化**，demand 指向 `Chaos.TestFramework.Sdk` —— 与
`generic-instantiation-materialization/STATUS.md` 记录的
「27 条 demand 全部 isCrossAssembly:true 指向未加载程序集」同构。

**因此：修 T4 之前必须先修 L2，否则 ContinueWith 永远跑不到。**

## 六、threading 20 failed 的同类发现

`threading` chunk 的 20 个 `failed` 也是 **`assertFailed:False, caught:True`**（抛异常，非断言失败）。
其中 ThreadPool 那 4 个（`GetMaxThreads`/`SetMinThreads`/`GetMinThreads`/`GetAvailableThreads`）
在 `managed_primitive_entries.h:236-240` 有**明确书面决定不接线**：

> `GetAvailableThreads`/`GetMaxThreads`/`GetMinThreads` have **NO native counterpart today**
> (the pool has no max/min configuration surface), so they are **deliberately NOT claimed here**
> — registering them against a placeholder would reproduce exactly the fake-pass this phase removes.

**即这 4 项是诚实的能力边界，不是缺陷。** 修它们需要先给 native pool 加 min/max 配置面，
不是接线工作。

          — assemblyDirs 对所有 chunk 静默失效
