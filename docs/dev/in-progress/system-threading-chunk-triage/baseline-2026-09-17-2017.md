## 二、WaitAll 根因（⚠️ 本节结论已被第四节推翻，保留作排查过程记录）

> **勿引用本节的「参数被静默丢弃」结论。** 它无法解释「同为 2 参的
> `WaitAll_40(Task[],int)` 却通过」，也解释不了「同 shape 的 `WaitAny` 全绿」。
> 最终根因见**第四节**：实参不是被丢弃，而是**错位后被当作数组句柄解引用**。

### 当时收集的证据链（仍然有效，只是解读错了）

1. **callee 有 2 个托管参数**（`aot-core-ir.json`，WaitAll_39 的 `call` 指令）：
   ```
   callee: "System.Threading.Tasks.Task::WaitAll:System.Boolean(System.Threading.Tasks.Task[],System.TimeSpan)"
   ```

2. **消费方 IR 却声明零参数**（同文件 method 条目）：
   ```
   parameterAbis: []
   ```

3. **生成物 shim 只有一个槽位，只透传第一个实参**
   （`native/codegen/generated/native-aot.page-0009.cpp:1997`）：
   ```cpp
   extern "C" CHAOS_IL2CPP_INT64
   ..._WaitAll_39_Task_System_TimeSpan_0(CHAOS_IL2CPP_INTPTR chaos_fn_arg_0)
   {
       CHAOS_IL2CPP_ARRAY(CHAOS_IL2CPP_INTPTR, 1) chaos_args{};   // ← 只有 1 个槽
       ...
       _s1 = reinterpret_cast<CHAOS_IL2CPP_INTPTR>(&chaos_locals[1]);   // ← TimeSpan 地址
       { const auto chaos_arg_0 = _s1;
         const auto chaos_result = chaos_task_wait_all(chaos_arg_0); }   // ← 实参错位
   ```

4. **native 签名确实只收数组**（`async_stubs.cpp:764`）：
   ```cpp
   CHAOS_IL2CPP_INT32 chaos_task_wait_all(CHAOS_IL2CPP_INTPTR tasks_handle) noexcept
   ```

5. **注册点按「首参是数组/IEnumerable」一刀切匹配全部重载**
   （`RuntimeHelperShapeRegistry.CoreStubs.Part1.S16.cs:1648-1700`），
   Resolver 无论重载一律渲染 `chaos_arg_0` 单槽：
   ```csharp
   // Every chunk overload takes Task[] as its FIRST parameter; ... the shim
   // carries exactly one slot — the array.  Matching on "first parameter is an
   // array" therefore covers all of them without enumerating each signature.
   ```
   —— 这段注释就是缺陷本身：**shim 槽数必须等于 callee 的 arity**，
   而不是「我们碰巧想转发的参数个数」。

### 相关性表（本节唯一站得住的部分）

| overload | AOT | 说明 |
|---|---|---|
| `WaitAll_38(Task[])` | PASS | 1 参，正好 1 槽 ✅ |
| `WaitAll_39(Task[], TimeSpan)` | **FAIL** | 第 2 操作数被当数组句柄 → AV ❌ |
| `WaitAll_40(Task[], int)` | PASS | 参数同样错位，但 `n==0` 时恰好返回 true（巧合） |
| `WaitAll_41(Task[], CancellationToken)` | PASS | 同上（巧合） |
| `WaitAll_42(Task[], int, CancellationToken)` | **FAIL** | 3 参 ❌ |

**当时误判为「参数丢弃」**，实际是「参数错位 + 误当数组句柄解引用」。
判别关键是 `WaitAny` 同 shape 全绿 —— 它 `return -1` 不解引用。

## 四、WaitAll/WaitAny 修复闭环（commit `fb9a42033`）

### 最终根因（第三版，前两版均被推翻）

| 版本 | 假设 | 推翻依据 |
|---|---|---|
| 1 | 超出的实参被**丢弃** | int 变体也丢参数却通过 —— 无法解释不对称 |
| 2 | shim arity 与 callee 不匹配 → 实参**错位** | 方向对，但没解释为何只有 TimeSpan 崩 |
| **3** | 单槽 shim + `DirectNativeSymbol` → **实参错位且被误当数组句柄** | ✅ 与全部观测一致 |

失败链：
```
WaitAll(Task[], TimeSpan)
  → shim 只声明 1 槽 → TimeSpan 留在求值栈
  → 生成体 _s1 = &chaos_locals[1]（TimeSpan 槽地址）当作 Task[] 传入
  → UnpackTaskArray 从 TimeSpan 读 length==0 → 返回 0
  → 走 false 分支 ChaosLoadInt64(0) → 空指针解引用 → AV
```

**为何只有 WaitAll 崩**：同 shape 下 `chaos_task_wait_any` 对空数组 `return -1`
**不解引用**，故 WaitAny 全绿 —— 掩盖了缺陷。这个「两个同注册重载、结果相反」
的不对称是最强判别信号。

**为何 int/CTS 变体通过**：参数同样被丢，但 `n==0` 时 WaitAll 恰返回 `true`
（.NET 对空数组返回 true 且 0 超时仍满足），与期望巧合一致。

### 修复

`Part1.S16.cs` T3 Resolver 由「首参是数组」改为 **`paramTypes.Count != 1`**，
只匹配单数组重载；超时/CTS 重载显式落 external-runtime fallback
（诚实可见未实现，而非貌似正确的错代码）。

### 实测（threading-tasks，504s）

| 指标 | 修复前 | **修复后** |
|---|---|---|
| AOT passed | 355/456 | **359/456** (+4) |
| AOT `caught`（异常） | 4 项 AV | **0** |
| 跨技术分歧 | 7 项 | **3 项** |

4 项 TimeSpan/CTS 变体全部 `passed=True caught=False kind=real`，AOT=JIT 一致。
残余 3 项分歧均为 `AOT=PASS / JIT=FAIL`（WhenAll_71、ValueTask AsTask/Preserve），
方向相反，属另一条线。

### 残留（未做，需多槽 shim + native 超时形参）

超时/CTS 重载现落 fallback，**语义未实现**。完整支持需要：
1. 按重载渲染多槽 shim（`paramTypes.Count` 个槽）
2. `chaos_task_wait_all/any` 增加 timeout 形参（今日仅收句柄）
