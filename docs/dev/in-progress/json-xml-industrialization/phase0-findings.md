# Phase 0 发现记录 — 度量基建

> 日期：2026-09-20

## 🔴 发现 1：现有 manifest 不是可信分母

`testing/foundation-dll/*/_dll/dll-method-manifest.json` 是既有 roadmap 指定的
「分母权威」（v1 roadmap §4 Phase 0 Resolved Decisions）。但实测发现：

| 事实 | 证据 |
|:-----|:-----|
| **manifest 不含 `System.Text.Json.JsonSerializer`** | `JsonSerializer` 是所有 JSON 序列化用例的核心入口，但 99 个 declaringType 里没有它 |
| fact 里有大量 `JsonSerializerTests` | text-json chunk 的 subject 含该前缀 |
| manifest 生成于 **2026-06-02** | 比本次基线早 3.5 个月 |
| `JsonSerializerOptions` 只有 1 个方法且非序列化入口 | `...JsonSerializerOptions::GetConverter:...` |

**结论**：用该 manifest 作分母会**系统性低估**工作量（遗漏核心 API）。

## 🔴 发现 2：fact 与 manifest 不在同一层，无法直接 join

```
manifest.methodSubjectId:  System.Text.Json/System.Text.Json.Utf8JsonWriter::WriteNull:System.Void(...)
                                ↑ 被测的 API 方法
fact.methodSubjectId:      CombinedSubjects/AutoGenerated.System_Text_Json.System_Text_Json_JsonDocumentTests::Dispose_0__0:System.Int64()
                                ↑ ATG 生成的测试方法
```

**直接 join 命中率 0%**。

### 可行的间接映射

测试方法命名有规律：

```
JsonDocumentTests::Parse_7_string_JsonDocumentOptions_0
      ↓              ↓    ↓
   测试类型      API 方法名  API 参数类型
```

按此正则提取 API 方法名后与 manifest 比对：**144/247 = 58.3% 命中**。
未命中的主要是 `Deserialize`（因 manifest 缺 `JsonSerializer`）。

**该映射有损**（参数类型编码不同：`System_ReadOnlyMemorybyte` vs
`System.ReadOnlyMemory<System.Byte>`），只能做**方法名级**匹配。

## 🔴 发现 3：fact 分类口径（已由并行调查确认）

来自 `fact_chunk.py`：

| 口径 | 含义 | 代码位置 |
|:-----|:-----|:---------|
| `passed` | **运行时原始 passed 之和，与 resultKind 无关** | :139 |
| `realVerified` | **仅 `resultKind=="real"`** | :1155, :1207 |
| `gatePassed/gateTotal` | 排除 {factoryGap, stubGap, nullArg, envSensitive} | :845-870 |

反向信息：`gatePassed` 曾有过吃 stubGap 的历史 bug（reflection chunk
`gateTotal=50 / gatePassed=440` = 880%），**已修**（:853-871 有注释记录）。
这解释了本日看到的 `text-json gatePassed=185/gateTotal=8` 异常快照 ——
那是**修复前**的陈旧数据。

## Phase 0 的修订结论

原计划「从 manifest 聚合建矩阵」**不成立**。需改为：

1. **分母来源待定** —— manifest 不完整，需评估：
   - (a) 用 ref-pack 反射枚举全量 API（`ApiSurfaceScanner` 路线）
   - (b) 以 **fact 的 subject 集**为分母（承认「已生成的测试对象」就是当前工作集）
   - (c) 两者交集 + 差集视图
2. **映射层必须显式建立**（测试方法 ↔ API 方法），且**标注为有损**
3. **分母口径要在报告中显式声明**，避免与 manifest 口径混淆

**这是一个需要用户拍板的 blocking question。**

## 🔴 发现 4：manifest 缺失的量化影响（决定性证据）

建立了可行的映射（见 §发现 2 修订），对 text-json chunk 的 247 个 subject 逐一映射后：

```
命中 manifest:      142  (57.5%)
未命中:            105  (42.5%)
  ├─ JsonSerializer    103   ← 42% 的测试对象指向它
  └─ JsonNamingPolicy    2
```

**manifest 缺 `JsonSerializer` 一个类型，就漏掉了 42% 的测试对象。**

这是「manifest 不是可信分母」的**量化证明**（非推测）。

### 映射实现（已验证可用）

```python
# 1. 匹配测试方法名
pat = re.compile(r'AutoGenerated\.(.*?)Tests::([A-Za-z_][A-Za-z0-9]*?)_(\d+)')
# 2. 类型名：下划线转点
typ = group(1).replace('_', '.')        # System_Text_Json.System_Text_Json_JsonDocument
# 3. 去掉重复的 assembly 段
parts = typ.split('.')
for k in range(len(parts)//2, 0, -1):
    if parts[:k] == parts[k:2*k]:
        parts = parts[:k] + parts[2*k:]; break
typ = '.'.join(parts)                    # System.Text.Json.JsonDocument
# 4. 与方法名组成 (declaringType, methodName) 二元组查 manifest
```

**特征**：`(declaringType, methodName)` 级匹配，**不含参数** ——
即「该类型的该方法有任何一个重载被覆盖」即算命中。**有意为之**：
参数级匹配不可行（见 §发现 2 的编码差异）。**因此矩阵是「方法名级」的
保守度量，报告中必须标注此局限。**

## 🔴 发现 5：现有 manifest 的数据源与公开表面不一致（根因）

用**同一个扫描器**（`Chaos.IL2CPP.Tools.DllManifest`）扫不同来源：

| 来源 | methods | 含 `JsonSerializer` | 含 internal 类型 |
|:-----|:-------:|:-------------------:|:----------------:|
| **现有 manifest**（仓库内） | **486** | ❌ | ✅（PooledByteBufferWriter/BitStack/MetadataDb...） |
| shared/Microsoft.NETCore.App/**8.0.11** | 312 | ✅ | ❌ |
| shared/Microsoft.NETCore.App/**9.0.0** | 327 | ✅ | ❌ |

**结论**：现有 manifest 扫的是**含 internal 的实现程序集**，而 shared DLL 是**公开表面**。
两者**都不是**干净的分母：

- 现有 manifest：含 internal（超出 public API 范围）+ **漏 JsonSerializer**（过滤规则误杀？）
- shared DLL：纯公开，但**不含 internal**（而本仓库的翻译范围可能包含部分 internal）

**因此「反射枚举全量」需要先明确：枚举哪个程序集、是否含 internal。**
这直接影响分母大小（312 / 327 / 486 / 其他）。

### 对 Phase 0 的影响

**分母口径仍未确定** —— 用户选了「反射枚举全量」，但**「全量」的定义待明确**：
- ref-pack（`Microsoft.NETCore.App.Ref`）→ 纯 public API 契约面
- shared runtime DLL → 运行时公开面（略多于 ref-pack）
- 现有 manifest 来源 → 含 internal

**建议**：以 **ref-pack 的 public API** 为分母（这是 .NET 生态标准的「公开面」定义），
并在报告中标注「不含 internal」。

## 🔴 发现 6：ref-pack 是干净的公开面（决策依据）

用同一扫描器扫 ref-pack 各版本：

| 来源 | methods | **types** | 含 `JsonSerializer` | 类型性质 |
|:-----|:-------:|:---------:|:-------------------:|:---------|
| 仓库现有 manifest | 486 | **99** | ❌ | 混大量 internal |
| ref-pack 8.0.11 | 312 | **17** | ✅ | 纯 public |
| ref-pack 9.0.0 | 327 | **19** | ✅ | 纯 public |
| ref-pack 10.0.6 | 342 | **19** | ✅ | 纯 public |

### ref-pack 10.0.6 的全部 19 个类型

```
System.Runtime.InteropServices.JsonMarshal
System.Text.Json.JsonDocument
System.Text.Json.JsonElement (+ArrayEnumerator/ObjectEnumerator)
System.Text.Json.JsonEncodedText
System.Text.Json.JsonException
System.Text.Json.JsonProperty
System.Text.Json.JsonSerializer          ← 仓库 manifest 缺的
System.Text.Json.JsonSerializerOptions
System.Text.Json.Nodes.JsonArray / JsonObject
System.Text.Json.Schema.JsonSchemaExporter
System.Text.Json.Serialization.JsonConverterAttribute
System.Text.Json.Serialization.JsonStringEnumConverter
System.Text.Json.Serialization.Metadata.DefaultJsonTypeInfoResolver
System.Text.Json.Serialization.Metadata.JsonTypeInfoResolver
System.Text.Json.Utf8JsonReader / Utf8JsonWriter
```

**全是业务方会用的公开类型**，无 internal。

### 对比：仓库 manifest 的 99 个类型含大量 internal

`ReadStack` / `WriteStack` / `WriteStackFrame` / `BitStack` /
`PooledByteBufferWriter` / `ArrayBuffer` / `JsonDocument+MetadataDb` /
`JsonSerializerOptions+CachingContext+CacheEntry` … ——
这些**不是 public API**，业务方无法调用。

### 结论：ref-pack 是唯一干净的公开面口径

**决定由用户做出**（本文件记录数据依据，不代用户拍板）。

**注意**：ref-pack 的 types 数少（19 vs 99）**不代表 API 少** ——
486 vs 342 的差异主要是 **manifest 含 internal + 扫描器把 nested/compiler-generated
类型也算进去了**。ref-pack 的 342 是**纯公开方法**。

## 🔴 发现 7：一个必须注意的反常

ref-pack 的 `types` 只有 17-19 个，而 methods 有 312-342 个 ——
**平均每类型 18 个方法**，分布高度集中（`Utf8JsonWriter` 一个类型就有 ~100 个重载）。

**这意味着**：分母的**类型数少但方法数多**，所以「按类型算覆盖率」会产生
严重误导（覆盖 1 个类型可能 = 覆盖 30% 的方法）。

**报告中必须用「方法级」覆盖率，且对重载多的类型（Utf8JsonWriter/Utf8JsonReader）
单独标注。**
