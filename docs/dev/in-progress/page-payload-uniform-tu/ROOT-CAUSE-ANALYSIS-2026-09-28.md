# 深度分析 — 为什么"每 TU ≤ 350K"总也达不成，以及根本解

> task_id: `page-payload-uniform-tu`
> 创建：2026-09-28
> 性质：**根因分析 + 方案对比**（不实现）
> 触发：用户要求「几个方案和深度分析，如何才能从根本上解决这个问题」

## 一、先把问题说准

### 1.1 现状实测（system chunk，System.Private.Xml/xml）

| 指标 | 值 |
|---|---|
| 载荷 TU 总字符 | ~9,260,000 |
| TU 数 | 28 |
| **超 350K 的 TU** | **4**（p0021 883K / p0025 563K / p0024 561K / p0027 440K）|
| 超过 350K 的**单个 unit** | **3**（hotpatch 874,416 / gcslotmap 799,731 / dispatch 555,918）|

**关键事实：每一个超预算 TU 都只含 1 个 unit**（已实测验证）。

### 1.2 因此问题的准确表述是

> **不是"装箱/切分做错了"，而是"有 3 个 section 比整个预算还大"。**

这句话决定了后续所有方案的取舍：**凡是作用于"如何把 unit 装进 TU"的手段
（装箱器、分页器、口径统一、全局视图）都不可能解决它** —— 它们处理的是
"多个小 unit 如何组合"，而这里根本没有组合，是一个 unit 自己超了。

我已用 300,000 次反例搜索证明贪心装箱在"给定不可分 unit、预算内装箱"上
不会产生可避免的超标；实测数据也显示超标 TU 全是单 unit。

## 二、为什么会有「比预算还大的 section」

三个大 section 的成因**各不相同**，这决定了它们不能用一个方案统一解决。

### 2.1 `hotpatch` 874,416 — 数据表 + 索引域耦合

| 数组 | 字符 | 占比 |
|---|---:|---:|
| `s_hotpatch_entries[1720]` | 603,879 | 68.9% |
| `s_hotpatch_methods[1720]` | 217,720 | 24.9% |
| `s_hotpatch_slots[1720]` | 47,486 | 5.4% |
| `s_hotpatch_types[45]` | 5,370 | 0.6% |

- 已分块的只有 `methods` / `types`（C3-3）
- **`entries` 的顺序有语义**：`s_hotpatch_slots[].slot` 硬编码了 entries 的下标
- `entries` 与 `methods` **不同序**（实测 0/10257 一致）⇒ 不能共用边界

### 2.2 `dispatch` 561,344 — 全局下标域的三个平行数组

| 数组 | 字符 | 占比 |
|---|---:|---:|
| `kMethodTable[1732]` | 254,775 | 45.4% |
| `kDefaultArgThunks[1732]` | 192,294 | 34.3% |
| `kSubjectSubjectIds[734]` | 98,248 | 17.5% |
| `kSubjectSlotMap/ContractMap[734]` | 10,336 | 1.8% |

- **实测：`kMethodTable[i]` 与 `s_hotpatch_entries[i]` 逐条相同 1720/1720**
  ⇒ 两者是同一符号序列，**必须共享切分网格**
- `kDefaultArgThunks[i]` 内联引用 `kMethodTable[i]`，同网格
- 三者都按**全局 match-slot 下标**寻址（`kSubjectSlotMap[si]` → 全局 `i`）

### 2.3 `gcslotmap` 256,064（已从 800K 降下）— 真正的 ABI 约束

- runtime `GcRegisterSlotMapsFromSection(begin, end)` 按 `entry_total_size` 步进的
  **单块连续内存**扫描
- 已通过"具名嵌套 struct → 扁平词数组"零 ABI 砍掉 52%（785K → 256K）
- 剩余 256K **本身已达标**（<350K）✅

## 三、根本解的候选方案

### 方案 A：**提高预算阈值**（不改代码）

**做法**：承认 350,000 对一个"单块数据表"过小，为其引入**分档预算**：
普通 section 350K，已知不可分的大数据表给一个更高的上限（如 1MB）。

**支持理由**：
- 350,000 的来源是 MSVC C1060（编译期堆耗尽），触发点实测在 **~15 MB / 448K 行**
  （`NativeAotEmitter.Shared.cs` 注释）
- 一个 874K 字符 / ~7,600 行的纯数据 TU，**离 15MB 的编译器崩溃点还有 17 倍余量**
- `gcslotmap`（256K，15,547 行）与 `reflection`（440K）编译均无问题（实测通过）
- **四个超标 TU 全都编译通过了** —— 没有任何一个触发 C1060

**代价**：放弃"每 TU ≤350K"这个统一口径，改为"分档 + 显式例外清单"。

**风险**：口径变复杂；后人可能滥用"例外"绕过真正的膨胀。

### 方案 B：**把"全局下标域"改为"chunk 感知寻址"**（ABI 演进）

**做法**（`design-entry-table-chunking-v2.md` 已详述）：
1. ABI 尾部追加 `entry_chunks` / `slot_chunks`
2. runtime 加 `HotpatchEntryAt(mod, index)` / `HotpatchSlotAt(mod, index)` 访问器
3. codegen 对 `entries` / `slots` / `kMethodTable` / `kDefaultArgThunks`
   按**同一网格**切分
4. 消费点（含 23 处 harness）全改走访问器

**收益**：`hotpatch` 874K 与 `dispatch` 561K **同批达标**（它们共享网格）。

**代价与风险**：
- 跨 **ABI + runtime + codegen** 三域
- 触碰**热路径**（`ChaosDispatchMethod` 每次打补丁方法调用都走）
- 需要 O(1)/O(log n) 的 chunk 定位（现有 `FindChunk` 是
  `O(chunk_count·log₂ chunk_count)`，需改为注册期预计算前缀和）
- **上一轮 26 步计划被两个对抗性评审双双判 FLAWED**（F1–F4 四个致命项）
- 新模块 + 老 runtime 不可解

### 方案 C：**改变数据表示，从源头消除文本量**（零 ABI）

**做法**：不动寻址方式，只让**同样的数据用更少的字符**表达。

可行手法（按已验证的经验）：
1. **去冗余前缀**：`kSubjectSubjectIds[]` 里每条都是
   `"CombinedSubjects/AutoGenerated.System_Private_Xml.System_Xml_XmlWriterTests::..."`，
   前缀高度重复 ⇒ 拆成「公共前缀表 + 后缀」或**按类型分组**
2. **符号名缩写**：`kMethodTable[]` 每条是完整 mangled 符号名（~148 字符/条）；
   可改为「类型索引 + 方法索引」或字符串池引用
3. **`s_hotpatch_entries`**：实测每条 ~350 字符，主要是 `type_name` + `method_name`
   重复出现（同样的字符串在 `s_hotpatch_methods` 里已有一份）

**已证实的先例**：本轮 `gcslotmap` 用同一思路（改发射形态而非寻址）**零 ABI 砍掉 52%**。

**收益估计**：`kSubjectSubjectIds` 98K → 可能 30K（前缀去重）；
`kMethodTable` 254K → 可能大幅下降（若符号名可池化）……

**风险**：
- 需要**逐表分析文本构成**（我还没做完整归因）
- 有些改动会触及"符号名 ↔ 消费者"的契约（如 harness 用符号名做日志）

### 方案 D：**把 section 提升为可切单元**（改 payload 分层）

**做法**：给 `PayloadSection` 增加"可切成多个独立 section"的声明
（`SectionSemantics.ByUnits` 已有协议，TP-Step2 建成但**尚无 producer**），
让 `dispatch` / `hotpatch` 内部的数组各自成为独立 section。

**关键限制**：这**只解决"多个数组挤在一个 TU"的问题**，
**不解决"单个数组自己超预算"**。

- 对 `dispatch`：`kMethodTable`(255K) + `kDefaultArgThunks`(192K) 若各自独立成
  section，则 255K/192K 都 **< 350K** ⇒ **可行！**
- 对 `hotpatch`：`entries` 603K 仍 > 350K ⇒ **仍不可行**

⇒ **方案 D 能让 dispatch 达标，但不能让 hotpatch 达标。**

**代价**：需要"同一网格"的约束被打破 —— 但实测三者**共享下标域**，
所以切分开后仍需运行时知道"索引 i 在第几个 chunk" ⇒ **仍需要 ABI**。
（除非用"数组间偏移"技巧，但那本质是 ABI 的一种。）

⚠️ 这是本轮我踩过的坑：`kSubjectSubjectIds` 切成了 2 个 chunk，
但两块仍在**同一个 section** 里，没被分到不同 TU ⇒ 白切。

## 四、方案对比

| 方案 | 覆盖面 | 跨域 | 触碰热路径 | 风险 | 已证实效果 |
|---|---|---|---|---|---|
| **A 提高阈值** | hotpatch + dispatch + reflection | 无 | 否 | 低 | — |
| **B ABI 演进** | hotpatch + dispatch | ABI+runtime+codegen | **是** | **高**（计划已被双重证伪） | — |
| **C 数据表示瘦身** | 逐表评估，可能全部 | 无 | 否 | 中 | ✅ gcslotmap −52% |
| **D section 提升** | 仅 dispatch | 需 ABI 配合 | 否 | 中 | 本轮证伪（同 section 无收益）|

## 五、我的建议

**先做 C，用它的实测数据决定是否需要 B。**

理由：

1. **C 是唯一已被证实有效的手法**：本轮 gcslotmap 用同一思路零 ABI 砍 52%。
   而它的前提是"逐表读产物做文本归因" —— 这正是本项目反复验证有效的方法
   （也是我多次凭推测下结论、事后被证伪的反面）。

2. **C 可能让 A/B 都不必要**：
   - `dispatch`：若 `kMethodTable` 的符号名可池化，255K 可能降到 100K 以内，
     加上 `kSubjectSubjectIds` 前缀去重，整个 TU 可能进 350K
   - `hotpatch`：`entries` 603K 里 `type_name`/`method_name` 与 `methods` 表重复，
     去重后可能显著下降

3. **B 的风险已被实证**：26 步计划被双重证伪，且触碰热路径。
   在没有 C 的数据之前做 B，是在**用最高风险的手段去解决一个可能不需要它的量**。

4. **A 是最低成本的兜底**：如果 C 做完仍差一点，A 用"分档预算 + 显式例外清单"
   收口，代价是口径变复杂 —— 但比 B 的 ABI 演进便宜一个数量级。

### 建议的执行顺序

```
第 1 步（先做，只读）：dispatch 三表 + hotpatch entries 的**文本构成归因**
    - kMethodTable 每条 148 字符里，符号名的"公共前缀"占多少？
    - s_hotpatch_entries 与 s_hotpatch_methods 的字符串重复率？
    - 产出一份"可压缩空间估计"

第 2 步：按归因结果做 C 的最优项（预期零 ABI）
第 3 步：重测。若达标 → 收工；若仍差 → 用 A 收口
第 4 步：仅当 A 也不可接受时，才启动 B（且有第 1 步的数据支撑）
```

## 六、如果一定要现在选一个

- 想要**最快见效、最低风险** → **A**（改常量 + 例外清单，可能 1 小时）
- 想要**最根本、且不碰 ABI** → **C**（需先做文本归因，1-2 轮）
- 想要**一劳永逸、接受高风险** → **B**（跨三域 + 热路径，且需重做已被证伪的设计）

**我不建议现在直接做 B。** 本轮已经有三次"先假设收益、再被实测推翻"
（dispatch/hotpatch 同问题、装箱器是瓶颈、切 98K 能达标），
而唯一成功的 gcslotmap 恰恰是**先读产物、再动手**。
