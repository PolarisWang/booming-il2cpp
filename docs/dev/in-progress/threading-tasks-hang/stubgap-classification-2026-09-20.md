# threading chunk stubGap 分类调查报告（2026-09-20）

> 任务：`lock-ctor-wire`（原计划：给锁类 `.ctor` 接线 `ChaosManagedHandleGetOrCreate`）
> 结论：**原计划前提不成立**，本报告用实测数据修正方向。
> 方法：架构查询（开工前置，CLAUDE.md 强制）

## 一、原计划及其前提

原计划（上一轮我提的建议）声称：

> 321 个 stubGap **高度集中于锁类**，是一个**共享根因**；
> 其中锁类约 **130 个**；修 `.ctor` → `GetOrCreate` 句柄接线可解。

## 二、实测证伪

### 2.1 321 个 stubGap **不是共享根因**

```
唯一 methodSubjectId 数: 321
stubGap 记录数:          321
```

**321 条记录 = 321 个不同 subject**，无一重复。不存在"一个根因解一片"。

### 2.2 锁类占比 **远低于** 声称的 130

按类型分布 TOP：

| 类型 | 数 |
|---|---:|
| WaitHandleTests | 60 |
| ThreadTests | 39 |
| ThreadPoolTests | 34 |
| MonitorTests | 31 |
| SemaphoreSlimTests | 24 |
| CancellationTokenTests | 16 |
| ... | |

但**关键在于**：`MonitorTests` 的样本是 `Monitor::Enter(object)` /
`TryEnter(object)` —— **静态方法，参数是 `object`，没有 handle 字段**。
"类型名里含 Monitor" ≠ "需要 handle 绑定"。

### 2.3 真正的分类维度：**异常类型**（决定性）

对 321 条按 ATG 产物的异常类型归类：

| 异常类型 | 数量 | 占比 |
|---|---:|---:|
| **System.ArgumentNullException** | **125** | 39% |
| System.NullReferenceException | 51 | 16% |
| System.NotSupportedException | 42 | 13% |
| System.InvalidOperationException | 38 | 12% |

| **System.Threading.SynchronizationLockException** | **7** | **2%** |
| 其余 | 14 | 4% |

**锁类真正的缺口只有 7 个**（`SynchronizationLockException`），
**不是 130 个**。

**参数校验类（ArgumentNull + NRE + ArgumentException）= 206 个 = 64%**，
与 handle 绑定**毫无关系**。

## 三、根因（ATG 侧，已定位到代码）

`src/tools/Chaos.IL2CPP.Tools.AutoTestGenerator/TestEmitter.cs:479-488`：

```csharp
if (isExternalAssembly)
{
    sb.AppendLine("            // AOT-STUB-GAP");
    sb.AppendLine($"            // [UNVERIFIED] AOT stub: {result.ExceptionType} thrown by {callExpr} (managed input->exception, AOT stub returns default — smoke test passes)");
    return;
}
```

**机制**：probe 用会触发异常的输入调用方法（如 `Register(default(Action))`
→ 真实 .NET 抛 `ArgumentNullException`）。ATG 判定该程序集为
`isExternalAssembly` 时，**不确定 AOT body 是否会同样抛异常**，
于是保守地**不生成 AOT body**，只写 smoke 占位 `return 42L;`。

产物实证（`CancellationToken.AutoGenerated.cs:60-65`）：

```csharp
public long Register_0_System_Action_0()
{
    // AOT-STUB-GAP
    // [UNVERIFIED] AOT stub: System.ArgumentNullException thrown by
    //   SubjectInstanceFactory.Create<System.Threading.CancellationToken>()
    //     .Register(default(System.Action)!) (managed input->exception,
    //   AOT stub returns default — smoke test passes)
    return 42L;
}
```

**故 `stubGap` 不是"实现缺口"，是 ATG 的保守判定** ——
它区分不了"AOT body 也会抛"与"AOT body 静默返回默认值"。

## 四、方向修正

原计划的 `.ctor` → `GetOrCreate` 接线：

- **收益**：最多 **7 个**（SynchronizationLockException），不是 130
- **不解决**：206 个参数校验类 + 42 NotSupported + 38 InvalidOperation
- **结论**：**收益/成本比过低，不值得作为主方向**

### 可能的真方向（未验证，供决策）

| 方向 | 覆盖 | 说明 |
|---|---|---|
| **A. ATG 异常语义比对** | **206+** | 让 ATG 实际比对「probe 观察到的异常类型」vs「AOT body 的行为」，一致则发真实 body 而非 AOT-STUB-GAP。**即 memory 里 `atg-stubgap-is-codegen-time-not-native` 指的方向** |
| B. 逐个补 native 实现 | 152 | 工作量大（152 个方法），且多数是参数校验，可能不需要 native |
| C. `.ctor`/`GetOrCreate` 接线 | 7 | 原计划；收益太小 |

**方向 A 与既有记录一致**（`atg-stubgap-is-codegen-time-not-native`：
"`value=42` 在 native 层不可修复，需 ATG 层 AOT probe 比对异常语义"）。

## 五、本报告的方法论价值

**开工前的架构查询拦下了一次方向错误。** 若直接照原计划实现
`.ctor` 接线，会：
1. 写大量代码，最多翻转 **7 个** subject（2%）
2. 而真正的大头（206 个参数校验类）完全没碰到
3. 最后得到一个"做了很多但数字没动"的结果

**教训（可复用）**：
- 「类型名聚类」≠「根因聚类」—— `MonitorTests` 含 31 个 stubGap，
  但它们调用的是**静态** `Monitor.Enter(object)`，与实例 handle 无关
- 分类必须用**机制维度**（此处=异常类型 / ATG 判定分支），
  不是**命名维度**（类型名 / 方法名）
- 先做**去重**再评估工作量：321 条 → 152 个方法，虚高一倍
