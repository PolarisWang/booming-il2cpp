## 二、为什么选 WaitHandle 家族

**数据**（`WaitHandle.AutoGenerated.cs`，60 个 stubGap）：

| 异常 | 数量 | 触发场景 |
|---|---:|---|
| `ArgumentNullException` | 37 | 静态 `WaitAll/WaitAny(null, …)` |
| `InvalidOperationException` | 13 | 实例方法对未初始化对象（`Close`/`Dispose`/`WaitOne`） |
| `ArgumentException` | 10 | 空数组等 |

**契约特征（这是选它的理由）**：

1. **全部是入口参数校验** —— 零并发语义
2. **不需要真的等待** —— 非法输入在触达等待逻辑前就抛
3. **不需要 handle 绑定** —— 与 `.ctor` 接线无关
4. **契约可从 .NET 实测确定**，无歧义

**子契约**（**已用 .NET 8 与 net10 双版本实测确认**）：

- **静态** `WaitAll(WaitHandle[], int|TimeSpan, bool)` / `WaitAny(...)`：
  - 数组 `null` → `ArgumentNullException` ✅ 实测
  - 空数组 → `ArgumentException` ✅ 实测
  - 含 `null` 元素 → `ArgumentNullException` ✅ 实测
- **实例** `WaitOne(...)` / `Close()` / `Dispose()` —— ⚠️ **见 §三之更正**

## 三、⚠️ 重大更正：实例类案例不可修（probe 构造缺陷）

实测发现实例类的 13 个案例**与静态的完全不同性质**：

| | 实例（13 个） | 静态（47 个） |
|---|---|---|
| probe 表达式 | `Create<WaitHandle>().WaitOne(...)` | `WaitHandle.WaitAll(null!, 0)` |
| 异常**来源** | **工厂自己抛的** | **被测方法抛的** |
| 为何 | `WaitHandle` 是**抽象类** → `GetUninitializedObject` 返回 null → `SubjectInstanceFactory.cs:39` **主动 throw InvalidOperationException** | 方法真的做参数校验 |
| 可修？ | ❌ **不可修**（probe 对抽象类调 `Create<T>()`，根本不合法） | ✅ 可修 |

**实测证据**（`SubjectInstanceFactory.Create<T>`，`src/reference/Chaos.TestFramework.Sdk/`）：

```csharp
public static T Create<T>()
{
    if (typeof(T).IsValueType) return default(T)!;
    var instance = RuntimeHelpers.GetUninitializedObject(typeof(T));
    if (instance is null)
        throw new InvalidOperationException(          // ← probe 观察到的 IOE 出自这里
            $"SubjectInstanceFactory.Create<{typeof(T)}>: GetUninitializedObject returned null...");
    return (T)(object)instance;
}
```

且 `WaitHandle` 上的方法实测**并不抛 IOE**：

| 调用（`WaitHandle` 引用，net8 与 net10 结果相同） | 实测 |
|---|---|
| `Uninit.WaitOne(0)` | `ObjectDisposedException`（**不是** IOE） |
| `Uninit.Close()` | **OK（不抛）** |
| `Uninit.Dispose()` | **OK（不抛）** |

**结论**：实例类 13 个的正确处置是**修 probe 构造**（换具体子类）或标 `factoryGap`，
**不是补 native**。本轮**不做这 13 个**。

### 6.3 ATG 白名单为何有害

`f7852434f` 让 `ExternalStubRaisesManagedException` 对 WaitHandle 静态方法返回 true，
生成 `try { call; throw new Exception("AOT stub did not throw"); } catch { }`。

**问题**：shape 没匹配上 → AOT 侧走 `chaos_external_runtime_*` **catch-all**，
它**返回 0 而不抛异常** → 于是 `throw new Exception(...)` 触发 →
subject 记录 **`caught=True`, `failed`**。

**数字证据**：

| | 基线 main | 加 ATG 白名单后 |
|---|---:|---:|
| stubGap | 321 | 267 |
| **failed** | **21** | **43**（+22） |
| realVerified | 112 | 115 |

**即：把 22 个「诚实的 stubGap」换成了「真 failed」—— 假红，与假绿同样有害。**

**教训**：ATG 白名单与 shape 注册是**一对**。只加白名单（不加能生效的 shape），
等于断言一个 AOT 侧产生不了的异常。
