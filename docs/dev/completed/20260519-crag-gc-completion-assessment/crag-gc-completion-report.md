# CRAG GC 完成度综合评估报告

> **日期**: 2026-05-19
> **范围**: `src/native/runtime-core/gc/` 全部 36 个文件 (~11,000 行 C++)

## 二、分项能力深度对比

### 2.1 分代收集 (Generational GC)

| 能力 | CRAG | CoreCLR | Mono | Unity | 风险评估 |
|------|------|---------|------|-------|---------|
| 新生代 Cheney 复制 | ✅ | ❌ (Mark-Sweep) | ✅ (类似) | ❌ | **低** — Cheney 是成熟算法 |
| 多代晋升策略 | ⚠️ 单次晋升 | ✅ gen0→1→2 多级 | ✅ nursery→old | ❌ | **中** — 单次晋升会导致 old gen 增速快 |
| 自适应分代大小 | ✅ EMA 存活率 | ✅ 自适应 | ✅ 自适应 | ❌ | **低** — 实现合理 |
| 年龄分段 (age table) | ❌ | ✅ | ✅ | ❌ | **低** — 无年龄分段不致命，但影响晋升决策精度 |
| 写屏障 (card table) | ✅ 两级 | ✅ card+隔离 | ✅ card | ❌ | **低** — 实现完整 |
| 记忆集 (remembered set) | ❌ | ✅ (card table 变体) | ❌ (card table) | ❌ | **低** — card table 可全覆盖 |

**CRAG 差异**: 新生代直接使用 Cheney 复制（非 Mark-Sweep），与 CoreCLR 架构不同。Card table 设计两级的灵感来自 Azul C4 / ZGC，而非 CoreCLR。

**CRAG 差异**: CRAG 的精确栈扫描依赖于 T4 代码生成时注册的 GcSlotMap。解释器帧 (T1-T3) 仅通过保守扫描覆盖。这意味着解释器中活跃的对象引用如果不在 nursery 中(只在栈上)可能被误判——但保守扫描会捕捉到它们。

## 三、缺失能力风险评估

### 高危 (会影响生产可用性)

| 缺失能力 | 影响 | 优先级 | 说明 |
|---------|------|--------|------|
| **线程挂起超时/看门狗** | 安全点失败 = 进程 STW 死锁 | **P0** | 单个线程不响应安全点会导致所有线程无限期阻塞。CoreCLR 有 100ms 超时 + 抢占式挂起回退。 |
| **终结器线程看门狗** | 终结器死锁 = 内存泄漏 | **P1** | 终结器内死锁会阻止所有 future finalizable 对象回收。 |

### 中危 (影响特定场景)

| 缺失能力 | 影响 | 优先级 | 说明 |
|---------|------|--------|------|
| **寄存器根丢失** | 瞬时对象引用丢失 → 提前回收 | **P1** | T4 帧中寄存器存放的对象引用如果不在栈溢出槽中，保守扫描找不到。实际风险低(寄存器值通常会被 spill 到栈上)，但仍需在 Phase 3d 精确 slot map 中确认。 |
| **单次晋升碎片化** | old gen 碎片率上升快 | **P2** | 无年龄分段，所有存活对象一次性`memcpy`到 old gen。如果临时大对象频繁创建，old gen 中会残留许多"死"段等待 BGC 清除。 |
| **NUMA 非感知** | 多 socket 机器上 BGC 性能差 | **P2** | CoreCLR server GC 在 NUMA 上每个 socket 分配独立堆。CRAG 全局共享一个堆，跨 socket 访问的内存延迟差异将影响标记/压缩。 |

### 低危 (可推迟)

| 缺失能力 | 影响 | 优先级 | 说明 |
|---------|------|--------|------|
| **CriticalFinalizer** | .NET Framework 兼容性 | **P3** | 非核心功能，.NET Core 也逐步淡化 |
| **GC 压力模式** | 测试覆盖 | **P3** | 有 stress test，但无 gcstress 类似模式 |
| **屏障合并优化** | 性能 | **P3** | 代码生成优化，不影响正确性 |
| **显式静态根注册** | 完整性 | **P3** | GCHandle 可替代 |

## 四、CRAG GC 独有优势

| 特性 | 描述 | 在哪方面优于 CoreCLR |
|------|------|---------------------|
| **跨页逐出压缩** | 合并多个碎片页的存活对象到一个页，释放完整页 | CoreCLR 仅做页内压缩，无法解决跨页碎片 |
| **哨兵稳定 ID 自由块追踪** | 不需要页首部即可识别 free 块，对 BGC 并发清除安全 | CoreCLR 使用页首部，需要 STW 维护 |
| **两级卡表** | 稀疏设计，仅 64K L1 条目 + 按需增长 | CoreCLR 卡表固定大小，4GB 堆需 16MB 卡表 |
| **Cheney 复制新生代** | 分配即转发，无需标记-清除 | CoreCLR 新生代是 mark-sweep，分配成本高 |
| **GcSlotMap 混合扫描** | T4 精确 + 保守回退，无漏根 | Mono/Unity 纯保守有假阳性 |

## 六、推荐下阶段优先级

| 优先级 | 项目 | 预估工作量 | 说明 |
|--------|------|-----------|------|
| **P0** | 线程安全点超时 + 抢占式挂起回退 | 3-5 天 | 防止进程 STW 死锁 |
| **P0** | 终结器线程看门狗 + 超时 | 2-3 天 | 防止终结器泄漏 |
| **P1** | 精确 slot map 完成 (Phase 3d) + 寄存器根确认 | 3-5 天 | 消除保守扫描理论风险 |
| **P1** | 新生代年龄分段 (1-2 次存活后才晋升) | 3-5 天 | 降低 old gen 碎片率 |
| **P2** | NUMA 感知堆布局 | 5-10 天 | 多 socket 性能提升 |
| **P2** | GC stress 模式 (gcstress) | 3-5 天 | 压力测试覆盖 |
| **P3** | 显式静态根注册 | 2 天 | 完整性 |
| **P3** | 屏障合并优化 (codegen) | 3-5 天 | 性能优化 |
