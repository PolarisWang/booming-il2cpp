# 类 IL2CPP 的 C# 到 C++ 系统设计

**日期：** 2026-03-30 00:16:31 +08:00

**状态：** 对话中已批准的草稿，待用户复核

## 目标

设计一个将 C#/.NET 项目翻译为 C++ 的系统，其能力范围整体上可与 Unity IL2CPP 相比较，并遵循分阶段推进的路线图：

- 第 1 阶段优先保证工程可交付性
- 性能是下一优先级的重要目标
- 长期目标是逐步接近 IL2CPP 级别的覆盖面与健壮性

本设计的前提假设如下：

- 以 IL/程序集优先作为规范化主流程
- 运行时完全自研
- 从一开始就面向跨平台目标
- 主线支持类库、控制台应用、CLI 工具、后台任务、通用服务端程序以及原生宿主嵌入
- 对动态特性采用分层支持，而不是要求在第 1 阶段全部完成

## 非目标

以下内容不属于第 1 阶段主线承诺的一部分：

- `dynamic`
- `System.Reflection.Emit`
- 类似 `Assembly.Load` 的动态延迟加载
- 完整的表达式树编译
- 以框架为核心的重量级 UI 技术栈，例如 WPF、WinForms、MAUI
- 类似 ASP.NET 的全栈框架完备支持

这些能力未来可以补充，但它们不用于定义第 1 阶段的架构边界。

## 架构总览

系统被划分为两个主要平面：

1. 翻译流水线
2. 运行时平台

主流程如下：

`source -> dotnet build/csc -> IL assemblies + metadata -> semantic/AOT analysis -> runtime-contract IR -> C++ emission -> native build -> executable/library/bundle`

核心子系统包括：

1. `Frontend Gateway`
2. `Assembly and Metadata Loader`
3. `Semantic and AOT Analyzer`
4. `IR Layer`
5. `C++ Backend`
6. `Runtime Core`
7. `Interop and Platform Abstraction`
8. `Build and Packaging`

核心架构规则：

- 高层托管语义必须先收敛到统一的 IR 与运行时契约，再进行平台相关的 lowering。

## 前端边界

系统的规范边界是以 IL/程序集优先为主。

这意味着：

- 标准 C# 编译流程仍然是入口
- 系统消费已编译的程序集（`.dll`、`.exe`）以及对应的元数据和符号
- 翻译器的角色是 IL AOT 后端，而不是替代 C# 语言编译器

源码感知能力仍然有价值，但只作为辅助层用于：

- 诊断
- 源码映射
- 调试元数据增强
- 开发者体验改进

源码感知逻辑不被视为与主翻译前端同等地位的系统入口。

## 运行时模型

运行时被划分为三个内部层次：

1. 对象与内存模型
2. 执行语义层
3. 元数据与反射层

### 对象与内存模型

所有托管堆对象共享一个稳定的 `ObjectHeader`。

该头部至少应支持：

- `TypeInfo*`
- GC 状态/标记位
- 同步/monitor 相关状态
- 可选的缓存身份/hash 状态

数组、字符串和普通对象共享相同的根对象语义，具体负载布局则位于运行时定义的契约之后。

生成出来的 C++ 代码不能直接假设底层原始内存布局，而必须始终通过运行时定义的对象访问规则进行操作。

### GC 方向

即使第 1 阶段使用更简单的精确 GC，整体架构也应当为未来的移动式收集器做好准备。

这意味着生成代码从一开始就必须依赖：

- 显式 root 跟踪
- 在需要处注册 handle
- 写屏障
- safepoint
- 由运行时拥有的对象/slot 访问辅助函数

这样可以保证未来升级 GC 时，不需要破坏生成代码 ABI。

### 执行语义层

该层负责：

- 异常创建、传播以及与原生展开机制的桥接
- 线程注册与分离
- TLS 集成
- safepoint 与 stop-the-world 协调
- 虚调用分发
- 接口分发
- 泛型运行时支持
- 托管/原生切换协议

### 元数据与反射层

反射元数据必须是运行时中的一等模型，而不是代码生成过程顺带产生的附属物。

运行时应维护以下正式结构：

- `TypeInfo`
- `MethodInfo`
- `FieldInfo`
- `PropertyInfo`
- `EventInfo`
- `GenericContext`
- 程序集/模块标识

这不仅对反射本身是必要的，也对以下能力必不可少：

- 异常格式化
- 序列化
- 诊断
- 运行时泛型解析

核心规则：

- 生成代码表达业务行为；托管语义由运行时契约负责。

## 翻译流水线与 IR

在 IL 输入与 C++ 输出之间使用三层表示。

### 1. Metadata Graph

目的：

- 定义已加载程序集的语义世界模型

职责：

- 程序集与模块
- 类型定义与类型引用
- 继承关系与接口关系
- 字段与方法签名
- 特性
- 泛型参数与约束
- 资源与符号挂接

这一层避免后续阶段重复解析原始程序集。

### 2. Typed IL IR

目的：

- 将方法体转换为适合分析的显式控制流/数据流形式

特性：

- 栈语义被规范化消除
- 局部变量与临时变量显式化
- 控制流图显式化
- 异常区域显式化
- 调用点与分发类型显式化
- 装箱/拆箱/数组操作变为显式节点

这是以下分析工作的主层：

- 调用图
- 虚调用闭包
- 接口调用闭包
- 泛型实例发现
- 反射保留逻辑
- 序列化保留逻辑

### 3. Runtime-Contract IR

目的：

- 以一种对后端稳定、且不依赖原始 IL 形态的方式表示托管语义动作

这一层的操作示例包括：

- 对象分配
- 数组分配
- 分发操作
- 元数据查找
- 类型检查与转换
- 写屏障
- 异常边界操作
- GC/handle 切换
- P/Invoke 切换

C++ 后端应以这一层 IR 为目标，而不是直接面向 IL。

### AOT 分析闭环

分析器应物化出一个显式的闭世界结果：

`roots -> call graph -> virtual/interface closure -> generic instantiations -> reflection preservation -> serialization preservation -> native export set`

输出必须记录到一个显式的 `AOT manifest` 中。

该 manifest 用于：

- 可复现性
- 增量重建支持
- 诊断
- 代码生成边界稳定性
- 回归对比

核心规则：

- 分析输出必须是可持久化产物，而不是隐藏在代码生成内部的副作用。

## C++ 后端与 ABI 策略

后端被划分为两部分：

1. 可移植发射层
2. 平台 ABI 适配层

### 可移植发射层

职责：

- 为 runtime-contract IR 发射稳定、统一的 C++
- 尽可能避免依赖编译器特定语义
- 保留有价值的调试结构
- 让生成结果在优化和诊断上都保持可预测性

### 平台 ABI 适配层

职责：

- 调用约定
- 符号可见性/导出规则
- 异常互操作边界
- 线程本地存储差异
- 原子操作与内存模型细节
- 不同编译器家族的特殊性

这一层将平台/编译器差异隔离在后端局部，而不让它们扩散到整个后端。

### 类型与布局策略

托管语义优先于原生语言惯用法。

运行时拥有以下对象的规范表示：

- 引用类型
- 值类型
- 装箱值
- 字符串
- 数组
- 委托
- 泛型实例

生成出来的 C++ 应面向这些契约，而不是为不同平台临时拼出各自的布局。

### 互操作边界

必须显式设计三个边界：

1. `Managed -> Native`
2. `Native -> Managed`
3. `Generated C++ -> Runtime Core`

第三个边界是最重要的内部 ABI，必须尽早版本化并稳定下来。

### 输出形态

系统应支持：

- 独立原生可执行文件
- 静态库或动态库
- 可嵌入的运行时 bundle

这是为了同时支持服务端部署和原生宿主嵌入。

核心规则：

- 先稳定内部 ABI，再适配外部 ABI。

## 互操作与平台抽象

由于目标从第 1 阶段起就是跨平台，因此平台抽象必须从一开始就存在。

抽象层应覆盖：

- 线程
- 互斥量/条件变量
- 文件系统
- 时间与定时器
- 进程/环境访问
- TLS
- 原子操作
- 第 1 阶段运行时所需的套接字/网络原语
- 加载器与符号解析工具

目标不是隐藏所有平台差异，而是防止平台假设泄漏进翻译流水线和运行时语义模型。

## 构建与打包

构建驱动应编排以下流程：

- 项目编译为程序集
- 调用翻译器
- 选择运行时源码
- 编译生成的 C++
- 平台相关的原生链接
- 生成符号/调试文件
- 打包为可执行文件、库或 bundle 形式

建议输出物包括：

- translated sources manifest
- AOT manifest
- 生成的 CMake/原生构建描述
- 最终打包的二进制或库
- 符号/映射产物

构建系统应将可复现性视为一等关注点。

## 阶段路线图

### 第 1 阶段 - MVP

目标：

- 在选定的主线范围内，能够翻译、编译并运行真实项目

范围内项目：

- 类库
- 控制台应用
- CLI 工具
- 后台任务
- 通用服务端程序
- 原生宿主嵌入

必须具备的能力：

- 稳定的程序集加载与元数据模型
- typed IL IR 与 runtime-contract IR
- root/调用图/泛型/反射保留闭环
- 自研运行时核心
- 精确 GC 基线
- 异常支持
- 线程注册与 safepoint
- 反射基础能力
- 泛型基础能力
- P/Invoke 基础能力
- 跨平台原生构建

第 1 阶段不要求：

- `dynamic`
- `Emit`
- `Assembly.Load`
- 完整表达式树编译
- 重量级框架完备支持

### 第 2 阶段 - 增强平台

目标：

- 提升语义深度、项目成功率、可诊断性与性能

典型工作包括：

- 更强的反射保留能力
- 更好的泛型共享/特化策略
- 增量 manifest 与缓存
- 兼容性诊断与报告
- 更稳健的宿主嵌入接口
- 更好的元数据与二进制体积缩减
- 更强的优化 pass 与去虚调用机会

### 第 3 阶段 - 接近 IL2CPP 能力

目标：

- 逐步接近平台级产品质量与覆盖广度

典型工作包括：

- 更深入的动态特性支持
- 更强的调试/符号体验
- 更高级的 GC/性能调优
- 更广泛的框架适配
- 更优的启动时间、吞吐与二进制体积优化

阶段规则：

- 每个阶段的判断标准都是“真实项目成功率”，而不只是功能清单是否打勾。

## 验证策略

验证必须从一开始就分层建设。

### 1. 流水线正确性

验证以下产物之间的一致性：

- 输入程序集
- metadata graph
- typed IL IR
- AOT manifest
- 生成的 C++
- 产出的原生制品

目的：

- 捕捉分析与代码生成之间的漂移

### 2. 运行时语义测试

为以下内容建立专门的运行时一致性测试：

- 对象模型
- GC 行为与 safepoint
- 异常
- 反射查询
- 泛型运行时行为
- P/Invoke 切换
- 线程 attach/detach 行为

### 3. Golden Project Suite

维护一组有代表性的真实 .NET 项目，覆盖：

- 类库
- CLI 工具
- 后台任务
- 服务端程序
- 嵌入场景

成功标准至少应包括：

- 翻译成功
- 编译成功
- 运行成功
- 行为与预期结果相比可接受

### 4. 跨平台一致性

在支持的平台矩阵上运行代表性项目，以验证：

- ABI 正确性
- 异常行为
- 线程行为
- 文件系统与编码行为
- 时间/定时器行为
- 编译器家族兼容性

核心规则：

- 在优化单个部件之前，先验证整条链路。

## 主要风险

顶层风险包括：

1. 泛型与反射闭包膨胀
2. GC/线程/异常耦合导致运行时行为不稳定
3. 平台 ABI 差异泄漏进生成代码
4. 过早承受来自第 1 阶段范围之外重量级框架的支持压力

风险控制方式：

- 保持显式的 AOT manifest
- 在激进优化前先稳定运行时契约
- 隔离 ABI 适配层
- 严格执行阶段边界
- 持续衡量真实项目成功率

## 阶段退出标准

阶段完成应以代表性项目成功为准，而不是模块开发完成为准。

示例性的第 1 阶段退出标准：

- 至少有一套代表性类库可以被正确翻译并执行
- 至少有一个 CLI/后台任务样例可以端到端跑通
- 至少有一个原生宿主嵌入场景成功
- 至少有一个跨平台子矩阵在一个以上平台上通过核心语义验证

核心规则：

- 在扩展范围之前，先强制满足阶段退出标准。

## 后续规划的开放主题

这份设计已经足以开始实现规划，但下一轮规划应将工作拆成具体执行轨道，例如：

- 元数据加载器与世界模型
- IL 规范化与 typed IR
- AOT 闭包引擎与 manifest 格式
- 运行时对象模型与精确 GC 基线
- 异常/线程/safepoint 协议
- 反射元数据运行时
- 可移植 C++ 发射器
- ABI 适配层
- 打包/构建驱动
- golden project 与语义验证套件
