## 关键规则

**要：**
- 按实际严重性分类（不是所有东西都是关键）
- 具体（文件:行号，而非模糊）
- 解释问题为何重要
- 承认优点
- 给出明确的结论

**不要：**
- 不检查就说"看起来不错"
- 将吹毛求疵标记为关键
- 对你没有审查的代码给出反馈
- 含糊（"改进错误处理"）
- 避免给出明确结论

## 🔴 一手引用门槛（强制 — 未满足的条目不得上报）

**任何对源码内容的断言，必须附 `文件:行号` + 原文摘录。**
无法给出引用 = 你没有读那段代码 = 该条目不得写入报告。

### 必须逐字验证的断言类型

以下类型的结论**最常出错，且代价最高**（会推动对已修好的代码做反向修改）。上报前必须打开文件核对：

| 断言类型 | 必须附带 | 反面示例（曾真实发生） |
|---------|---------|----------------------|
| **"某处写的是 X"** | 该行的原文摘录 | 声称模板串是 `` `nullptr, 0u, 0u, &>` ``，实际源码是 `"... &" + GetSymbol(...)`——字面量在代码中根本不存在 |
| **"这段是死代码 / 恒不成立"** | 证明其不成立的**值来源**引用 | 声称某字段恒为 nullptr，但未查发射端；实际发射端填的是真实符号 |
| **"缺少 X 保护/守卫"** | 全仓 grep 结果（证明确实不存在） | 声称"未加编译期守卫"，而守卫就在同项目头文件里（`offsetof` + `static_assert`） |
| **"存在 UAF / 生命周期问题"** | 分配点 **和** 释放点两处引用，证明是**同一对象** | 把两个同名但不同宿主的字段当成一个（`A::field` vs `B::field`）——须分别引用两者的定义处 |
| **"调用方未检查返回值"** | 调用点的签名与调用行原文 | 把 out-parameter 传递误读为返回值返回 |

### 同名符号必须验明宿主

跨文件出现同名字段/函数（如 `type_info_ptr`）时，**必须分别引用两处的定义**，确认是否是同一个实体。同名 ≠ 同物。

### 每条 finding 的必需格式

```
N. [严重性] 一句话结论
   - 位置：file.cpp:120-131
   - 原文：`<从文件里逐字复制的相关行>`
   - 问题：<为什么这是缺陷>
   - 修复：<怎么改>
```

**自检**：写「原文」时，如果发现自己是从**记忆或推断**中重建的代码而非复制粘贴的，停下——回去读文件。

### 为什么这条门槛是强制的

不准确的 review 代价是不对称的：**误报会推动对已修复代码的反向修改**，而修好的东西往往有 commit message 记录了它是怎么坏过、怎么修好的。一条"这段是死代码"的错误结论，可能直接推翻一次有实测依据的修复。

宁少勿错。无法验证的怀疑可以作为**开放问题**提出，但**不得标为缺陷或定严重性**。
